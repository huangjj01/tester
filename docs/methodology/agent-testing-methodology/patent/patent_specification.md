# 说明书

## 发明名称

一种基于分层约束与流程门禁的 AI Agent 测试工程闭环方法及系统

## 技术领域

本发明涉及人工智能辅助软件测试技术领域，具体涉及一种基于分层约束与流程门禁的 AI Agent 测试工程闭环方法及系统。

## 背景技术

随着大语言模型技术的发展，AI Agent 已经能够参与软件测试中的多类任务，包括阅读需求文档、生成测试用例、执行命令、检索日志和总结测试结果。

现有技术中，AI Agent 辅助测试的实践主要分为三类：

第一类是基于提示词的测试用例生成技术，即根据需求文档、接口说明或源代码生成测试用例。该类技术提升了用例草拟效率，但停留在"应该测什么"的层面，对环境前置确认、工具选择、执行证据采集和报告交付缺少约束。

第二类是基于 ReAct 模式的 Agent 执行技术，即 AI Agent 按照推理-行动循环调用命令、浏览器、日志检索和自动化脚本完成操作。该类技术增强了执行能力，但若缺少任务路由和证据模板约束，Agent 可能在错误的流程中执行正确的命令，产生不可复核的结果。

第三类是面向 CI/DevOps 的 Agent 技术，主要围绕已有 issue、流水线和失败信号进行分析和修复。该类技术接近工程现场，但较少覆盖从测试用例设计到测试执行报告的完整交付链路。

上述现有技术存在以下共同缺陷：

缺陷一：任务入口不稳定。AI Agent 接收到测试请求后，可能直接进入下单执行或日志查询，而不是先确认应该进入哪条测试流程。后续动作可能服务于错误的测试目标。

缺陷二：环境前置确认缺失。AI Agent 在执行测试用例前，未确认目标环境的版本、包、二进制、配置、启动参数和环境变量是否满足测试前提。即使测试结果符合预期，也无法证明是目标功能的行为。

缺陷三：测试工具选型隐含化。AI Agent 倾向于使用已有的批量工具或背景流量观察替代定向验证，导致测试输入不可控、证据不可归因到具体测试用例。

缺陷四：执行证据散落。测试结果停留在对话上下文中，未持久化为可复核的执行记录。后续工程师或 Agent 无法交接和复查。

缺陷五：结论定性不可控。AI Agent 可能将未经证实的推断写成正式测试结论，或将未知现象直接判定为正常，缺少基于业务字典和跨层证据的系统化判断机制。

缺陷六：流程约束仅依赖文档。现有方法通过规则文档和技能文档约束 Agent 行为，但 Agent 仍可能跳过关键环节。文档约束缺少可执行的校验和阻止机制。

## 发明内容

### 本发明要解决的技术问题

本发明要解决的技术问题是：如何将 AI Agent 在测试任务中的不确定性行为纳入可执行、可检查、可恢复的工程过程，使 Agent 的测试工作具备可复核性和可交接性。

### 技术方案

为解决上述技术问题，本发明提供一种基于分层约束与流程门禁的 AI Agent 测试工程闭环方法，包括以下步骤：

步骤 S1、任务路由步骤：接收用户测试请求，将所述测试请求与预定义的工作流目录进行匹配，确定当前测试任务对应的主工作流类型、子流程和必读资产集合。当所述测试请求未命中任何预定义工作流时，生成未命中说明并阻止进入后续步骤。该步骤解决了任务入口不稳定的问题。

步骤 S2、需求与用例约束步骤：对所述测试任务涉及的多源需求信息进行甄别对齐，所述多源需求信息包括需求文档、代码变更、通知和用户澄清。基于甄别结果生成覆盖清单和测试用例集合，其中区分理论可覆盖范围与当前可执行范围。该步骤解决了需求基线不稳定和覆盖遗漏的问题。

步骤 S3、测试实施设计步骤：在执行测试用例前，强制完成环境前置确认、测试工具选型和逐用例执行方案设计三个子步骤。

其中，环境前置确认子步骤确认测试所依赖的目标环境、版本、包、二进制、配置、启动参数、环境变量和外部依赖。

测试工具选型子步骤针对每个测试用例，从输入控制能力、断言能力、证据归因能力、mock 能力、环境影响和可重复性六个维度评估并选择测试工具。

逐用例执行方案设计子步骤为每个测试用例生成包含输入构造、执行动作、断言条件、证据采集路径和环境恢复步骤的可执行方案。

该步骤解决了环境前置缺失和工具选型隐含化的问题。

步骤 S4、执行证据采集步骤：在测试执行过程中，按预定义的证据模板采集并持久化执行事实，所述执行事实包括用例标识、实际输入、运行态信息、关键业务标识、实际输出、断言结果和证据存储路径。该步骤解决了执行证据散落的问题。

步骤 S5、判断基线约束步骤：基于预定义的业务行为字典和已知缺陷库，将测试产出按三分法分类为正常、异常和未知三类。其中，正常类要求命中业务字典且证据链自洽，异常类要求命中异常模式或跨层证据不自洽，未知类标记为待确认且禁止写入正式结论。该步骤解决了结论定性不可控的问题。

步骤 S6、交付与沉淀步骤：从执行记录和覆盖矩阵生成测试报告，所述测试报告禁止新增执行记录中不存在的结论。测试结束后生成测试工程反思候选，将本次测试暴露的流程缺口转化为可复用工程资产候选。

步骤 S7、流程门禁强制步骤：在步骤 S3 至 S6 的执行过程中，通过流程门禁系统对每个步骤的产物进行结构校验和内容非空校验，校验未通过时阻止进入后续步骤，校验通过后持久化步骤完成状态并推进至下一步骤。该步骤解决了流程约束仅依赖文档的问题。

本发明还提供一种基于分层约束与流程门禁的 AI Agent 测试工程闭环系统，包括工作流配置模块、状态管理模块、门禁校验模块、目标产物模式模块和中断恢复模块。

所述工作流配置模块用于定义测试实施步骤序列、步骤间依赖关系、每个步骤的产物输出路径和门禁校验规则。

所述状态管理模块用于创建和维护工作流运行实例，将运行状态和每个步骤的执行状态持久化为本地文件。

所述门禁校验模块用于在步骤完成时对步骤产物进行结构校验和内容非空校验，校验通过时推进至下一步骤，校验未通过时阻止推进并记录错误信息。

所述目标产物模式模块用于根据用户指定的目标产物类型动态确定必经步骤集合。

所述中断恢复模块用于在 AI Agent 执行中断后，通过读取持久化的状态文件恢复执行进度。

### 技术效果

本发明的技术效果包括：

1. 通过六层分层约束，将 AI Agent 在测试任务中的不确定性行为分解为六类可控的工程约束，每一层对应一类断裂点，使 Agent 的测试行为从依赖上下文记忆转变为依赖显式工程约束。

2. 通过流程门禁系统，将文档约束升级为可执行的校验机制，能够在 Agent 跳过关键环节时实时阻止，而不是事后发现。

3. 通过状态持久化和中断恢复机制，使测试实施过程不依赖 AI Agent 的对话上下文，支持跨会话、跨时间段的连续执行。

4. 通过目标产物模式，支持按需执行部分流程，避免简单任务承担完整闭环的成本。

5. 通过三分法判断基线和业务字典机制，将测试结论的形成从 Agent 的主观判断转变为基于预定义基线的系统化分类，降低误报和漏报风险。

6. 通过反思沉淀机制，将每次测试暴露的流程缺口转化为可复用工程资产，使系统的约束能力随使用次数增长而持续增强。

### 实施例一：分层约束方法的具体实施

本实施例详细说明六层约束方法的具体实施方式。

**一、任务路由层的实施**

任务路由层通过项目级工作流目录实现。所述工作流目录采用结构化文档形式，定义了以下映射关系：

- 任务类型到主工作流的映射：例如"功能测试实施"映射到测试实施工作流，"失败排查"映射到故障分析工作流，"部署验证"映射到部署工作流。
- 主工作流到子流程的映射：例如测试实施工作流包含用例设计子流程、实施设计子流程和执行记录子流程。
- 主工作流到必读资产的映射：例如测试实施工作流要求读取测试实施技能文档和模板文件。

AI Agent 接收用户请求后，首先将请求文本与工作流目录中的任务类型进行语义匹配。匹配成功时，Agent 进入对应的主工作流，并按声明的子流程和必读资产执行。匹配失败时，Agent 必须显式输出未命中说明，不得临时拼接流程。

任务路由层的工程资产包括：
- 入口规则文件：定义红线约束和强制入口，规定哪些任务必须进入正式流程。
- 工作流路由文件：定义任务类型到主工作流、子流程、必读文档和输出结构的映射。
- 技能文档：承载具体可复用操作步骤。

**二、需求与用例层的实施**

需求与用例层通过信息源甄别和覆盖清单机制实现。

信息源甄别的具体步骤为：
1. 列出所有信息源，包括需求文档、代码变更、通知、历史缺陷和用户澄清。
2. 对不同信息源中的同一需求点进行交叉比对，标记冲突项。
3. 对冲突项标记为待确认，不得以单一信息源为准。

覆盖清单的生成步骤为：
1. 从甄别后的需求中提取测试点。
2. 按业务维度组织测试点为覆盖清单。
3. 区分理论可覆盖范围和当前可执行范围。
4. 将不可构造输入、缺少环境前提或缺少工具支持的测试点标记为"本轮不执行"或"部分覆盖"。

测试用例的生成要求每个用例包含：前置条件、输入、预期输出、断言方式和证据采集方式。生成完成后，执行覆盖清单回查，确认每个覆盖清单项至少对应一个测试用例。

**三、测试实施设计层的实施**

测试实施设计层包含三个强制子步骤：

环境前置确认的检查项包括：
- 目标环境标识（测试环境、预发布环境等）
- 目标版本、包或二进制文件
- 服务进程和配置文件
- 启动参数和环境变量
- mock 服务和外部依赖
- 环境恢复基线

测试工具选型的评估维度包括：

| 维度 | 评估问题 | 影响 |
|------|---------|------|
| 输入控制 | 是否能精确构造测试输入 | 决定使用定向工具还是批量工具 |
| 断言能力 | 工具是否支持自动断言 | 决定是否需要补充断言逻辑 |
| 证据归因 | 是否会混入背景流量 | 决定测试结果是否可归因到具体用例 |
| mock 能力 | 是否需要模拟外部事件 | 决定是否需要 mock 服务 |
| 环境影响 | 是否会影响其他测试 | 决定是否需要隔离 |
| 可重复性 | 是否能稳定复现 | 决定是否适合回归测试 |

工具选型结果以结构化表格输出，包含：用例场景、现有工具覆盖情况、选用工具、是否需要新增用例或脚本、断言方式、选择理由和缺口风险。

逐用例执行方案为每个测试用例生成可执行的步骤序列，包含：输入构造方式、执行动作、断言条件、证据采集路径和环境恢复步骤。

**四、执行证据层的实施**

执行证据层要求在测试执行过程中同步采集以下类型的证据：

| 证据类型 | 具体内容 |
|---------|---------|
| 标识类 | 订单标识、请求标识、追踪标识、用例标识 |
| 日志类 | 应用日志、事件日志、协议消息日志、系统日志 |
| 报告类 | 自动化测试报告、统计文件 |
| 运行态 | 进程命令行、进程标识、配置文件、版本信息 |
| 外部层 | 下游原始报文、mock 服务记录、监控指标 |

证据采集的关键要求：
- 使用完整标识精确匹配，禁止使用尾号、时间邻近或同类样本替代。
- 每个用例的证据必须能回溯到同一笔业务事件。
- 若某一证据层无记录，必须显式记录"已检查但无记录"，不得省略。

**五、判断基线层的实施**

判断基线层通过业务行为字典、已知缺陷库和三分法实现。

业务行为字典的结构为：

| 场景 | 环境口径 | 预期行为 | 分类 |
|------|---------|---------|------|
| 维护窗口内断连 | 工作日 5×23 | 连接断开后重连 | 正常 |
| 维护窗口后新单拒绝 | 工作日 5×23 | 返回维护关闭拒绝 | 正常 |
| 非维护时段断连 | 任意 | 非预期断连 | 异常 |

三分法的判定规则：
- 正常：命中业务字典中的正常模式，且跨层证据自洽。
- 异常：命中业务字典中的异常模式，或命中已知缺陷库中的历史反例，或跨层证据不自洽。
- 未知：未命中业务字典中的任何模式，或证据不足以判定，或业务口径未确认。未知类禁止写入正式结论，只能标记为待确认。

跨层证据一致性检查的实施方式：对同一测试事件，检查其在客户端层、服务端层、事件日志层和下游原始消息层的记录是否自洽。当不同层的状态、时间或标识出现矛盾时，触发补充证据采集。

**六、交付与沉淀层的实施**

交付与沉淀层包含三个产出：

覆盖矩阵：对全部设计用例进行状态汇总，状态枚举包括通过、失败、需复测、当前口径部分覆盖、本轮不执行、不单独执行但已覆盖和阻塞。覆盖矩阵禁止省略任何状态的用例。

测试报告：从覆盖矩阵和执行记录提炼，包含已验证通过项、发现的问题或需复测项、部分覆盖和未执行项、环境恢复状态和剩余风险。测试报告禁止新增执行记录中不存在的结论。

测试工程反思候选：包含规则缺口、工作流缺口、技能流程缺口、模板缺口、工具缺口和业务字典缺口。反思候选经人工确认后方可沉淀为长期工程资产。

### 实施例二：流程门禁系统的具体实施

本实施例详细说明流程门禁系统（Test Agent Workflow Runner）的具体实施方式。

**一、系统架构**

流程门禁系统采用命令行接口形式实现，包含以下模块：

1. 工作流配置模块：采用 YAML 格式的声明式配置文件，定义步骤序列和校验规则。
2. 状态管理模块：采用 JSON 格式的本地文件存储运行状态和步骤状态。
3. 门禁校验模块：对 Markdown 格式的步骤产物进行结构和内容校验。
4. 目标产物模式模块：根据目标类型动态确定必经步骤。
5. 中断恢复模块：通过状态文件实现跨会话恢复。

**二、工作流配置**

工作流配置文件定义了测试实施的 8 个步骤：

| 步骤序号 | 步骤标识 | 步骤名称 | 依赖步骤 | 校验类型 |
|---------|---------|---------|---------|---------|
| 1 | input_sources | 输入资料确认 | 无 | 标题校验 |
| 2 | scope | 测试范围与执行口径 | input_sources | 标题校验 |
| 3 | environment_precheck | 环境前置判断 | scope | 标题校验 |
| 4 | tool_selection | 测试工具选型 | environment_precheck | 表格校验 |
| 5 | execution_guide | 测试实施指南 | tool_selection | 标题校验 |
| 6 | execution_record | 测试执行记录 | execution_guide | 标题校验 |
| 7 | report | 最终报告 | execution_record | 标题校验 |
| 8 | reflection | 测试工程反思 | report | 标题校验 |

**三、目标产物模式**

系统支持四种目标产物模式：

| 目标类型 | 终点步骤 | 必经步骤 |
|---------|---------|---------|
| execution_guide | execution_guide | 步骤 1-5 |
| execution_record | execution_record | 步骤 1-6 |
| report | report | 步骤 1-7 |
| full | reflection | 步骤 1-8 |

非必经步骤标记为"当前目标不要求"状态，不阻止目标达成。

**四、门禁校验规则**

标题校验规则的实施：
1. 解析 Markdown 文档，提取所有标题（一级至六级）。
2. 对配置中要求的每个标题，检查文档中是否存在精确匹配的标题文本。
3. 对每个匹配到的标题，检查其下方到下一个标题之间是否存在非空正文。
4. 缺失标题时输出"缺失标题：<标题名>"错误。
5. 标题下无内容时输出"标题无内容：<标题名>"错误。

表格校验规则的实施：
1. 解析 Markdown 文档，定位表格结构。
2. 提取表头行，检查是否包含所有必需列。
3. 对数据行进行有效性检查：判断关键列的值是否为占位符。
4. 占位符判定规则：空值、尖括号包围的文本（如 `<待填写>`）、不区分大小写的"TBD"、"待补充"。
5. 当所有数据行的关键列均为占位符时，判定为校验失败。

依赖校验规则的实施：
1. 读取当前步骤配置中的依赖步骤列表。
2. 检查每个依赖步骤的状态是否为"已完成"。
3. 任一依赖步骤未完成时，输出"依赖未满足：<步骤标识>"错误。

**五、状态管理**

运行状态文件（run.json）记录：
- 运行标识：包含时间戳和微秒的唯一标识
- 工作流类型
- 任务名称
- 目标产物模式
- 运行状态：运行中、已阻塞、已完成、已失败
- 当前步骤
- 阻塞原因

步骤状态文件（checklist.json）记录每个步骤的：
- 步骤标识和名称
- 是否为必经步骤
- 当前状态：等待执行、已阻塞、已完成、当前目标不要求
- 产物输出路径
- 依赖步骤列表
- 完成时间
- 校验错误列表

**六、中断恢复机制**

中断恢复的实施步骤：
1. AI Agent 执行中断后，通过状态查询命令读取 run.json 和 checklist.json。
2. 根据步骤状态确定当前应执行的步骤。
3. 通过下一步查询命令获取当前步骤的产物路径和校验要求。
4. 若当前步骤的产物文件已存在但步骤未完成，在原文件基础上补全内容。
5. 补全后通过完成命令执行校验。

中断恢复的关键约束：
- 禁止依赖对话上下文推测当前进度。
- 若步骤状态为已阻塞，必须先处理校验错误。
- 恢复后仍必须通过门禁校验，不得直接标记完成。

**七、幂等性保证**

完成命令具有幂等性：
- 对已完成步骤重复执行完成命令时，返回已完成提示。
- 不修改已记录的完成时间。
- 不重复推进当前步骤指针。
- 不影响后续步骤的状态。

### 实施例三：应用实施例

本实施例以一个真实的功能测试任务说明本发明方法和系统的应用过程。

**一、测试任务背景**

测试任务为验证交易系统客户端组件新增的虚拟时钟漂移能力。该能力通过环境变量注入时间偏移量，使客户端在判断订单过期时使用虚拟时间而非真实时间。

核心逻辑为：
- 虚拟当前时间 = 真实当前时间 + 时间漂移量
- 当虚拟当前时间 >= 订单过期时间时，判定订单过期

该功能只在特定构建版本中生效，普通版本不受影响。

**二、任务路由层的应用**

AI Agent 接收到"验证虚拟时钟漂移功能"的请求后，与工作流目录匹配，命中"功能测试实施"工作流。系统确定主流程为测试实施工作流，必读资产包括测试实施技能文档和二进制切换技能文档。

**三、需求与用例层的应用**

Agent 列出信息源：需求通知、代码变更和用户澄清。通过甄别发现：
- 需求通知描述了虚拟时钟的计算公式和过期判断逻辑。
- 代码变更确认了环境变量名称和 fallback 行为。
- 用户澄清确认了测试环境和可用的构建版本。

生成覆盖清单后，区分了可执行范围和不可执行范围：
- 可执行：正漂移过期、零漂移不影响、非法环境变量 fallback、未设置环境变量 fallback、算法单入口。
- 不可执行：订单过期时间为零的场景（当前环境无法构造该输入）。

**四、测试实施设计层的应用**

环境前置确认发现：
- 测试依赖特定的 fake-clock 构建版本二进制。
- 环境变量必须通过守护进程配置注入，而非 SSH 会话设置。
- 修改配置后必须重启守护进程，并验证进程标识变化。

工具选型结果：
- 普通单场景：选用定向自动化工具，新增专用测试类型，支持精确输入和北向断言。
- 算法单场景：选用自动化工具配合行情模拟触发，需要额外的 mock 行情服务。
- 背景流量观察：不采用，因为订单不可控、证据不可归因。

**五、流程门禁系统的应用**

AI Agent 启动流程门禁系统，创建运行实例，目标产物为完整闭环。

系统按步骤推进：
1. 输入资料确认：Agent 列出需求文档、代码变更和环境说明，通过标题校验。
2. 测试范围确认：Agent 明确测试范围和不测范围，通过标题校验。
3. 环境前置判断：Agent 确认目标二进制、环境变量注入方式和重启方式，通过标题校验。
4. 工具选型：Agent 填写工具选型表，系统检查表格列完整性和有效数据，通过表格校验。
5. 实施指南：Agent 生成逐用例执行步骤，通过标题校验。

在步骤 4 中，Agent 首次提交的工具选型表关键列为占位符，系统返回"无有效数据行"错误并标记为已阻塞。Agent 补充具体工具选择和理由后，重新提交通过校验。

**六、执行证据层的应用**

测试执行过程中，Agent 为每个用例记录：
- 订单标识：用于精确匹配后续证据。
- 北向协议回执：确认客户端收到的响应。
- 事件日志：确认服务端内部状态。
- 下游消息层：确认是否向下游发送（过期场景应无下游发送）。

**七、判断基线层的应用**

测试产出中出现一个非预期现象：算法单场景下，订单未直接被拒绝，而是先确认后再形成过期终态。

Agent 查询业务字典未命中该模式，标记为"未知"。经人工确认后，该行为属于算法单的正常路径（先确认再触发过期），更新业务字典并将该用例标记为通过。

**八、交付与沉淀层的应用**

最终覆盖矩阵显示：11 个用例通过，1 个部分覆盖，1 个需复测，4 个本轮不执行，1 个已由其他用例覆盖。

测试工程反思候选包括：
- 规则缺口：测试前必须确认二进制版本和环境变量注入方式。
- 技能缺口：需固化二进制切换和环境变量配置流程。
- 工具缺口：需新增专用自动化测试类型。
- 字典缺口：需补充算法单过期终态的正常模式。

上述反思候选经人工确认后，分别沉淀为全局规则、技能文档、自动化工具和业务字典的更新。

### 实施例四：关键算法的伪代码描述

本实施例以伪代码形式给出流程门禁系统中关键算法的实现逻辑。本发明不限于特定编程语言或运行平台。

**一、标题存在性与内容非空校验算法**

```
算法：CHECK_REQUIRED_HEADINGS
输入：文档内容 content，必需标题列表 required_headings
输出：错误列表 errors

步骤：
1. 将 content 按行分割为 lines 数组
2. 初始化空集合 heading_map  // 存储 {标题文本 → 是否有非空正文}

3. 遍历 lines 中每一行 line：
   3.1 若 line 匹配标题模式（以 1~6 个 # 开头，后跟空格和文本）：
       提取标题文本 heading_text
       记录 (行号, heading_text) 到 headings 列表

4. 对 headings 列表中每个标题 (line_idx, heading_text)：
   4.1 确定正文范围：从 line_idx+1 到下一个标题行之前（或文件末尾）
   4.2 检查正文范围内是否存在至少一行非空白内容
   4.3 将结果记入 heading_map[heading_text]
       若同名标题出现多次，取逻辑或（有一处有内容即视为通过）

5. 初始化空列表 errors
6. 对 required_headings 中每个标题 heading：
   6.1 若 heading 不在 heading_map 中：
       追加错误 "缺失标题: heading"
   6.2 否则若 heading_map[heading] 为假：
       追加错误 "标题无内容: heading"

7. 返回 errors
```

该算法的核心逻辑为：首先解析文档中所有标题的位置和文本；然后对每个标题确定其正文范围（当前标题到下一个标题之间）；最后检查正文范围内是否存在非空行。

**二、占位符判定算法**

```
算法：IS_PLACEHOLDER
输入：单元格文本 value
输出：布尔值（真表示为占位符）

步骤：
1. 去除 value 首尾空白，得到 stripped
2. 若 stripped 为空字符串，返回 真
3. 若 stripped 匹配模式 "<任意内容>"（尖括号包裹），返回 真
4. 若 stripped 转大写后等于 "TBD"，返回 真
5. 若 stripped 等于 "待补充"，返回 真
6. 返回 假
```

该算法定义了四类占位符模式：空值、尖括号模板文本、英文待定标记和中文待补充标记。当表格所有数据行的关键列均被判定为占位符时，门禁校验判定为失败，阻止步骤推进。

**三、步骤完成与门禁校验的完整流程**

```
算法：COMPLETE_STEP
输入：运行目录 run_dir，步骤标识 step_id，工作流配置 workflow_config
输出：执行结果（成功 / 阻塞 / 错误）

步骤：
1. 从 run_dir 加载运行状态 run_state 和步骤状态列表 checklist
2. 在 checklist 中查找 step_id 对应的步骤状态 step_state
   若未找到，返回 错误

3. 【幂等检查】
   若 step_state.status 已为 "已完成"，直接返回 成功
   （不修改完成时间，不推进当前步骤指针）

4. 【依赖检查】
   对 step_state.depends_on 中每个依赖步骤 dep_id：
     在 checklist 中查找 dep_id 的状态
     若该依赖步骤状态不为 "已完成"，返回 错误（依赖未满足）

5. 【产物存在性检查】
   从 workflow_config 获取 step_id 的产物输出路径
   拼接完整路径 artifact_path = run_dir / 输出路径
   若 artifact_path 对应的文件不存在：
     设置 step_state.status = "已阻塞"
     记录校验错误 "产物文件不存在"
     持久化状态到 run_dir
     返回 阻塞

6. 【内容校验】
   读取 artifact_path 文件内容
   根据步骤配置的校验规则类型执行校验：
     若配置了必需标题列表：执行 CHECK_REQUIRED_HEADINGS
     若配置了必需表格列列表：执行表格列校验 + 有效数据校验

7. 【状态更新】
   若校验通过：
     设置 step_state.status = "已完成"
     记录完成时间
     清空校验错误列表
     推进 run_state.current_step 到下一个等待执行的步骤
     持久化状态到 run_dir
     返回 成功
   若校验失败：
     设置 step_state.status = "已阻塞"
     记录所有校验错误
     持久化状态到 run_dir
     返回 阻塞
```

该流程的关键设计包括：
1. 幂等性保证：对已完成步骤重复执行完成命令时直接返回成功，不修改状态。
2. 严格的依赖链：任一前置步骤未完成时，拒绝执行当前步骤的校验。
3. 分层校验：先检查产物文件是否存在，再检查内容是否满足门禁规则。
4. 状态持久化：无论校验通过或失败，都将最新状态写入本地文件，支持后续中断恢复。

**四、工作流配置的声明式定义**

工作流配置采用声明式结构，以下为一种具体的配置格式示例：

```
工作流配置结构：
  工作流标识: test_execution
  工作流名称: 测试实施工作流

  目标产物映射:
    execution_guide → 终点步骤: execution_guide
    execution_record → 终点步骤: execution_record
    report → 终点步骤: report
    full → 终点步骤: reflection

  步骤列表:
    步骤1:
      标识: input_sources
      名称: 输入资料确认
      产物路径: artifacts/01_input_sources.md
      依赖: 无
      校验规则: 必需标题 [输入资料, 已确认项, 待确认项]

    步骤4:
      标识: tool_selection
      名称: 测试工具选型
      产物路径: artifacts/04_tool_selection.md
      依赖: [environment_precheck]
      校验规则: 必需表格列 [Case/场景, 现有工具是否覆盖, 选用工具,
               是否需要新增, 断言方式, 选择理由, 缺口/风险]
      附加校验: 至少1行非占位符有效数据
```

该配置格式的设计要点：
1. 步骤序列通过列表顺序隐含定义，无需显式编号。
2. 依赖关系通过依赖字段显式声明，支持非线性依赖图。
3. 校验规则通过必需标题列表或必需表格列列表二选一声明，不同步骤可使用不同校验类型。
4. 目标产物模式通过目标映射定义，将目标类型映射到终点步骤标识。
