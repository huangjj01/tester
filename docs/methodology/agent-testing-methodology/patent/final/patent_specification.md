# 说明书

## 发明名称

用于 AI Agent 测试实施流程的配置化门禁控制方法、系统、介质及程序产品

## 技术领域

本发明涉及人工智能辅助软件测试技术领域，具体涉及一种用于约束 AI Agent 测试实施行为的配置化流程门禁控制方法及系统。

## 背景技术

随着大语言模型技术的发展，AI Agent 已经能够参与软件测试中的多类任务，包括阅读需求文档、生成测试用例、执行命令、检索日志和总结测试结果。然而，在真实功能测试实施过程中，AI Agent 存在以下技术问题：

第一，流程跳步问题。AI Agent 在执行测试实施任务时，可能跳过环境前置确认、测试工具选型、执行记录或测试工程反思等关键环节，直接进入后续步骤。现有的文档规则约束（如规则文件、技能文档）仅依赖 Agent 自觉遵守，缺少可执行的阻止机制。

第二，上下文丢失问题。AI Agent 的对话上下文存在长度限制和压缩机制，当测试实施任务跨越多个会话或被中断时，Agent 无法可靠地恢复到中断前的执行进度，可能重复已完成的步骤或遗漏未完成的步骤。

第三，产物质量不可控问题。AI Agent 生成的测试实施产物（如环境前置文档、工具选型表、执行记录）可能存在关键内容缺失，例如标题存在但下方无实质内容，或表格存在但全部为占位符数据。现有技术缺少对产物内容进行结构化校验的机制。

第四，流程灵活性不足问题。不同测试任务需要完成的步骤范围不同，例如只需要生成测试实施指南时不需要执行记录和报告步骤。现有工作流系统通常要求执行全部步骤，缺少根据目标产物类型动态裁剪必经步骤的能力。

现有技术中，通用工作流管理系统和质量门机制已被广泛应用于 CI/CD 流水线和软件发布流程，但这些系统面向的是代码构建和部署场景，其校验规则针对编译结果、测试覆盖率和安全扫描等指标，不适用于对 AI Agent 生成的结构化文档产物进行内容校验。

## 发明内容

### 本发明要解决的技术问题

本发明要解决的技术问题是：如何通过配置化的流程门禁机制，对 AI Agent 在测试实施过程中生成的步骤产物进行结构校验和内容校验，在校验未通过时阻止流程推进，并通过状态持久化支持跨会话的中断恢复。

### 技术方案

为解决上述技术问题，本发明提供一种用于 AI Agent 测试实施流程的配置化门禁控制方法，由计算设备执行，包括以下步骤：

步骤 S1、配置加载步骤：读取声明式工作流配置数据，所述工作流配置数据定义了有序的步骤序列、每个步骤的产物输出路径、步骤间的依赖关系和每个步骤的门禁校验规则。

步骤 S2、实例创建步骤：根据接收到的任务标识和目标产物类型，创建工作流运行实例，生成包含时间戳的唯一运行标识，在本地存储中建立运行状态数据和步骤状态数据，并根据所述目标产物类型确定必经步骤集合，将非必经步骤标记为当前目标不要求状态。

步骤 S3、步骤推进步骤：根据所述步骤间的依赖关系和各步骤的当前状态，确定当前应执行的步骤，并向 AI Agent 输出当前步骤的产物输出路径和门禁校验要求。

步骤 S4、门禁校验步骤：当 AI Agent 完成当前步骤的产物生成后，对所述产物依次执行依赖校验、产物存在性校验和产物内容校验。

步骤 S5、状态更新步骤：门禁校验通过时将步骤状态更新为已完成并推进当前步骤指针；门禁校验未通过时将步骤状态更新为已阻塞并记录校验错误信息，阻止推进。

步骤 S6、状态持久化步骤：在每次状态变更后将状态数据持久化至本地存储，支持 AI Agent 中断后通过读取持久化数据恢复执行进度。

本发明还提供一种用于 AI Agent 测试实施流程的配置化门禁控制系统，包括工作流配置模块、状态管理模块、目标产物模式模块、门禁校验模块和中断恢复模块。

### 技术效果

本发明的技术效果包括：

1. 通过门禁校验机制，在 AI Agent 跳过关键环节时实时阻止流程推进，将文档约束升级为可执行的校验机制。

2. 通过状态持久化和中断恢复机制，使测试实施过程不依赖 AI Agent 的对话上下文，支持跨会话、跨时间段的连续执行。

3. 通过结构校验和有效数据校验，确保 AI Agent 生成的产物具有实质内容，而非空标题或占位符数据。

4. 通过目标产物模式，支持按需执行部分流程，避免简单任务承担完整闭环的成本。

5. 通过配置合法性校验，在工作流启动前发现配置错误（如重复步骤标识、不存在的依赖），避免运行时异常。

6. 通过幂等性设计，确保重复操作不会破坏已有状态，提高系统鲁棒性。

### 实施例一：配置化门禁控制方法的具体实施

本实施例详细说明配置化门禁控制方法各步骤的具体实施方式。

**一、配置加载步骤**

工作流配置数据采用声明式结构，定义以下内容：

1. 步骤序列：有序的步骤列表，每个步骤包含步骤标识、步骤名称和产物输出路径。
2. 依赖关系：每个步骤可声明零个或多个前置依赖步骤标识。
3. 门禁校验规则：每个步骤配置一种校验规则，为必需标题列表或必需表格列列表之一。
4. 目标产物映射：将目标产物类型映射到终点步骤标识。

配置加载时还执行合法性校验：
- 检查所有步骤标识是否唯一，存在重复时拒绝加载。
- 检查每个步骤声明的依赖步骤标识是否在步骤序列中存在。
- 检查目标产物映射中的终点步骤标识是否在步骤序列中存在。

在一种实施方式中，配置数据采用 YAML 格式存储，示例结构如下：

```
工作流配置：
  标识: test_execution
  目标映射:
    execution_guide → execution_guide
    full → reflection
  步骤列表:
    - 标识: input_sources, 产物: artifacts/01_input_sources.md, 校验: 标题校验
    - 标识: scope, 依赖: [input_sources], 产物: artifacts/02_scope.md, 校验: 标题校验
    - 标识: tool_selection, 依赖: [environment_precheck], 产物: artifacts/04_tool_selection.md, 校验: 表格校验
```

**二、实例创建步骤**

接收任务标识和目标产物类型后，系统执行以下操作：

1. 生成唯一运行标识：格式为"时间戳_微秒_任务标识"，确保同一秒内多次创建不冲突。
2. 创建运行目录，建立产物子目录。
3. 初始化运行状态数据：记录运行标识、工作流类型、任务名称、目标产物类型、当前步骤（首个步骤）和运行状态（运行中）。
4. 初始化步骤状态数据：对每个步骤，根据目标产物类型判断是否为必经步骤，必经步骤初始状态为等待执行，非必经步骤初始状态为当前目标不要求。
5. 将运行状态数据和步骤状态数据持久化至本地存储。

在一种实施方式中，运行状态数据和步骤状态数据分别存储为 JSON 格式文件。

**三、步骤推进步骤**

系统根据以下逻辑确定当前应执行的步骤：

1. 从步骤序列中，按顺序查找第一个状态为等待执行的步骤。
2. 检查该步骤的所有依赖步骤是否均为已完成状态。
3. 若依赖满足，将该步骤确定为当前步骤。
4. 向 AI Agent 输出当前步骤的产物输出路径和门禁校验要求（必需标题列表或必需表格列列表）。

**四、门禁校验步骤**

门禁校验按以下顺序依次执行：

第一层：依赖校验
- 读取当前步骤配置中的依赖步骤列表。
- 检查每个依赖步骤的状态是否为已完成。
- 任一依赖步骤未完成时，返回"依赖未满足"错误，不执行后续校验。

第二层：产物存在性校验
- 拼接当前步骤的产物输出路径。
- 检查该路径对应的文件是否存在。
- 文件不存在时，返回"产物文件不存在"错误。

第三层：产物内容校验
- 根据步骤配置的校验规则类型执行对应校验。

标题校验的具体实施：
1. 解析产物文件，通过正则匹配提取所有一级至六级标题的位置和文本。
2. 对配置中要求的每个必需标题，检查是否存在精确匹配的标题文本。
3. 对每个匹配到的标题，确定其正文范围（当前标题到下一个标题之间），检查是否存在至少一行非空白内容。
4. 缺失标题时生成"缺失标题"错误，标题下无内容时生成"标题无内容"错误。

表格有效数据校验的具体实施：
1. 解析产物文件中的表格结构，提取表头行和数据行。
2. 检查表头是否包含所有必需列。
3. 对每个数据行的关键列值执行占位符判定。
4. 占位符判定规则：空值为占位符；尖括号包围的文本为占位符；不区分大小写的"TBD"为占位符；"待补充"为占位符。
5. 当所有数据行的关键列均为占位符时，生成"无有效数据行"错误。

幂等性保证：
- 对已处于已完成状态的步骤执行门禁校验时，直接返回成功，不修改完成时间，不推进步骤指针。

**五、状态更新步骤**

校验通过时：
1. 将当前步骤状态更新为已完成。
2. 记录完成时间。
3. 清空校验错误列表。
4. 从步骤序列中查找下一个等待执行的步骤，更新当前步骤指针。
5. 若所有必经步骤均已完成，将运行状态更新为已完成。

校验未通过时：
1. 将当前步骤状态更新为已阻塞。
2. 将所有校验错误信息写入步骤状态数据的校验错误列表。
3. 不推进当前步骤指针。

**六、状态持久化与中断恢复**

状态持久化：每次状态变更后，将运行状态数据和步骤状态数据写入本地存储文件。

中断恢复：
1. AI Agent 中断后，通过状态查询接口读取持久化的状态文件。
2. 获取当前运行状态和各步骤状态。
3. 通过下一步查询接口获取当前步骤的产物路径和校验要求。
4. 若产物文件已存在但步骤未完成，在已有内容基础上补全。
5. 补全后仍须通过门禁校验。

关键约束：禁止依赖 AI Agent 的对话上下文推测当前进度，必须以持久化状态文件为唯一事实来源。

### 实施例二：配置化门禁控制系统的具体实施

本实施例详细说明系统各模块的具体实施方式。

**一、系统架构**

系统采用分层架构：
- 交互接口层：提供创建、状态查询、下一步查询、完成、全局校验和合并输出六种操作。
- 核心逻辑层：包含工作流配置模块、状态管理模块、目标产物模式模块、门禁校验模块和中断恢复模块。
- 存储层：包含配置文件、状态文件和产物文件三类存储。

在一种实施方式中，交互接口层采用命令行接口实现，核心逻辑层采用单进程应用实现，存储层采用本地文件系统实现。

**二、工作流配置模块**

职责：
- 从配置文件加载工作流定义。
- 解析步骤序列、依赖关系、校验规则和目标映射。
- 执行配置合法性校验。
- 提供步骤查询接口（按标识查找步骤配置、获取下一步骤）。

配置合法性校验包括：
- 步骤标识唯一性：遍历步骤序列，检查是否存在重复标识。
- 依赖存在性：对每个步骤的依赖列表，检查依赖标识是否在步骤序列中存在。
- 目标终点存在性：对目标映射中的每个终点步骤标识，检查是否在步骤序列中存在。

**三、状态管理模块**

职责：
- 创建运行实例，生成唯一标识。
- 维护运行状态数据和步骤状态数据。
- 提供状态读写接口。
- 将状态持久化至本地存储。

运行状态数据结构：
- 运行标识（字符串，包含时间戳和微秒）
- 工作流类型标识
- 任务名称
- 目标产物类型
- 运行状态（运行中/已阻塞/已完成/已失败）
- 当前步骤标识
- 阻塞原因

步骤状态数据结构（每个步骤一条）：
- 步骤标识和名称
- 是否为必经步骤
- 当前状态（等待执行/已阻塞/已完成/当前目标不要求）
- 产物输出路径
- 依赖步骤列表
- 完成时间
- 校验错误列表

**四、目标产物模式模块**

职责：
- 接收目标产物类型。
- 从配置中查找对应的终点步骤。
- 将首个步骤到终点步骤之间的步骤标记为必经。
- 将终点步骤之后的步骤标记为当前目标不要求。

支持的目标产物类型示例：
- execution_guide：必经步骤为输入确认到实施指南（步骤 1-5）。
- execution_record：必经步骤为输入确认到执行记录（步骤 1-6）。
- report：必经步骤为输入确认到最终报告（步骤 1-7）。
- full：必经步骤为全部步骤（步骤 1-8）。

**五、门禁校验模块**

职责：
- 接收步骤完成请求。
- 依次执行依赖校验、存在性校验和内容校验。
- 返回校验结果（通过/失败及错误列表）。
- 通知状态管理模块更新状态。

校验流程的退出码约定：
- 0：校验通过，步骤已完成。
- 1：错误（步骤不存在、依赖未满足等）。
- 2：校验失败，步骤已阻塞。

**六、中断恢复模块**

职责：
- 从本地存储读取运行状态和步骤状态。
- 向 AI Agent 提供当前进度信息。
- 提供下一步骤的产物路径和校验要求。

恢复约束：
- 不依赖对话上下文。
- 已阻塞步骤必须先处理校验错误。
- 已有产物文件在补全后仍须通过校验。

### 实施例三：关键算法的伪代码描述

**一、标题校验算法**

```
算法：CHECK_REQUIRED_HEADINGS
输入：文档内容 content，必需标题列表 required_headings
输出：错误列表 errors

1. 将 content 按行分割
2. 遍历每行，匹配标题模式（1~6 个标记符号后跟文本），提取标题位置和文本
3. 对每个标题，确定正文范围（当前标题到下一标题之间）
4. 检查正文范围内是否存在非空白行
5. 对 required_headings 中每个标题：
   - 若不存在：追加"缺失标题"错误
   - 若存在但无非空白正文：追加"标题无内容"错误
6. 返回错误列表
```

**二、占位符判定算法**

```
算法：IS_PLACEHOLDER
输入：单元格文本 value
输出：布尔值

1. 去除首尾空白得到 stripped
2. 若 stripped 为空，返回真
3. 若 stripped 匹配"<任意内容>"模式，返回真
4. 若 stripped 转大写等于"TBD"，返回真
5. 若 stripped 等于"待补充"，返回真
6. 返回假
```

**三、步骤完成流程**

```
算法：COMPLETE_STEP
输入：运行目录，步骤标识，工作流配置
输出：成功/阻塞/错误

1. 加载运行状态和步骤状态
2. 查找目标步骤，未找到则返回错误
3. 幂等检查：已完成则直接返回成功
4. 依赖检查：任一依赖未完成则返回错误
5. 产物存在性检查：不存在则标记阻塞并返回
6. 内容校验：执行标题校验或表格校验
7. 校验通过：标记完成，推进步骤指针，持久化
8. 校验失败：标记阻塞，记录错误，持久化
```

### 实施例四：测试实施场景的应用

本实施例说明本发明在真实测试实施场景中的应用。

**一、场景描述**

AI Agent 接收到功能测试实施任务，需要产出测试实施指南。系统启动门禁控制，目标产物类型为 execution_guide，必经步骤为输入资料确认、测试范围确认、环境前置判断、测试工具选型和测试实施指南共 5 步。

**二、门禁阻止跳步的效果**

Agent 在完成输入资料确认和测试范围确认后，尝试直接生成测试实施指南（跳过环境前置和工具选型）。系统执行依赖校验，发现实施指南步骤依赖工具选型步骤，而工具选型步骤尚未完成，返回"依赖未满足"错误，阻止推进。Agent 被迫回到环境前置判断步骤。

**三、有效数据校验的效果**

Agent 完成环境前置判断后进入工具选型步骤，生成了包含正确表头的工具选型表，但所有数据行的关键列均为"<待填写>"占位符。系统执行表格有效数据校验，判定所有行为占位符，返回"无有效数据行"错误，将步骤标记为已阻塞。Agent 补充具体工具选择和理由后重新提交，通过校验。

**四、中断恢复的效果**

Agent 在完成工具选型后，对话上下文被压缩，Agent 丢失了当前进度信息。Agent 通过状态查询接口读取持久化状态，确认当前步骤为测试实施指南，通过下一步查询接口获取产物路径和校验要求，从中断点继续执行。

**五、目标产物模式的效果**

由于目标产物类型为 execution_guide，系统将执行记录、最终报告和测试工程反思三个步骤标记为当前目标不要求。当实施指南步骤完成后，系统判定目标已达成，输出完成信号。后续若用户要求继续生成报告，可创建新的运行实例，目标产物类型设为 report。

### 实施例五：分层约束模型与门禁系统的协同

本实施例说明本发明的分层约束模型如何与门禁控制系统协同工作，为门禁系统提供测试工程层面的约束依据。

**一、分层约束模型概述**

如图 7 所示，本发明提出六层约束模型，将 AI Agent 在测试任务中的不确定性行为分解为六类可控的工程约束。六层自上而下分别为：

第一层，任务路由层：控制入口不确定性。将用户测试请求匹配到预定义的工作流类型，确定主流程、子流程和必读资产。当请求未命中任何工作流时，阻止 Agent 进入后续步骤。该层解决的问题是 Agent 拥有多个技能文档却不知道当前应先使用哪一个。

第二层，需求与用例层：控制需求基线和覆盖不确定性。对多源需求信息进行甄别对齐，区分理论可覆盖范围与当前可执行范围，生成覆盖清单和测试用例。该层解决的问题是 Agent 基于单一信息源生成用例导致预期错误或覆盖遗漏。

第三层，测试实施设计层：控制环境和工具不确定性。在执行用例前强制完成环境前置确认、测试工具选型和逐用例执行方案设计。该层解决的问题是 Agent 把用例当成可以立即执行的命令，跳过环境和工具确认。

第四层，执行证据层：控制事实和归因不确定性。按预定义的证据模板采集并持久化执行事实，包括标识、日志、报告、运行态和外部层证据。该层解决的问题是测试结果停留在对话上下文中，无法复核和交接。

第五层，判断基线层：控制结论定性不确定性。基于业务行为字典和已知缺陷库，将测试产出按三分法分类为正常、异常和未知。该层解决的问题是 Agent 将未经证实的推断写成正式结论。

第六层，交付与沉淀层：控制报告和经验沉淀不确定性。从执行记录生成测试报告，并将流程缺口转化为可复用工程资产候选。该层解决的问题是测试经验散落在对话记录中无法复用。

六层之间存在自上而下的约束传递关系：上层约束为下层执行提供前提和边界。同时存在自下而上的反馈修正关系：下层执行中发现的事实可以反馈修正上层约束，例如执行中发现用例预期错误时，反馈到需求与用例层修正覆盖清单。

**二、门禁系统与分层模型的对应关系**

门禁控制系统通过工作流配置数据，将分层约束模型中第三层至第六层的关键步骤固化为可校验的步骤序列。具体对应关系为：

| 分层模型层次 | 门禁系统步骤 | 门禁校验规则 |
|------------|------------|------------|
| 第三层：测试实施设计 | 环境前置判断 | 标题校验（6 个必需标题） |
| 第三层：测试实施设计 | 测试工具选型 | 表格校验（7 列 + 有效数据） |
| 第三层：测试实施设计 | 测试实施指南 | 标题校验（5 个必需标题） |
| 第四层：执行证据 | 测试执行记录 | 标题校验（6 个必需标题） |
| 第五层+第六层：判断+交付 | 最终报告 | 标题校验（5 个必需标题） |
| 第六层：交付与沉淀 | 测试工程反思 | 标题校验（4 个必需标题） |

第一层（任务路由）和第二层（需求与用例）在当前实施中通过输入资料确认和测试范围确认两个步骤体现，门禁校验确保 Agent 在进入实施设计前已明确输入来源和测试范围。

**三、工程资产协同体系**

如图 8 所示，分层约束模型依赖六类工程资产协同工作：

1. 规则（Rules）：定义红线约束和强制入口，规定哪些任务必须进入正式流程。
2. 工作流（Workflows）：定义任务类型到主流程的路由映射，声明子流程和必读资产。
3. 技能（Skills）：承载具体可复用操作步骤和场景化方法。
4. 模板（Templates）：固化交付物的结构要求。
5. 业务字典（Dictionaries）：提供正常、异常和未知行为的判定基线。
6. 执行记录（Records）：保存真实执行事实和证据。

这六类资产的维护原则为：规则放红线，工作流放路由，技能放步骤，字典放判断基线，模板放结构，记录放事实。

门禁控制系统与工程资产的关系为：门禁系统的工作流配置数据引用模板中定义的结构要求（必需标题、必需表格列），将其转化为可执行的校验规则。执行记录中暴露的缺口经人工确认后，可回补到规则、工作流、技能、模板或字典中，形成持续改进的闭环。

**四、协同效果**

分层约束模型为门禁系统提供了"应该约束什么"的方法论依据，门禁系统为分层约束模型提供了"如何强制执行"的技术保障。两者协同的效果是：

- 方法论确保约束的完整性：六层覆盖了从入口到沉淀的全部断裂点。
- 门禁系统确保约束的强制性：校验未通过时阻止推进，而非依赖 Agent 自觉遵守。
- 状态持久化确保约束的连续性：跨会话中断后仍能从断点恢复，不丢失已完成的约束。
- 反思沉淀确保约束的演进性：每次测试暴露的缺口转化为新的约束，系统能力持续增强。
