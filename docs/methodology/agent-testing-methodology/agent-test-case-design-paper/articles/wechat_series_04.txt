系列：《让 Agent 设计出高质量测试用例》· 第 4 篇

从全量生成到精准增量

---

前三篇我们讲了 Agent 为什么老翻车，也讲了怎么靠约束把它拉回正轨。最后这一篇只聊一个现实问题：为什么同一个团队，上个月刚总结完经验，这个月让 Agent 重新设计用例，它还是像第一次见这个需求一样？

很多人会把这件事归因于“Agent 没记忆”。我现在更倾向于另一个说法：不是它没记忆，是团队没有把经验整理成它能复用的东西。

**先看一个很常见的场景**

一个新需求过来，Agent 很容易这样干：把相关功能从头到尾重写一遍。基础下单写几条，改单写几条，撤单写几条，恢复、异常、边界条件再补几条。最后看起来挺努力，给了你 25 条 case。

问题是，里面有 17 条其实已经被存量自动化覆盖了。真正跟这次变更直接相关、必须新增设计的，可能只有 8 条。这 8 条如果单独拎出来，审核很快，执行也很聚焦。可一旦被淹没在 25 条里，团队的注意力就会被稀释。你要花时间做两件本来不该做的事：先分辨哪些是旧的，再判断哪些是真的新的。

这就是“全量生成”的问题。它不一定错，但很浪费。所谓“精准增量”，说白了就是三步：先知道已经有什么，再知道这次改了什么，最后只设计还缺的那部分。听起来简单，难点在第一步。很多团队没有一份 Agent 能读懂的“已有覆盖说明书”。于是它每次都像在一片空地上开工。

**怎么把 25 条压到 8 条**

我们后来做了一件很朴素的事：先不给 Agent 写新 case，而是先让它回答一个问题：“这次需求，哪些场景已经被现有回归覆盖了？”

它要先翻存量自动化索引，再对照这次需求影响的能力点、动作链和状态节点，把已有覆盖标出来。比如一次订单能力变更，初看好像会影响下单、改单、撤单、恢复全链路，但实际对照后发现，基础下单成功、基础改单成功、基础撤单成功、恢复后继续改单，这些都已有覆盖。

这次真正新增的，只有新增语义下的触发条件、触发后和原有生命周期节点的衔接、一个历史缺陷附近的异常分支，以及一条过去没覆盖到的边界时间窗口。这样一过滤，25 条就变成 8 条，而且这 8 条每一条都说得清自己为什么存在。

我很喜欢这种状态。因为这时候用例不再像“把需求复述一遍”，而像“把本次风险点钉出来”。

**要让 Agent 做到精准增量，得先沉淀什么**

这里说的“沉淀”，不是建一个很大的知识库，更不是把每次聊天记录全塞进去。真有用的沉淀，其实就几类。

第一类，存量自动化索引。已有 case 覆盖了哪些场景，最好能按功能、动作链、状态节点去查。没有这份索引，Agent 根本分不清“旧覆盖”和“新增覆盖”。

第二类，生命周期矩阵。一个功能从进入系统到终态，通常会经过哪些关键节点，每个节点有哪些继续动作、异常分支和可观察证据。这个东西的作用，不是让 Agent 背下来，而是让它别凭感觉想场景。

第三类，已知能力基线。哪些订单类型、哪些时效类型、哪些操作能力是系统早就支持的，哪些是这次才新增的。没有这个基线，Agent 很容易把老能力重新写成新需求。

第四类，断言模板。很多问题不是出在“有没有想到 case”，而是出在“断言写弱了”。把常见测试意图到断言的映射沉淀下来，能明显减少这种退化。

第五类，历史缺陷模式。这个特别值钱。因为很多需求最该补的，不是主路径，而是你们以前摔过跤的地方。比如“改单拒绝后原状态被改坏”这种坑，只要沉淀过一次，后面同类需求就不该再漏。

如果只能先做一件事，我建议从第一类开始：先建存量自动化索引。它对“从全量生成到精准增量”的帮助最大，也最直接。

**沉淀不是越多越好，关键是别把错的东西记进去**

这里我们踩过一个很典型的坑。

有一次，Agent 在某次测试里得出了一个临时结论。这个结论在当时那个环境下是对的，但它其实依赖一组特殊配置。后来它把这个结论写成了通用规则。再后来，另一个类似需求来了，它按这条“规则”去设计用例，结果整批预期都偏了。

问题不在 Agent 会不会总结，问题在于它太愿意总结了。所以沉淀这件事，一定要有人把关。我们后来把规则压得很简单：Agent 可以提出“沉淀候选项”，但只有经过人确认，这个候选项才算正式知识。

确认时主要看三件事：这是不是通用规律，而不是一次性的现场结论；这条知识应该落到哪一层；它有没有适用范围。如果只适用于特定环境，就必须写清楚。这一步很土，但很有用。它能防止知识库越积越多，最后全是半真半假的结论。

**人和 Agent 到底怎么分工**

讲到这里，分工其实就比较清楚了。人更适合做判断：这次需求真正危险的地方在哪，哪些历史问题值得继续盯，哪些业务口径还没定，哪些经验可以沉淀成长期资产。

Agent 更适合做遍历：快速翻存量 case，把新需求和老覆盖逐项对照，在覆盖框架里稳定地过组合、过节点、过动作链，把“这里已覆盖”“这里要新增”“这里本轮做不了”整理清楚。

我现在越来越不相信一种说法：要么让 Agent 全做完，人只最后看一眼；要么干脆别让它碰核心工作。这两种都太极端了。更现实的方式是：让 Agent 负责重活和脏活，让人类负责最后那些真正需要判断力的地方。这样效率高，质量也稳。

**这套方法也有边界**

还是得说句老实话，它不是没有成本。如果是一个特别简单、输入输出都很清楚的小需求，直接写几条 case 可能更快，没必要把整套流程铺满。

另外，项目早期的效果也不会立刻很好。因为最值钱的那部分能力，恰恰依赖沉淀；而沉淀这件事，本来就要靠时间慢慢攒。还有一点得承认：即使你已经有了约束、有了沉淀，Agent 也还是会犯错。它不会因为知识库变厚了，就突然变成一个永远正确的人。

但两者的区别非常大。没有沉淀时，它每次都像临场发挥；有沉淀时，它是在已有地基上继续施工。前者出错以后，你往往不知道错在哪一层。后者出错，至少大多数时候你能定位：是基线错了、覆盖漏了、断言弱了，还是沉淀本身该更新了。

**这一系列最后想说的一句**

很多团队把 Agent 用不好，不是因为模型不够强，而是因为希望它每次都从零开始，却还能稳定做对。这事本身就不太现实。

高质量的 Agent 用例设计，靠的从来不只是一次对话里的提示词，还靠结构化约束、存量知识沉淀，以及人把关键判断守住。

如果要把这篇压成一个最短的落地建议，我会给三句：先建存量自动化索引，再做增量过滤，不要默认全量重写，最后把真正值得长期复用的经验，经过人审后再沉淀。

这三步做起来，Agent 才会越来越像一个有项目经验的同事，而不是一个每次都要重新培训的实习生。

本文基于真实交易系统测试项目实践总结。
