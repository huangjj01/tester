系列：《让 Agent 设计出高质量测试用例》· 第 3 篇

断言是用例的灵魂

---

上一篇把七步约束法讲完了。这一篇我只盯住其中最容易出事故的一步：断言。为什么单独拿出来讲？因为很多用例看起来没问题，真正危险的地方往往不在场景，而在断言。

场景写错了，通常一跑就会暴露；断言写弱了，最糟糕的情况不是失败，而是通过。这才麻烦。团队看到“通过”，会默认功能没问题。直到线上出事，回头翻 case，才发现那条用例从头到尾根本没验证到核心业务逻辑。这种“假通过”，比“明确失败”更坑。

**什么叫弱断言**

最常见的几种说法，你一定见过：“验证订单处理成功。”“系统返回正确结果。”“ordStatus=0。”这些话有一个共同特点：它们最多只能证明“系统有响应”，很难证明“业务语义正确”。

比如验证 OCO 订单，收到 ack 当然是必要的，但远远不够。你真正要证明的是：一腿成交以后，另一腿会不会被自动取消；关联关系是不是对的；关键字段有没有按预期落下去。再比如验证一个过期拒绝场景，“有拒绝”只能说明它没接单，不足以证明它是因为过期拒绝，也不足以证明它没有往下游继续发。

这就是弱断言最讨厌的地方。它经常不是明显错误，而是只验证了最外层那一层皮。

**Agent 为什么特别容易写出这种东西**

因为弱断言太像“标准答案”了。“验证功能正常”“确认系统行为符合预期”“系统处理成功”这类表达，在历史文档、旧模板和公开材料里到处都是。Agent 一旦没有被强约束，就很容易往这个方向退化。

它也不是故意偷懒，它只是会自然选择最省力、最通用、最不容易马上被挑错的表达。问题在于，测试不是写得圆就行，测试要能证明事。

**怎么把断言从废话拉回证据**

我们后来定下来的顺序很简单：不是先写步骤，再补预期，而是先回答：“这条 case 到底要证明什么业务事实？”

比如你不是先写“下一个条件单，设置时钟漂移 120 秒，观察结果”，而是先写：测试意图是验证正向时钟漂移会让未到期订单被提前判定过期；要证明的业务事实是，虚拟当前时间超过过期时间后，网关应在本地拒绝该订单，且不能继续往下游发送。断言自然就跟着出来了：要看拒绝状态、拒绝原因，还要补一层证据证明它确实没有往下游继续发。

这个顺序的关键在于，一旦“要证明什么”先被写清楚，断言就很难继续糊弄。你总得拿出能支撑这个业务事实的观察点。反过来，如果你先把步骤写完，最后再补一列预期结果，就很容易写成“执行完了，看结果对不对”。这正是弱断言最爱钻的空子。

**一个很实用的判断标准**

如果一句断言可以替换到十几条不同的 case 里都不显得违和，那它大概率就是弱断言。比如“收到回执”“系统正常处理”“返回成功”“有终态”这些话都太通用了，通用到几乎不携带业务信息。

而真正有用的断言，通常都带着场景特征。验证改单成功，不只是“收到回执”，还要看到修改后的字段值；验证改单拒绝后再次改单成功，不只是“第二次成功”，还要证明第一次 reject 存在、原状态没被改坏、第二次基于正确原单继续走；验证字段透传，不只是“下单成功”，还要证明北向回执、服务端链路、必要时南向证据里字段值一致；验证竞态，不只是“最后有个终态”，还要证明到底是谁优先：成交优先，还是撤单优先。

你会发现，这些都不是从“系统有反应”出发，而是从“我要证明哪件事”出发。

**还有一种坑：字段是编出来的**

除了弱断言，Agent 还有一种常见失误：臆想字段。它觉得某类订单“应该有一个字段”，于是顺手把那个字段写进断言里。看上去很专业，实际上可能根本不存在。这种坑最烦的地方在于，执行时你会以为功能有问题，结果查半天才发现，错的是用例自己。

所以我们后来把规则压得很硬：断言字段不能靠猜。先看现有自动化能力能断什么，再看协议和接口契约里有没有这个字段，必要时再去实现侧确认。如果还确认不了，就把这条 case 标成阻塞，别拿相似字段硬顶上去。

这听起来严格，但比写一个“大概率存在”的字段进去要省事得多。因为后者早晚会回来找你。

**工具断不了，不能假装已经覆盖了**

还有个场景很常见：测试意图是对的，但当前工具断不到。比如北向回执没暴露关键字段，比如自动化能力看不到内部关联关系，比如必须结合内部事件日志或南向原始日志，才能把业务事实坐实。

这时候最容易滑坡的做法是：“那我先用 ordStatus=0 顶一下，算覆盖了。”这个念头一定要忍住。工具能力不足，不等于测试意图可以降级。正确做法是老老实实写出来：这条 case 的目标断言目前自动化做不到，属于能力缺口，需要补证据或补工具。它可以是阻塞，可以是待建设，但不能伪装成“已经测过”。

**好用例名，往往已经告诉你断言该怎么写**

我后来越来越相信一件事：一个用例名字如果写得含糊，后面的断言大概率也会含糊。比如“撤单校验”“GTC 订单检查”“部分成交后改单验证”，它们说了对象，但没说风险，也没说要证明什么。

而如果名字写成“终态订单再次撤单必须被拒绝且不能复活旧订单”“GTC 订单跨日后必须保持有效而不能被误清理”“部分成交后改单数量不能小于已成交数量”，断言方向几乎已经写在标题里了。所以对我们来说，用例命名不是排版问题，而是测试意图的第一道表达。

**一个真实例子**

我们遇到过一个虚拟时钟漂移场景，Agent 一开始写出的预期是：算法单触发到下游网关时，如果因为时钟漂移而过期，应该直接 reject。这句话听上去没什么毛病，但它其实把链路理解错了。

真实链路是：先下算法单，等行情触发，再由算法引擎送单到下游网关，最后网关判断过期并形成终态闭环。也就是说，这里真正要证明的不是“直接 reject”，而是“触发以后，过期判断在正确位置生效，并形成预期的终态”。

一旦测试意图这样改写，断言就跟着一起变准了。不是盯着一个简单 reject 状态，而是盯住那条完整业务链路该落成什么结果。这个例子特别能说明问题：很多断言之所以弱，不是因为不会写字段，而是因为前面那句“我要证明什么”压根没想清楚。

**这一篇只想留下三句话**

第一，断言不是用例的附属品，断言才是用例真正证明自己的地方。第二，弱断言最危险的地方，不是它明显错误，而是它太容易制造“假通过”。第三，工具做不到时，要承认缺口，不要降低标准，更不要拿一句模糊断言冒充覆盖。

只要把这三件事守住，很多看起来很复杂的断言设计问题，反而会慢慢变得清楚。
