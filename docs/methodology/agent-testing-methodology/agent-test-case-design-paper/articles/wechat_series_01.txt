系列：《让 Agent 设计出高质量测试用例》· 第 1 篇

快≠好：Agent 用例设计最常见的七种翻车

---

你让 Agent 帮你写测试用例，它 3 分钟给了你 20 条。格式漂亮，分组齐全，优先级和预期结果都写上了。第一眼看，真的很容易兴奋。我一开始也这么想过：如果它已经能把用例写成这样，那这件事是不是快可以交给它了？

后来真把这些 case 拿去落地，心情就完全变了。有的需求基线是错的，有的输入当前环境根本构造不出来，有的预期结果写了跟没写一样，还有一些明明已经被回归覆盖了，它又从头写了一遍。最后看下来，不是“3 分钟省了我半天”，而是“3 分钟先生成一版，再花半天返工”。

这不是一次偶然失手，也不是某个模型特别不稳。这更像是 Agent 设计测试用例时的典型错觉：它写得很快，也写得很像，但“像用例”和“真能用”，中间隔着很远。

**为什么它总能写得像，却不一定能用**

先说我的结论：问题往往不在模型太弱，而在于我们把用例设计误当成了文本生成。如果只是生成文本，Agent 已经很强了。你给它一段需求，它能快速整理结构、补齐字段、铺开场景，看起来相当完整。

可测试用例设计不是把需求换个说法写出来。它至少还包含这些判断：需求到底有几个来源，彼此是不是一致；哪些场景理论上该测，但当前环境其实做不了；哪些路径已经被存量回归覆盖，这次只需要补增量；每条 case 到底要证明什么业务事实；预期结果能不能被工具断言，而不是只靠人眼感觉“差不多对”。

这些事，Agent 不是完全做不到。更常见的情况是：没人要求它先做，它就直接跳到了最后一步，把答案写出来了。这也是为什么很多 Agent 产出的用例，第一眼顺，第二眼虚，第三眼开始到处冒坑。

**我们踩过的七种翻车**

这些坑我们在项目里踩过很多次，收一收，大致就是七类。

第一类，需求基线偏了。Agent 只看了一份通知或一段聊天记录，就开始写 case，没有去对齐代码变更、接口契约和后续澄清。结果文档里说的是一个行为，系统里跑的是另一个行为。它按前者写预期，执行时当然全对不上。

第二类，覆盖维度漏了。这类最容易骗人。它通常会给你几条很像样的 case：下单成功、改单成功、撤单成功。表面上基本操作都齐了，但真正危险的路径没了，比如“改单拒绝后再改单”“撤单与成交在途竞态”“部分成交后继续改数量”。它不是完全不知道这些场景，而是没有一个覆盖框架逼着它系统去过。

第三类，断言弱得像空气。“验证订单处理成功”“系统返回正确结果”“ordStatus=0”这种话你一定见过。问题是，它们最多只能证明“系统有响应”，很难证明“业务语义是对的”。比如验证 OCO 订单，你要证明的是一腿成交以后另一腿会不会自动取消，而不是只证明下单时收到了 ack。

第四类，理论输入当真实输入。有些字段在文档里看着像输入项，实际上是服务端根据交易日历、配置或内部状态算出来再下发的。Agent 不会天然知道这个差别，于是它会顺手给你设计一条当前环境根本构造不出来的 case，而且写得像随时能跑。

第五类，全量生成，增量为零。项目里明明已经有很多自动化回归覆盖了基础生命周期，新需求只需要补几条真正的增量。但 Agent 一旦不知道“已经有什么”，就会默认从头再写一遍。最后 25 条里有一大半都跟存量重复，真正该补的那几条反而不突出。

第六类，用例追不回去。你问它：覆盖清单里的某一项，对应哪条 case？答不上来。再反过来问：某条 case 对应的是哪一个覆盖目标？也答不上来。没有这种双向关系，最后就很难判断覆盖到底完整不完整。

第七类，每次都从零开始。上个月做过一次很像的需求，已经沉淀出动作链、生命周期节点、断言模板。这个月换个新对话，Agent 又像第一次接触这个领域一样重来一遍。同类需求的质量，不取决于团队有没有积累，而取决于这次上下文喂得够不够全。

**这七类问题，其实是一回事**

表面上看，七种翻车各不相同。有的是信息不准，有的是覆盖不全，有的是断言太弱，有的是根本不可执行。但往下挖一层，会发现它们都指向同一个误区：我们把 Agent 当成了一个“用例生成器”，输入需求，输出 case，最好一次完成，越快越好。

可高质量的用例设计不是一个瞬间出结果的动作，它更像一个分阶段收敛的过程。前面要先甄别信息、锁定基线、确认范围、过覆盖维度，后面才能谈步骤、断言和回查。如果这些前置动作没有被显式要求，Agent 就会走最省力的路径：先写出来再说。这时候它交给你的，往往不是可执行的测试设计，而是“像测试设计的文本”。

**“那我把提示词写长一点，不就行了吗？”**

很多人第一反应都是这个。坦白说，我一开始也试过，后来发现不太行。不是提示词完全没用，而是它很难独自承担流程控制这件事。第一，上下文会被压缩。你前面写得再细，任务一长、对话一多，早期规则就可能被冲淡。第二，任务切换会丢上下文。上一个需求里辛苦得出的判断，不会自动变成下一个需求的稳定资产。第三，Agent 会自己补空白。你说“先甄别信息源”，它可能理解成“这次应该没什么歧义”，但实际上歧义只是没被显式列出来。

所以提示词当然重要，但它更像提醒，不像护栏。真正能稳住质量的，不是一段更长的话，而是一套不能随便跳步的约束流程。

**这一篇只想留下一个判断**

如果只让我用一句话总结这篇，我会说：Agent 用例设计最麻烦的问题，不是它写不出来，而是它太容易写出一堆看起来没毛病、实际上需要大量返工的东西。换句话说，速度不是问题，失控才是问题。

下一篇我们就不再停留在“它会怎么翻车”，而是往前走一步：怎么给它一套结构化约束，让它从“像用例”慢慢收敛到“能用的用例”。

**下篇预告**

第 2 篇：七步约束法，从“像用例”到“能用的用例”。

我们会把整个过程拆开：先看信息源怎么甄别，再看基线怎么锁、范围怎么收、覆盖怎么过、断言怎么写，最后怎么回查。很多今天看起来像“模型能力问题”的坑，换成流程约束后，能少掉一大半。

本文基于真实交易系统测试项目实践总结。
