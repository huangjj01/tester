系列：《让 Agent 设计出高质量测试用例》· 第 2 篇

七步约束法：从“像用例”到“能用的用例”

---

上一篇把问题摊开了：Agent 写用例最麻烦的地方，不是写不出来，而是太容易写出一堆看起来像样、实际需要返工的东西。那下一步自然就是：怎么管住它？

我说的“管住”，不是把提示词再写长 5000 字，也不是贴一张注意事项清单。真正有用的是把用例设计拆成几个不能乱跳的阶段，让 Agent 一步一步收敛。我们后来在项目里跑出来的一套流程，一共七步：

信息源甄别 -> 基线锁定 -> 范围过滤 -> 覆盖设计 -> 用例与断言 -> 人机审核 -> 回查

你可以把它理解成一条传送带。每一步都只解决一类问题，每一步都要留下能检查的产物。这样到了最后，交给你的就不再是一份突然冒出来的成品，而是一条有过程、有依据的设计链路。

**为什么一定要分步，不直接一次写完**

很多团队现在的做法其实都差不多：把需求丢给 Agent，等它一口气生成一版用例，然后人来做最后审核。问题在于，这种模式最省的是 Agent，不是人。因为你真正开始发现问题，已经是在它交卷之后了。那时你看到的是成品，不是过程。你知道哪里不对，却不知道它是在哪一步拐歪的。

分阶段的好处就在这里。如果信息源阶段就有冲突，那问题属于基线；如果基线没问题，但覆盖维度漏了，那问题属于覆盖设计；如果覆盖对了，但断言太弱，那问题属于用例设计。错在什么地方，就回到那一步修，不用整篇推翻重来。

**七步到底在做什么**

下面不按培训材料的写法一条条展开到很细，只说每一步最关键的作用。

第一步，信息源甄别。先别急着写 case，先搞清楚“需求到底是什么”。真实项目里，需求经常同时散在 PRD、代码说明、通知、群消息和口头澄清里，而且彼此不一定一致。Agent 最容易犯的一个错，就是看了一份材料就开写。我们要求它先把来源列出来，再把矛盾点标出来，冲突的地方先找人定口径。

第二步，基线锁定。甄别完以后，要定一版本次真正采用的需求基线。否则后面所有设计都可能建立在半确认状态上。对我们来说，这一步本质上是在回答：“这次到底按哪个版本算？”

第三步，范围过滤。不是所有相关内容都该进本次新用例。已有回归覆盖的基础能力，不重复写；外部系统本身的行为，不抢着测；当前环境构造不出来的输入，不假装能做。范围一旦不收，Agent 就会自然滑向全量生成。

第四步，覆盖设计。这一步我特别想强调一句：覆盖设计是工程问题，不是创意问题。不是让 Agent 随便发散场景，而是给它一个框架，让它按功能动作、状态节点、异常分支、时间窗口、恢复行为这些维度去系统遍历。没有这个框架，它想到几个有趣边界场景没什么用，基础组合照样会漏。

第五步，用例与断言。到了这一步，才开始真正写 case。但顺序也不能反。不是先写步骤、最后补一句预期结果，而是先明确这条 case 要证明什么业务事实，再倒推出必须断言什么，最后才写输入和步骤。这样写出来的用例，才不容易变成一堆动作说明书。

第六步，人机审核。有些问题必须停下来问人，不能让 Agent 自己脑补。比如某个行为到底算 bug 还是 feature，某个字段是否真的会暴露出来，某个边界条件在当前环境能不能构造。审核不是最后看一眼，而是关键节点的人机交接。

第七步，回查。这是最容易被偷懒的一步，也是最值钱的一步。用例写完以后，要反过来看：覆盖清单里的每一项有没有落到具体 case，上面写的 case 又各自在证明什么。如果这一步不做，很多遗漏不会自己跳出来。

**最容易被低估的三步**

如果你让我挑三个最容易被忽略、但最影响质量的步骤，我会选这三个。

第一，信息源甄别。因为很多人默认“需求已经给你了”，其实没有。给你的只是几份可能互相打架的材料。这个时候 Agent 很擅长做比对，但前提是你得先让它比。

第二，范围过滤。很多团队的问题不是 case 写少了，而是写太多了。把已覆盖的内容再写一遍，看起来很勤奋，实际上只会稀释注意力。第 4 篇我会专门展开讲这件事。

第三，回查。人和 Agent 都很容易在“已经写完了”这一刻松下来。但很多系统性遗漏，只有在回查时才会暴露。我们自己的经验是，只要认真回查，几乎每次都能再捞出 1 到 2 个漏点。

**为什么这套方法比长提示词更靠谱**

因为提示词更像提醒，流程更像护栏。提醒的意思是：我希望你这么做；护栏的意思是：你不能跳过去。这两者差别很大。

你在提示词里写“请先确认需求来源是否一致”，Agent 可能会理解成“这次应该没问题”。但如果流程明确规定，没有甄别表就不能进入下一步，那它就必须先把这件事做完。我后来越来越觉得，很多所谓的 Agent 质量问题，本质上不是模型不会，而是流程没有把该做的动作变成强制动作。

**这一篇想留下的核心判断**

七步约束法不是为了让 Agent 变慢，而是为了让它少走弯路。你当然可以追求一次性生成，但代价通常是把本该前置暴露的问题，拖到最后一起返工。而分阶段收敛的好处是：每一步只解决一类问题，每一步都能检查，错了也知道该回哪一步修。这比让它一口气写完，再靠人从成品里抓 bug，要稳得多。
