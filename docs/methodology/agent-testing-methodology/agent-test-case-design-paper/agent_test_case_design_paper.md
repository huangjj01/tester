# 让 AI Agent 设计出高质量测试用例：一种结构化约束方法

## 摘要

AI Agent 已经能够在数分钟内生成格式工整的测试用例，但"能生成"与"高质量"之间存在显著鸿沟。在真实项目实践中，Agent 生成的用例普遍存在需求基线偏移、覆盖维度遗漏、断言弱化、不可执行和无法追溯等质量问题。本文基于一个某业务系统（示例业务系统）的测试工程实践，提出 Agent 用例设计的七阶段结构化约束方法：信息源管理与跨源甄别、需求基线锁定与范围过滤、系统化覆盖设计、测试意图驱动的用例与断言设计、人机协作审核闭环、领域知识渐进沉淀、回查与一致性保障。该方法通过在每个阶段设置明确的输入条件、质量门禁和输出规范，将 Agent 的"快速生成"能力转化为"可信赖的测试设计"能力。通过 EXAMPLE-1001 sample-client fake-clock 功能测试和 示例业务系统 订单生命周期用例设计两个案例，本文验证了该方法在收敛 Agent 用例设计偏差、提升覆盖完整性和断言有效性方面的实际效果。

## 关键词

AI Agent；测试用例设计；结构化约束；测试意图；断言设计；覆盖分析；人机协作；领域知识沉淀

## 1. 引言

### 1.1 Agent 用例生成的现状

大模型 Agent 在测试用例生成领域展现了令人印象深刻的速度。给定一段需求描述，Agent 可以在几分钟内输出数十条格式规范的测试用例，覆盖点看起来也不少。这种能力让许多团队开始尝试用 Agent 替代或辅助测试用例设计工作。

然而，速度不等于质量。在我们的实际项目中，Agent 生成的用例经常出现以下情况：

- 看起来覆盖了很多场景，但仔细检查发现关键维度被遗漏
- 预期结果写得很"正确"，但实际上无法被任何工具断言
- 用例之间缺乏系统性，像是对需求文本的逐句翻译而非工程化设计
- 需求来源之间存在矛盾时，Agent 默默选择了其中一个版本，没有暴露冲突
- 用例无法追溯到覆盖目标，也无法判断是否存在遗漏

### 1.2 问题的本质

这些问题的根源不是模型能力不足。Agent 确实理解需求文本，也确实知道测试用例应该长什么样。问题在于：**测试用例设计是一项工程活动，不是文本生成活动。**

高质量的测试用例设计需要：

1. **信息甄别能力**：从多个来源（需求文档、代码变更、通知、口头澄清）中识别矛盾和歧义
2. **范围判断能力**：区分"理论上应该测"和"当前环境能测"
3. **系统化覆盖能力**：不是发散联想，而是按维度系统遍历
4. **断言设计能力**：不是写"验证功能正常"，而是定义可执行的通过标准
5. **增量思维**：识别存量覆盖，只设计真正的增量
6. **可追溯性**：每个用例能回到覆盖目标，每个覆盖目标能找到对应用例

Agent 天然擅长的是"生成"——给定输入，快速产出格式化输出。但上述六项能力中，没有一项是纯粹的生成问题。它们都需要**结构化的约束流程**来引导 Agent 的行为。

### 1.3 本文的主张

本文的核心主张是：

> AI Agent 设计高质量测试用例的关键，不在于模型的生成能力本身，而在于通过结构化的多阶段约束流程，将 Agent 的"快速生成"能力转化为"可信赖的测试设计"能力。

换言之，**约束即能力**。没有约束的 Agent 生成的是"看起来像用例的文本"；有约束的 Agent 生成的是"可执行的测试设计"。

### 1.4 本文的贡献

本文的贡献包括三点：

1. **提出 Agent 用例设计的七阶段结构化约束模型**：将 Agent 从"一次性生成"拉回"分阶段收敛"，每个阶段有明确的输入条件、质量门禁和输出规范。
2. **定义"测试意图驱动"的断言设计方法**：解决 Agent 用例设计中最普遍的"弱断言"问题，建立从测试意图到可验证断言的系统化映射。
3. **建立领域知识渐进沉淀机制**：通过覆盖清单、生命周期矩阵、已知能力基线和增量过滤，让 Agent 的用例设计质量随项目资产积累持续提升。

### 1.5 与已有工作的关系

本文是《从用例设计到执行报告：一种可落地的 Agent 测试工程方法论》的深度展开。该方法论提出了六层约束模型（任务路由、需求与用例、测试实施设计、执行证据、判断基线、交付与沉淀），本文聚焦其中第二层——需求与用例层，深入探讨"如何让 Agent 设计出高质量用例"这一具体问题。


## 2. Agent 用例设计的典型质量问题

在我们的项目实践中，Agent 设计测试用例时反复出现七类质量问题。这些问题不是偶发的，而是在缺少结构化约束时几乎必然出现的系统性缺陷。

### 2.1 需求基线偏移

**表现**：Agent 从单一来源（如一封通知邮件）直接生成用例，没有对齐代码变更、接口契约和用户澄清。当多个来源存在矛盾时，Agent 默默选择了其中一个版本，没有暴露冲突。

**案例**：在 EXAMPLE-1001 fake-clock 需求中，通知邮件描述了虚拟时钟漂移的基本公式，但没有说明 `DayOrderExpireTime=0` 时的行为。Agent 初期按"通用理解"假设了 `0` 表示不过期，但没有标注这是假设而非确认事实。

**后果**：用例的预期结果建立在未经确认的假设上，执行时才发现输入不可构造或预期不正确。

### 2.2 覆盖维度遗漏

**表现**：Agent 生成的用例看起来数量不少，但覆盖维度不系统。它倾向于沿着需求文本的叙述顺序逐句翻译，而不是按业务维度系统遍历。

**案例**：对 示例业务系统 订单类需求，Agent 容易只覆盖"下单成功""改单成功""撤单成功"三个点状场景，而遗漏动作链组合（如"改单拒绝后再改单""撤单与成交在途竞态"）和复杂状态后的继续动作（如"部分成交后改数量小于已成交量"）。

**后果**：测试覆盖存在系统性盲区，高风险路径未被验证。

### 2.3 断言弱化

**表现**：用例的"预期结果"写得过于笼统，如"验证功能正常""订单处理成功""系统返回正确结果"。或者只写了最基础的状态断言（如 `ordStatus=0`），无法证明复杂的业务语义。

**案例**：验证 OCO（One-Cancels-Other）订单时，Agent 只断言"下单成功"（`ordStatus=0`），没有断言 OCO 类型字段、关联关系或一腿成交后另一腿自动取消的联动行为。这样的断言即使通过，也无法证明 OCO 语义正确。

**后果**：用例即使执行通过，也无法证明目标功能正确。测试变成了"走过场"。

### 2.4 理论输入与可执行输入混淆

**表现**：Agent 设计的用例假设所有输入都可以任意构造，没有考虑当前环境的实际约束。

**案例**：fake-clock 测试中，Agent 设计了"DayOrderExpireTime=0 时不应过期"的用例，但 `DayOrderExpireTime` 是 upstream-service 根据交易日历计算后下发的，测试脚本无法手工传入。这个用例在当前环境下不可执行。

**后果**：不可执行的用例如果被强行标记为"通过"或"失败"，都会误导测试结论。正确做法是标记为"本轮不执行"并说明原因。

### 2.5 增量意识缺失

**表现**：Agent 天然倾向全量生成。面对一个新需求，它会把所有相关场景都写成新用例，包括已经被存量自动化回归覆盖的场景。

**案例**：示例业务系统 项目中，`type=trailingStop` 和 `type=normal_order` 的存量自动化 case 已经覆盖了基础的下单、改单、撤单、成交、恢复等生命周期路径。新需求只需要设计增量 case，但 Agent 初期会把这些基础路径重新写一遍。

**后果**：用例文档膨胀，真正的增量被淹没在重复内容中；团队无法快速识别"这次到底新增了什么"。

### 2.6 用例不可追溯

**表现**：用例与覆盖目标之间缺乏双向追溯关系。无法从覆盖清单找到对应用例，也无法从用例回到它要验证的覆盖目标。

**后果**：无法判断覆盖是否完整，无法在需求变更时快速定位受影响的用例。

### 2.7 领域知识未沉淀

**表现**：Agent 每次设计用例都从零开始，不会利用项目中已经积累的领域知识（如生命周期矩阵、已知能力基线、历史缺陷模式）。

**后果**：同类需求的用例设计质量不稳定，取决于当次对话的上下文质量而非项目知识积累。

## 3. 结构化约束方法：总体框架

### 3.1 设计理念

针对上述七类质量问题，我们提出的核心设计理念是：**用结构化的阶段约束替代一次性生成。**

传统的 Agent 用例生成模式是：

```
需求输入 -> Agent 一次性生成 -> 用例输出
```

这种模式把用例设计当作一个黑盒函数调用。Agent 内部可能做了一些推理，但过程不可见、不可控、不可复核。

我们提出的结构化约束模式是：

```
信息源管理 -> 跨源甄别 -> 需求基线锁定 -> 范围过滤
  -> 系统化覆盖设计 -> 测试意图驱动的用例与断言
  -> 人机协作审核 -> 回查与沉淀
```

每个阶段有明确的：
- **输入条件**：进入该阶段前必须具备什么
- **执行规则**：该阶段内 Agent 必须做什么、不能做什么
- **质量门禁**：该阶段的输出必须满足什么条件才能进入下一阶段
- **输出规范**：该阶段产出什么交付物

### 3.2 七阶段概览

| 阶段 | 解决的质量问题 | 核心动作 | 质量门禁 |
|------|--------------|---------|---------|
| 1. 信息源管理与跨源甄别 | 需求基线偏移 | 列源、比对、标冲突、升级人类 | 冲突项必须有解决结论 |
| 2. 需求基线锁定与范围过滤 | 理论/可执行混淆、增量缺失 | 锁基线、过滤存量、标不可执行 | 基线有明确采纳依据 |
| 3. 系统化覆盖设计 | 覆盖维度遗漏 | 按维度建清单、交叉矩阵、动作链 | 覆盖清单完整且可回查 |
| 4. 测试意图驱动的用例与断言 | 断言弱化、不可执行 | 先写意图再写用例、三质量标准 | 每条用例通过三质量检查 |
| 5. 人机协作审核 | 假设未确认、字段臆想 | 草案->审核->修正 | 人类确认关键业务口径 |
| 6. 领域知识沉淀 | 知识未积累 | 矩阵、基线、字典更新 | 新能力回填基线文档 |
| 7. 回查与一致性保障 | 不可追溯 | 覆盖回查、规则变更扫描 | 每个清单项有对应用例 |

### 3.3 阶段之间的关系

七个阶段不是简单的线性流水线。它们之间存在反馈关系：

- 第 4 阶段（用例设计）可能发现第 3 阶段（覆盖设计）遗漏的维度，需要回补
- 第 5 阶段（人类审核）可能修正第 2 阶段（需求基线）的假设
- 第 7 阶段（回查）可能发现第 4 阶段的用例与第 2 阶段的基线不一致

但反馈不意味着可以跳过。**每个阶段必须先完成再进入下一阶段**，反馈时必须回到对应阶段重新执行，而不是在当前阶段临时修补。

### 3.4 我的观点：覆盖设计是工程问题，不是创意问题

Agent 的"创意能力"——联想、发散、类比——在用例设计中的价值其实有限。测试覆盖设计本质上是一个**系统化遍历问题**：给定业务维度和状态空间，按规则组合出需要验证的路径。

Agent 真正有价值的能力是**快速系统遍历**——但这需要结构化的覆盖框架来引导。没有框架时，Agent 的"创意"反而会导致覆盖不系统：它可能想到一些有趣的边界场景，却遗漏了基础的状态组合。

因此，本方法的第 3 阶段（系统化覆盖设计）不是让 Agent "自由发挥"，而是给它一个覆盖框架，让它在框架内做系统遍历。


## 4. 第一阶段：信息源管理与跨源甄别

### 4.1 为什么信息源管理是第一步

Agent 设计用例时，第一个动作通常是"阅读需求然后开始写"。但在真实项目中，"需求"不是一个单一文档，而是散落在多个来源中的信息碎片：

- 产品需求文档（PRD）
- 代码变更说明或 commit message
- 通知邮件或即时消息
- 接口契约或协议规范
- 用户在对话中的口头澄清
- 已有测试用例或回归套件
- 历史缺陷记录

这些来源之间经常存在矛盾、歧义或版本差异。如果 Agent 不做甄别就直接生成用例，它实际上是在一个不确定的基线上构建测试设计——这是后续所有质量问题的根源。

### 4.2 信息源列举与版本过滤

第一步是显式列出所有信息来源，并对每个来源标注状态：

- `BASELINE-CURRENT`：当前生效的权威来源
- `REFERENCE-HISTORICAL`：历史版本，仅供参考
- `PENDING-CONFIRMATION`：待人类确认

**版本过滤规则**：当多个文档描述同一主题时，必须进行版本过滤：
- 优先使用标记为"正式版""生效版"或最新审批日期的文档
- 历史版本只能作为背景参考，不能定义预期结果
- 两个"当前"版本冲突时，升级人类确认

### 4.3 跨源甄别：冲突识别与解决

跨源甄别是本阶段的核心动作。对每个影响测试设计的高风险主题，Agent 必须提取各来源的说法，构建甄别表：

| 主题 | 来源 A 说法 | 来源 B 说法 | 问题类型 | 解决方案 |
|------|-----------|-----------|---------|---------|
| 维护窗口时间 | 21:00-21:15 UTC | 21:00-21:02 UTC | 直接冲突 | 升级人类确认 |
| 过期判断公式 | 虚拟时间 >= ExpireTime | 未提及 | 信息缺失 | 以代码为准，标注来源 |

**问题类型分类**：
- **直接冲突**：两个来源断言不同事实
- **歧义**：措辞模糊，可能有多种理解
- **术语漂移**：同一个词在不同来源中含义不同（如不同时区的"维护窗口"）
- **信息缺失**：某个关键行为只有一个来源提及

**解决规则**：
- 直接冲突和歧义必须升级人类确认，Agent 不能默默选择一个版本
- 术语漂移必须在甄别表中显式记录，后续用例中统一术语
- 信息缺失标注为 `ASSUMPTION (until confirmed)`

### 4.4 甄别结论的文档化

甄别结论不能只存在于 Agent 的"思考过程"中，必须写入正式文档。这有两个作用：

1. **可复核**：后续审核者能看到 Agent 做了哪些判断、依据是什么
2. **可追溯**：当需求变更时，能快速定位哪些用例受影响

甄别结论的输出格式示例：

```
## 信息源甄别结论

### 采纳基线
- 过期判断公式：以代码实现为准（来源：commit xxx）
- 维护窗口：21:00:01-21:01:59 UTC（来源：人类确认 2026-05-14）

### 待确认项
- DayOrderExpireTime=0 的行为：需求未明确，标记 PENDING HUMAN

### 历史版本差异（仅供参考）
- 旧通知中维护窗口为 21:00-21:15，已被新口径替代
```

### 4.5 示例业务系统 领域的特殊甄别维度

在 示例业务系统（Sample Business Domain）领域，跨源甄别需要特别关注以下维度：

- **时区差异**：某外部交易所 公开文档用 CT（Central Time），内部系统用 UTC 或 ET，必须统一
- **阶段命名差异**：交易所文档的 Close / Pre-open / No-cancel / Open 与内部架构文档的命名可能不一致
- **版本修订日期**：交易所规则可能在某个日期后变更，必须确认当前生效版本
- **服务端行为 vs 客户端行为**：同一个拒绝，在服务端 event.log 和客户端北向 FIX 中的表达可能不同

### 4.6 我的观点：甄别是 Agent 最被低估的能力

在实践中，我发现跨源甄别是 Agent 最被低估的能力应用场景。Agent 的优势不只是"快速生成"，还包括"快速比对"——它能同时持有多个文档的内容，逐项对比差异。这种能力在人工操作中极其耗时，但对 Agent 来说几乎是即时的。

关键在于：**必须显式要求 Agent 做甄别，而不是让它默默做选择。** 没有约束时，Agent 会把甄别过程内化为隐式判断；有约束时，Agent 会把甄别过程外化为可复核的文档。

这也引出一个更深层的观察：Agent 的很多"错误"不是因为它不能做正确的事，而是因为没有人要求它把正确的事做得可见。结构化约束的本质，就是把 Agent 内部的隐式推理转化为外部的显式过程。

## 5. 第二阶段：需求基线锁定与范围过滤

### 5.1 从甄别结论到需求基线

跨源甄别完成后，Agent 需要把甄别结论转化为明确的需求基线——这是后续所有用例设计的"地基"。

需求基线应包含：
- 被测功能的核心业务规则
- 系统责任边界（哪些行为由本系统负责，哪些由外部系统负责）
- 关键状态变化和业务结果
- 重要的排除项和非目标
- 采纳的基线依据（哪些来源被选择，为什么）
- 仍需确认的假设（标记 PENDING HUMAN）

### 5.2 范围过滤：四类不应进入新需求用例的内容

在构建覆盖清单之前，必须先过滤掉不属于本次新需求用例的内容：

**第一类：固有存量行为。** 在本次变更之前就存在、且不受本次变更影响的行为。这些行为应该由存量回归套件覆盖，不需要在新需求用例中重复。

**第二类：外部系统边界。** 如果某个行为（如交易所的会话状态切换时间）由外部系统拥有和执行，不应写用例验证外部系统是否正确切换。应该写的是：在外部系统处于各种状态时，本系统的行为是否正确。

**第三类：回归管理。** 回归套件是独立管理的资产。不应把回归 case 嵌入新需求用例文档中。

**第四类：不可构造输入。** 当前环境无法构造的输入，不应写成可执行用例。应标记为"本轮不执行"并说明原因和前提条件。

### 5.3 增量过滤：识别存量覆盖

增量过滤是范围过滤的延伸，专门解决"Agent 全量生成"的倾向。

增量过滤的步骤：
1. 用覆盖维度列出理论覆盖点
2. 用存量自动化 case 索引标记已覆盖的点
3. 对已覆盖点，不再写成新需求 case；只在"回归执行要求"中声明必须执行并通过
4. 对新增语义、变更语义、未自动化覆盖的高风险组合，才写入增量用例
5. 若存量覆盖了动作链但不覆盖新参数或新边界，写成"改造/新增建议"

**关键原则**：增量过滤不是"少写用例"，而是"只写真正需要新增的用例"。存量回归仍然要执行，只是不在新需求文档中重复展开。

### 5.4 理论输入与可执行输入的区分

这是一个容易被忽视但极其重要的区分。

| 类型 | 定义 | 处理方式 |
|------|------|---------|
| 可执行输入 | 当前环境和工具能够构造的输入 | 正常设计用例 |
| 理论输入 | 业务上应该测试，但当前无法构造 | 标记"本轮不执行"，说明前提条件 |
| 不合法输入 | 业务上不应该出现的输入 | 不设计用例，或设计负面用例验证拒绝 |

Agent 最常犯的错误是把理论输入当作可执行输入。在 EXAMPLE-1001 案例中：
- `DayOrderExpireTime=0`：理论上应该测试"不过期"行为，但 upstream-service 当前不能模拟该输入 -> 标记本轮不执行
- `真实已过期订单`：理论上应该测试"负漂移不足时仍应过期"，但当前无法构造真实已过期输入 -> 标记本轮不执行
- `drift=120`（正漂移）：当前环境可以通过 guard 配置注入 -> 正常设计用例

正确标记"本轮不执行"不是测试失败，而是诚实的测试结论。它比强行执行不可控输入、然后把不确定结果写成"通过"要有价值得多。

### 5.5 我的观点：增量思维是 Agent 用例设计的分水岭

在我看来，增量思维是区分"Agent 辅助用例设计"和"Agent 高质量用例设计"的分水岭。

全量思维下，Agent 每次都从零开始，生成一堆看起来完整但实际上大量重复的用例。团队需要花时间去重、对比、筛选——这些时间可能比手写用例还多。

增量思维下，Agent 先理解"已经有什么"，再设计"还需要什么"。这要求 Agent 能够访问和理解存量资产（如自动化 case 索引、生命周期矩阵、已知能力基线），并在此基础上做差异化设计。

这也是为什么领域知识沉淀（第 6 阶段）如此重要——它为增量思维提供了"已有什么"的基础。没有沉淀的项目，Agent 每次都只能全量生成；有沉淀的项目，Agent 可以做精准增量。


## 6. 第三阶段：系统化覆盖设计

### 6.1 覆盖清单的构建方法

覆盖清单是用例设计的骨架。它回答的问题是："我们需要验证哪些维度？"

构建覆盖清单的通用维度包括：

- 功能动作（下单、改单、撤单、查询等）
- 角色或客户类型
- 状态转换（正常流转、异常流转、边界状态）
- 时间窗口或调度（日切、维护窗口、holiday）
- 上下游消息流（请求、响应、超时、重试）
- 成功路径
- 失败源分类（本地拒绝、下游拒绝、连接失败、超时）
- 恢复或重启行为
- 配置变体
- 外部依赖行为
- 审计、日志或可观测证据

**关键规则**：覆盖清单不是"想到什么写什么"，而是按维度系统遍历。Agent 必须逐个维度检查是否适用，不适用的写"不适用"，而不是跳过不提。

### 6.2 领域交叉矩阵

对于复杂业务领域，单一维度的覆盖清单不够。需要构建交叉矩阵，把多个维度组合起来。

以 示例业务系统 订单为例，核心交叉矩阵是"新增语义 x 已支持生命周期 x 高风险动作链"：

**第一步：锁定新增语义**

从需求中提取：
- 新增或变化的业务规则
- 支持哪些订单类型
- 支持哪些操作
- 支持哪些状态
- 哪些行为明确不支持

**第二步：对齐完整生命周期状态机**

用项目已有的生命周期基线文档，检查新增语义影响哪些生命周期节点：

| 生命周期节点 | 是否受影响 | 影响方式 |
|------------|-----------|---------|
| 下单确认 | 是 | 新增 fake-clock 判断 |
| 下单拒绝 | 是 | 新增过期拒绝路径 |
| 改单确认 | 否 | 沿用既有回归 |
| 部分成交 | 否 | 沿用既有回归 |
| 过期 | 是 | 核心变更点 |
| 恢复 | 待确认 | 恢复后 fake-clock 是否仍生效 |

**第三步：动作链组合覆盖**

订单类测试不是点状覆盖。必须检查动作链组合是否适用。我们在实践中总结了 24 条核心动作链模式：

- `place -> ack`
- `place -> reject`
- `place -> cancel -> canceled`
- `place -> replace -> replaced`
- `place -> partial fill -> full fill`
- `place -> partial fill -> cancel`
- `place -> replace reject -> replace again -> replaced`
- `place -> cancel reject -> cancel again -> canceled`
- `place -> cancel request -> full fill -> cancel reject`（竞态）
- `place -> replace request -> full fill -> replace reject`（竞态）
- `place -> recover -> replace -> cancel/fill`
- ...

每次设计订单需求用例时，先用完整生命周期状态机判断应该覆盖哪些动作链；再按需从存量自动化索引查找已有样本，输出可复用、需改造、新增、暂不自动化四类结论。

### 6.3 复杂状态后的继续动作矩阵

这是我们在实践中发现的一个关键覆盖维度，也是 Agent 最容易遗漏的。

传统用例设计倾向于只覆盖"当前操作"：下单成功、改单成功、撤单成功。但真实系统中，订单经历过的历史状态会影响后续行为。

**核心问题**：订单在经历了 `partial fill`、`replace reject`、`cancel reject`、`recovery`、`pending` 等复杂状态后，后续的 `replace`、`cancel`、`fill` 行为是否仍然正确？

我们要求 Agent 在设计用例时，必须建立"历史状态 x 后续动作"的矩阵：

| 历史状态 | 后续 replace | 后续 cancel | 后续 fill | 后续 reject |
|---------|------------|-----------|----------|-----------|
| ack 后未成交 | 应允许 | 应允许 | 应允许 | - |
| partial fill 后 | 应允许（qty > cumQty） | 应允许 | 应允许 | - |
| replace reject 后 | 应允许重试 | 应允许 | 应允许 | - |
| cancel reject 后 | 应允许 | 应允许重试 | 应允许 | - |
| recovery 后恢复活跃 | 应允许 | 应允许 | 应允许 | - |
| 已终态 | 应拒绝 | 应拒绝 | 不应发生 | - |

### 6.4 多层故障模式覆盖

当一个规则由多个组件层层执行时（如网关 -> 路由 -> 下游），必须覆盖多层故障模式：

- 主层正确拦截，次层一致
- 主层遗漏，次层兜底拦截
- 主层和次层判断不一致（fail-safe 行为）
- 两层都遗漏（高风险路径：告警 + 可观测 + 事后闭环）

这四种模式不是"可选的边界场景"，而是多层执行架构下的**强制安全用例**。

### 6.5 分层组合策略

面对大量覆盖维度，不能盲目做笛卡尔积。我们采用四层组合策略：

| 层次 | 覆盖目标 | 用例数量 |
|------|---------|---------|
| 冒烟层 | 新增语义的最基本成功和失败路径 | 少量 |
| 生命周期层 | 新增语义实际改变的生命周期节点 | 中等 |
| 高风险层 | 竞态、恢复、日切、维护窗口、复杂状态后继续动作 | 较多 |
| 固定回归层 | 存量自动化覆盖，只声明必须执行通过 | 不新增 |

这种分层避免了两个极端：要么只写冒烟（覆盖不足），要么全量笛卡尔积（用例爆炸）。

### 6.6 我的观点：覆盖框架比覆盖数量重要

很多团队评估用例质量时看数量："这次写了 50 条用例，覆盖应该够了。"但数量不等于覆盖。50 条用例如果都集中在成功路径，可能不如 20 条按维度系统设计的用例。

Agent 的优势恰恰在于：给它一个覆盖框架，它能快速、系统地遍历所有组合。人类的优势在于：定义覆盖框架本身——哪些维度重要、哪些组合高风险、哪些可以省略。

最佳协作模式是：**人类定义覆盖框架，Agent 在框架内做系统遍历，人类审核遍历结果。**

## 7. 第四阶段：测试意图驱动的用例与断言

### 7.1 测试意图优先原则

这是我们方法中最核心的设计原则：

> 先明确该 case 要证明的业务事实，再设计输入、动作链、断言和证据。

传统的用例设计顺序是：场景 -> 步骤 -> 预期结果。这种顺序容易导致"步骤写了很多，但不知道在证明什么"。

我们要求的顺序是：**测试意图 -> 要证明的业务事实 -> 必须断言什么 -> 输入和步骤设计**。

例如，不是先写"下一个 TrailingStop 订单，设置 drift=120"，而是先写：

```
测试意图：验证正漂移使未到期订单提前被判过期
要证明的业务事实：当 drift > 0 且 虚拟当前时间 >= DayOrderExpireTime 时，
                  sample-client 本地拒绝该订单，不向下游发送
必须断言：ordStatus=8, execType=8, text 包含 "Day order expired",
         event.log 无 TO_VENDOR 记录
```

然后才设计具体的输入和步骤。

### 7.2 用例命名即测试意图的第一道表达

用例名称是测试意图最直接的载体。评审人扫一眼用例列表，应该就能知道每条 case 在验证什么业务事实、防止什么业务风险。

我们在实践中发现，Agent 生成的用例名称极易退化为"测试对象 + 校验/检查/验证"的检查项标题。这类名称看起来规范，但完全不传达测试意图：

**反例（检查项标题，不表达意图）**：
- 撤单校验
- GTC 订单检查
- 部分成交后改单验证

**正例（直接表达要证明的业务事实或要防止的风险）**：
- 终态订单再次撤单必须被拒绝且不能复活旧订单
- GTC 订单跨日后必须保持有效而不能被误清理
- 部分成交后改单数量不能小于已成交数量

区别在于：反例只告诉你"测了什么对象"，正例告诉你"要证明什么事实"。正例即使脱离上下文，评审人也能判断这条 case 的价值和覆盖目标。

这条规则在我们的 skill 中被提升为最高优先级的硬规则——放在所有流程步骤之前。因为用例名称是测试设计质量的第一个可见信号：如果名称都写不清楚，后面的断言和证据大概率也是模糊的。

### 7.3 三质量标准

每条用例在定稿前，必须通过三项质量检查：

**标准一：可执行（Executable）**

测试人员（或 Agent）能独立按步骤执行，不需要额外解释：
- 用例名称必须直接表达测试意图（要证明什么业务事实，或要防止什么业务风险）
- 前置条件必须是可检查的系统状态，不能是模糊描述
- 预期结果必须是可观察的输出，并注明证据类型

反例：`撤单校验` -> 不知道在验证什么业务事实
正例：`终态订单再次撤单必须被拒绝且不能复活旧订单` -> 意图清晰，可直接审核

**标准二：可回归（Regression-ready）**

用例能被自动化或稳定复现：
- 预期结果中的每一项必须可独立断言（映射到一条 assert 语句）
- 用例之间的状态依赖必须在前置条件中显式列出，不能依赖执行顺序

**标准三：可审核（Reviewable）**

需求方和开发能通过阅读用例验证覆盖：
- 用例按业务维度组织，不按技术模块组织
- 需求分析中的每条规则都能追溯到至少一条用例

### 7.4 断言设计：从"有回执"到"证明业务事实"

断言是用例的灵魂。没有断言的用例只是操作步骤。

**弱断言禁止规则**：以下断言只能作为基础断言，不能单独证明复杂测试意图：

- `ordStatus=0`（只证明"有 ack"，不证明业务语义）
- `execType=0`（同上）
- "收到任意回执"
- "没有报错"

**断言设计模板**：

| 测试意图 | 不能只断言 | 必须断言 |
|---------|-----------|---------|
| 新订单类型下单 | ordStatus=0 | 返回订单类型字段、扩展字段 |
| 改单成功 | 收到回执 | execType=5, ordStatus=5, 被修改字段=目标值 |
| 改单拒绝后再改单 | 第二次成功 | 第一次 reject + 原单状态保持 + 第二次基于正确原单成功 |
| 撤单与成交竞态 | 有终态 | 成交优先时：execType=F + cancel reject；撤单优先时：execType=4 |
| 字段透传 | 下单成功 | 北向/服务端/南向证据中目标字段值一致 |
| 过期拒绝 | 有拒绝 | ordStatus=8, execType=8, text 含过期原因, 无南向发送 |

### 7.5 断言字段确认规则

Agent 设计断言时，一个常见错误是"臆想字段"——基于经验或字段名猜测某个字段存在，但实际上该字段在当前系统的北向回执中并不暴露。

**字段确认顺序**：
1. 先查已有自动化 case 和解析能力，确认当前工具能匹配哪些字段
2. 再查协议定义、FIX tag 映射、接口契约，确认字段是否应该出现
3. 在允许的阶段查看服务端代码，确认字段如何生成和透传
4. 若以上都不能确认，必须向人类工程师提出待确认问题

**强制规则**：断言字段不能臆想。字段存在性未确认时，用例状态必须是阻塞，不得用相似字段或历史样例替代。

### 7.6 从用例到自动化 case 的桥接

高质量用例不只是文档，还应该能桥接到自动化执行。我们的方法要求：

1. 每个用例的 Case ID 必须在自动化 case 的 `name` 字段中体现，保证双向追溯
2. 自动化 case 设计前必须先输出断言计划，不能先模仿样例写代码再反推断言
3. 自动化 case 的 `describe` 字段必须压缩写入测试意图和关键断言点
4. 若自动化工具无法证明测试意图，只能标记为工具能力缺口，不能用弱断言冒充覆盖

这个桥接机制确保了：用例设计的质量能传递到自动化执行，而不是在转化过程中被稀释。

### 7.7 我的观点：断言是用例的灵魂

在所有质量问题中，断言弱化是最隐蔽也最危险的。因为弱断言的用例"看起来"是通过的——执行了、有结果了、没报错——但实际上什么都没证明。

Agent 特别容易犯这个错误，因为它的训练数据中大量存在"验证功能正常""确认系统返回正确结果"这类模糊表达。没有显式约束时，Agent 会自然地退化到这种表达方式。

**测试意图驱动**的核心价值就在于：它强制 Agent 在写用例之前先回答"这个 case 要证明什么业务事实"。一旦业务事实被明确，断言就自然变得具体——因为你必须找到能证明这个事实的可观察输出。

## 8. 第五阶段：人机协作与审核闭环

### 8.1 为什么人机协作不是可选项

在需求基线、业务口径和字段确认等环节，人类确认是质量保证的锚点，不能被 Agent 的"自信"替代。

Agent 的一个特点是：它很少说"我不确定"。即使面对信息不足的情况，它也倾向于给出一个看起来合理的答案。在用例设计中，这种"自信"会导致：

- 把假设写成事实
- 把行业通用语义套用到特定系统
- 把字段名相似的字段当作同一个字段
- 把"应该是这样"写成"确认是这样"

因此，人机协作不是"Agent 做完了让人类看一眼"，而是在关键节点设置强制确认点。

### 8.2 强制确认点

| 确认点 | 触发条件 | 确认内容 |
|--------|---------|---------|
| 需求冲突解决 | 跨源甄别发现直接冲突 | 采纳哪个版本 |
| 业务口径确认 | 需求未明确某个行为 | 该行为的预期是什么 |
| 字段存在性确认 | 协议和代码都不能确认 | 该字段是否在回执中暴露 |
| 不可构造输入确认 | 理论 case 当前无法执行 | 是否标记本轮不执行 |
| 新能力语义确认 | 需求引入新 TIF/订单类型 | 具体行为定义 |

### 8.3 审核闭环：草案 -> 审核 -> 修正 -> 沉淀

用例设计的审核不是一次性的"通过/不通过"，而是一个闭环：

1. **Agent 输出草案**：包含信息源、甄别结论、需求分析、覆盖清单、用例和回查
2. **人类审核**：重点审核甄别结论、覆盖完整性、断言有效性和待确认项
3. **Agent 修正**：根据审核意见修正用例，并触发一致性扫描（第 7 阶段）
4. **沉淀**：审核通过的用例进入正式文档；审核过程中确认的业务口径进入领域知识库

### 8.4 审核清单

我们为人类审核者提供了结构化的审核清单：

**基础信息审核**：
- 用例名称是否表达业务场景
- 覆盖关系是否明确
- 自动化边界是否写清

**断言审核**：
- 测试意图是否明确
- 是否存在弱断言冒充覆盖
- 关键状态是否都有断言
- 字段是否已确认存在

**可维护性审核**：
- 用例之间是否有隐式依赖
- 是否可被后续自动化
- 是否可被其他人独立执行

### 8.5 我的观点：人类确认是质量的锚点

在 Agent 辅助测试的讨论中，经常有一种倾向：追求"全自动"——Agent 从需求到用例到执行到报告全部自主完成。但在我们的实践中，完全自主的 Agent 用例设计质量是不可靠的。

原因不是 Agent 能力不足，而是**测试设计中存在不可自动化的判断**：

- "这个行为是 bug 还是 feature？"——需要业务确认
- "这个字段在回执中是否暴露？"——需要实现确认
- "这个边界条件在当前环境下能否构造？"——需要环境确认

这些判断的答案不在任何文档中，只存在于人类工程师的领域知识中。Agent 可以识别出"这里需要确认"，但不能替代确认本身。

因此，高质量的 Agent 用例设计不是"Agent 独立完成"，而是"Agent 高效完成可自动化的部分，并精准识别需要人类确认的部分"。

## 9. 第六阶段：领域知识渐进沉淀

### 9.1 沉淀的动机

Agent 用例设计的质量高度依赖上下文。同一个 Agent，在有丰富领域知识的上下文中设计的用例，质量远高于从零开始的设计。

问题是：对话上下文是临时的。一次对话中积累的领域理解，在下次对话中就消失了。如果不做沉淀，每次用例设计都是从零开始。

### 9.2 需要沉淀的领域知识类型

| 知识类型 | 示例 | 沉淀位置 |
|---------|------|---------|
| 生命周期矩阵 | 订单从下单到终态的所有路径 | 领域 skill references |
| 已知能力基线 | 当前系统支持哪些订单类型、TIF、操作 | 能力基线文档 |
| 动作链模式 | 24 条核心动作链组合 | 领域 skill |
| 覆盖维度清单 | 通用覆盖维度 + 领域特有维度 | 通用 skill |
| 断言模板 | 测试意图到断言的映射 | 断言设计指南 |
| 存量自动化索引 | 已有自动化 case 覆盖了什么 | case catalog |
| 历史缺陷模式 | 过去出现过的典型问题 | 缺陷库 |
| 业务规则字典 | 正常/异常/未知的判定基线 | 行为字典 |

### 9.3 沉淀的触发时机

领域知识沉淀不是一次性工程，而是随项目迭代渐进积累：

- **新需求完成测试后**：若引入了新的业务能力，回填能力基线文档
- **发现覆盖遗漏后**：补充覆盖维度清单或动作链模式
- **发现断言不足后**：补充断言模板
- **发现重复设计后**：补充存量自动化索引
- **发现新缺陷模式后**：补充缺陷库

### 9.4 沉淀的质量控制

沉淀不是"Agent 觉得有用就写进去"。必须经过人类 review：

1. Agent 输出"沉淀候选项"
2. 人类审核是否值得沉淀、沉淀到哪里、措辞是否准确
3. 确认后才正式写入领域知识库

这个控制避免了两个问题：
- 过度沉淀：把临时性的、特定于某次测试的结论写成通用规则
- 错误沉淀：把未经验证的假设写成已确认的业务规则

### 9.5 沉淀与增量过滤的闭环

领域知识沉淀和增量过滤形成正向循环：

```
沉淀越充分 -> 存量覆盖识别越准确 -> 增量过滤越精准
-> 新增用例越聚焦 -> 测试发现越有价值 -> 沉淀越充分
```

这个循环意味着：项目越成熟，Agent 用例设计的质量越高、效率越高。早期投入的沉淀工作，会在后续迭代中持续产生回报。

## 10. 第七阶段：回查与一致性保障

### 10.1 覆盖回查

用例设计完成后，必须做一次覆盖回查：

```
覆盖清单项 -> 对应哪些 Case ID
```

如果某个清单项没有对应用例，必须显式说明：
- 是否被存量回归覆盖（标注回归 case 引用）
- 是否本轮不执行（标注原因）
- 是否确实遗漏（补充用例）

### 10.2 规则变更一致性扫描

在用例设计过程中，需求基线可能被人类审核修正。每次规则变更后，必须扫描以下位置是否存在过时措辞：

1. 信息源甄别结论
2. 需求分析中的业务规则
3. 覆盖清单项措辞
4. 用例名称
5. 预期结果

如果发现不一致，必须修正并标注变更：`规则更新：[旧规则] -> [新规则]`

### 10.3 我的观点：回查是最容易被跳过、也最不应该被跳过的步骤

在实践中，回查是 Agent 最容易跳过的步骤。因为到这一步时，用例已经写完了，Agent（和人类）都有一种"完成感"。但回查恰恰是发现系统性遗漏的最后机会。

我们的经验是：**每次认真做回查，都能发现 1-2 个遗漏的覆盖点。** 这些遗漏通常不是"完全没想到"，而是"在某个维度的某个组合上漏掉了"。


## 11. 案例验证

### 11.1 案例一：EXAMPLE-1001 sample-client fake-clock 用例设计

#### 需求概述

EXAMPLE-1001 的功能变更是：sample-client 新增虚拟墙钟漂移能力，核心公式为 `虚拟当前时间 = 真实当前时间 + drift`，用于判断 DAY 订单是否过期。

#### 七阶段方法的应用

**第一阶段（信息源甄别）**：

识别出三个信息来源：通知邮件、代码变更、用户口头澄清。甄别发现：
- 通知描述了基本公式，但未说明 `DayOrderExpireTime=0` 的行为
- 代码实现了 `0` 表示不过期的逻辑
- 用户确认了普通 sample-client 不应受影响

甄别结论：以代码实现为权威来源，`DayOrderExpireTime=0` 标记为"需求未明确但代码已实现"。

**第二阶段（基线锁定与范围过滤）**：

范围过滤结果：
- 存量回归覆盖：普通订单生命周期（由 `normal_order` 固定回归覆盖）
- 本轮不执行：FC-006（真实已过期输入不可构造）、FC-007/008（DayOrderExpireTime=0 不可模拟）
- 增量用例：fake-clock 特有的 drift 行为验证

**第三阶段（系统化覆盖设计）**：

覆盖清单 13 项（CK-01 到 CK-13），按以下维度系统构建：
- drift 值域：正数、负数、0、非法值、未设置
- 订单入口：用户直接下单、算法单触发到 sample-client
- 二进制类型：fake-clock debug、普通 debug、release
- 过期判断：未到期 ACK、已到期拒绝、边界精度
- 南向行为：过期时不向下游发送

**第四阶段（测试意图驱动的用例与断言）**：

18 个用例，每个都先写测试意图。例如 FC-003：

```
测试意图：验证正漂移使虚拟时间超过 DayOrderExpireTime 时，订单被本地拒绝
要证明的业务事实：drift=120 时，虚拟当前时间 >= DayOrderExpireTime，
                  sample-client 判定 Day order expired
必须断言：ordStatus=8, execType=8, text 含 "Day order expired"
补充证据：event.log 无 TO_VENDOR（证明未向下游发送）
```

**第五阶段（人机协作）**：

关键确认点：
- FC-014 的预期从"直接 reject"修正为"算法单触发后形成终态闭环"
- FC-018 的预期从"合法 env 必须打印日志"修正为"由运行态和订单行为覆盖"
- 确认普通 sample_client_debug 不启用 fake-clock

**第六阶段（沉淀）**：

测试完成后沉淀：
- fake-clock 能力回填到已知能力基线
- 算法单入口的工具选型经验沉淀到实施指南模板

**第七阶段（回查）**：

覆盖回查发现所有 13 个清单项都有对应用例或明确的"本轮不执行"标注。

#### 方法的纠偏效果

| Agent 初期偏差 | 方法如何纠正 |
|--------------|-----------|
| 忽略环境前置 | 第三阶段要求覆盖"二进制类型"维度 |
| 工具选型不充分 | 第三阶段要求区分普通单/算法单入口 |
| 混淆理论/可执行输入 | 第二阶段强制区分并标记 |
| 断言弱化 | 第四阶段要求先写测试意图再写断言 |
| 错误理解算法单预期 | 第五阶段人类确认修正 |

### 11.2 案例二：示例业务系统 订单生命周期用例设计实践

#### 背景

示例业务系统 订单类需求是项目中最复杂的用例设计场景。一个看似简单的"支持新 TIF"需求，实际上需要与完整的订单生命周期状态机做交叉，覆盖数十条动作链组合。

#### 领域 skill 的作用

我们为 示例业务系统 订单用例设计构建了专项 skill（`domain_order_case_design`），它与通用 skill（`test-case-design-checklist`）配合使用：

1. 通用 skill 提供：信息源甄别、跨源冲突解决、覆盖清单构建、回查
2. 领域 skill 提供：生命周期状态机基线、动作链模式库、复杂状态后继续动作矩阵、增量过滤方法

这种"通用 + 领域"的双层 skill 结构，让 Agent 既有通用的方法论框架，又有领域特定的覆盖知识。

#### 动作链覆盖的实际效果

以一个"支持 GTC TIF"的假设需求为例，Agent 在领域 skill 引导下的覆盖设计：

**无领域 skill 时 Agent 的典型输出**：
- GTC 下单成功
- GTC 改单成功
- GTC 撤单成功
- GTC 过期行为（如果有）

**有领域 skill 时 Agent 的输出**：
- GTC place -> ack（冒烟）
- GTC place -> reject（非法参数）
- GTC place -> partial fill -> replace（qty > cumQty）
- GTC place -> partial fill -> replace（qty < cumQty -> 交易所 cancel/reject）
- GTC place -> replace reject -> replace again
- GTC place -> cancel request -> full fill -> cancel reject（竞态）
- GTC place -> recover -> replace -> fill
- GTC 跨日后是否仍活跃（GTC 特有语义）
- GTC 日切后改撤行为
- GTC recovery 后状态保持

覆盖从 4 条扩展到 10+ 条，且每条都有明确的测试意图和断言设计。

#### 增量过滤的实际效果

在有存量自动化索引的情况下，Agent 能识别出：
- `place -> ack`、`place -> reject`、`replace -> replaced`、`cancel -> canceled` 已由 `normal_order` 固定回归覆盖
- 只需新增 GTC 特有语义（跨日活跃、日切行为）和 GTC 与复杂状态的交叉

最终增量用例从"全量 20+ 条"精简为"真正增量 8 条 + 回归执行声明"。

## 12. 与现有方法的对比讨论

### 12.1 与 Prompt-based Test Generation 的对比

当前主流的 Agent 用例生成方法是 prompt-based：给 Agent 一段需求描述和一个提示词模板，让它一次性生成用例。

| 维度 | Prompt-based | 本文方法 |
|------|-------------|---------|
| 生成速度 | 极快（一次性） | 较慢（多阶段） |
| 需求基线 | 隐式（Agent 内部判断） | 显式（甄别文档化） |
| 覆盖系统性 | 依赖提示词质量 | 依赖覆盖框架 |
| 断言质量 | 容易弱化 | 测试意图驱动 |
| 增量能力 | 无（每次全量） | 有（依赖存量索引） |
| 可复核性 | 低（过程不可见） | 高（每阶段有文档） |
| 人机协作 | 事后审核 | 过程中强制确认 |

本文方法的代价是速度——多阶段流程比一次性生成慢。但在真实项目中，用例设计的瓶颈从来不是"写得不够快"，而是"写得不够好导致后续返工"。

### 12.2 与 CodiumAI / TestPilot 等工具的对比

CodiumAI、TestPilot 等工具主要面向单元测试和 API 测试的自动生成，它们的优势在于：
- 能直接从代码生成测试
- 与 IDE 深度集成
- 生成的测试可以直接运行

本文方法与它们的定位不同：
- 本文面向**功能测试**和**集成测试**，不是单元测试
- 本文关注的是**测试设计质量**，不是测试代码生成
- 本文处理的是**多源需求对齐**，不是单一代码文件

两者可以互补：CodiumAI 等工具解决"代码级测试的自动生成"，本文方法解决"业务级测试的设计质量"。

### 12.3 与传统测试设计方法的对比

传统测试设计方法（如等价类划分、边界值分析、状态转换测试）提供了覆盖设计的理论基础。本文方法不是替代这些方法，而是：

1. 把这些方法**编码为 Agent 可执行的约束规则**（如覆盖清单维度、动作链模式）
2. 补充了传统方法不涉及的**Agent 特有问题**（如跨源甄别、增量过滤、断言字段确认）
3. 增加了**人机协作机制**，解决 Agent 无法独立判断的业务口径问题

## 13. 边界与局限

### 13.1 方法的适用条件

本方法最适合以下场景：
- 功能测试和集成测试（非单元测试）
- 业务逻辑复杂、状态空间大的系统
- 有多个信息来源需要对齐的需求
- 需要长期维护和迭代的测试资产

对于以下场景，本方法可能过重：
- 输入输出明确、无歧义的简单功能
- 一次性验证、不需要回归的场景
- 纯 UI 测试或纯性能测试

### 13.2 对领域知识沉淀的依赖

本方法的增量过滤和系统化覆盖高度依赖领域知识的积累。在项目早期，领域知识库为空时，Agent 的用例设计质量主要依赖通用 skill 和人类审核。随着项目迭代，领域知识逐渐积累，Agent 的设计质量才会持续提升。

这意味着：**本方法的投资回报是长期的，不是即时的。** 团队需要接受早期的沉淀成本。

### 13.3 人类确认的成本

强制确认点增加了人类工程师的参与成本。在实践中，我们发现：
- 大部分确认可以在 5 分钟内完成
- 关键确认（如业务口径）可能需要跨团队沟通
- 确认的价值远大于成本——一次确认避免了后续大量返工

### 13.4 不能保证 Agent 永远正确

即使有七阶段约束，Agent 仍可能在具体用例的措辞、断言的精确性或覆盖的完整性上犯错。本方法提升的是**系统性质量**和**可复核性**，不是消除所有错误。

关键区别在于：有约束时，错误是可发现、可定位、可修正的；无约束时，错误可能隐藏在"看起来正确"的输出中。

## 14. 结论

### 14.1 核心发现

通过在真实某业务系统测试项目中的实践，我们发现：

1. **Agent 用例设计的质量瓶颈不是生成能力，而是工程约束。** Agent 能快速生成格式正确的用例，但缺少约束时，这些用例在需求基线、覆盖系统性、断言有效性和可追溯性上普遍存在问题。

2. **结构化的多阶段约束能显著提升用例质量。** 通过信息源甄别、范围过滤、系统化覆盖、测试意图驱动断言和人机协作审核，Agent 的用例设计从"快速但不可靠"转变为"系统且可信赖"。

3. **领域知识沉淀是质量持续提升的关键。** 生命周期矩阵、动作链模式、已知能力基线和存量自动化索引，为 Agent 提供了增量设计的基础。项目越成熟，Agent 的设计质量越高。

4. **人机协作是不可替代的质量锚点。** 在需求基线、业务口径和字段确认等环节，人类确认是防止 Agent "自信地犯错"的最后防线。

### 14.2 方法论总结

本文提出的七阶段结构化约束方法，本质上是把测试用例设计从"一次性生成"转变为"分阶段收敛"：

- 第一阶段解决"基线从哪来"
- 第二阶段解决"范围是什么"
- 第三阶段解决"覆盖什么"
- 第四阶段解决"怎么证明"
- 第五阶段解决"谁来确认"
- 第六阶段解决"知识怎么积累"
- 第七阶段解决"有没有遗漏"

每个阶段都在收敛不确定性。七个阶段叠加后，Agent 的输出从"不确定的文本生成"变成了"可控的工程设计"。

### 14.3 对行业的启示

我们的实践表明，Agent 辅助测试用例设计的正确方向不是追求"更强的模型"或"更长的提示词"，而是：

1. **建立结构化的约束流程**，让 Agent 的行为可控、可复核
2. **投资领域知识沉淀**，让 Agent 的质量随项目成熟度提升
3. **设计合理的人机协作边界**，让人类和 Agent 各做擅长的事
4. **关注断言质量而非用例数量**，因为没有断言的用例只是操作步骤

最终，高质量的 Agent 用例设计不是 Agent 独立完成的产物，而是**结构化约束 + 领域知识 + 人机协作**三者共同作用的结果。

| 1 | 跨源甄别是否完成 | 冲突项有解决结论或 PENDING HUMAN |
| 2 | 需求基线是否锁定 | 有明确的采纳依据 |
| 2 | 范围过滤是否完成 | 存量/不可执行/外部边界已标注 |
| 3 | 覆盖清单是否按维度构建 | 不适用的维度显式标注 |
| 3 | 动作链组合是否检查 | 适用的动作链有对应用例 |
| 4 | 每条用例是否有测试意图 | 意图明确且可验证 |
| 4 | 用例名称是否直接表达测试意图 | 非"XX校验/检查"式标题 |
| 4 | 断言是否通过弱断言检查 | 无 ordStatus=0 冒充覆盖 |
| 4 | 三质量标准是否通过 | 可执行、可回归、可审核 |
| 5 | 待确认项是否已确认 | PENDING HUMAN 已解决或显式保留 |
| 6 | 新能力是否标注沉淀 | 有沉淀候选项 |
| 7 | 覆盖回查是否完成 | 每个清单项有对应用例或说明 |

## 附录 B：关键术语表

| 术语 | 定义 |
|------|------|
| 跨源甄别 | 对多个信息来源进行比对，识别冲突、歧义和术语漂移的过程 |
| 需求基线 | 经过甄别和确认后，作为用例设计依据的需求事实集合 |
| 范围过滤 | 从理论覆盖中排除存量行为、外部边界、回归管理和不可构造输入 |
| 增量过滤 | 识别存量自动化已覆盖的点，只设计真正需要新增的用例 |
| 测试意图 | 一条用例要证明的具体业务事实 |
| 弱断言 | 只能证明"有响应"但不能证明业务语义正确的断言 |
| 三质量标准 | 可执行、可回归、可审核——每条用例必须满足的三项质量要求 |
| 动作链 | 订单从创建到终态经历的操作序列 |
| 领域知识沉淀 | 将项目中积累的业务规则、覆盖模式和历史经验固化为可复用资产 |
| 覆盖回查 | 用例设计完成后，验证每个覆盖清单项都有对应用例的检查过程 |
