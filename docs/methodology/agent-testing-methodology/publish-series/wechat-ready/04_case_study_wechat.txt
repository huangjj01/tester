案例一：某业务网关虚拟时钟漂移功能测试

某某业务系统的交易网关组件新增了虚拟墙钟漂移能力，用于联调和仿真测试中验证“日内订单过期时间”逻辑。

核心公式是：

虚拟当前时间 = 真实当前时间 + VIRTUAL_CLOCK_DRIFT_SEC

过期判断为：

DayOrderExpireTime 不等于 0，并且虚拟当前时间大于等于 DayOrderExpireTime，则触发过期拒单。

正 drift 让订单更早过期，负 drift 延后过期，DayOrderExpireTime=0 表示不过期。该能力只在特定 fake-clock 构建中生效，普通构建不受影响。

这个需求为什么难测

难点不在于“下一个单看看结果”，而在于测试前提和证据链。

第一，环境前置不是附属动作。

fake-clock 能力依赖特定二进制、启动时环境变量注入、通过进程守护服务的启动命令生效，并且修改后必须重启守护服务，验证 PID 变化。

第二，DayOrderExpireTime 不能任意构造。

它由上游服务根据交易日历计算后下发，测试脚本无法手工传入。

第三，普通单和算法单入口不同。

普通单可以由自动化框架直接下单。算法单需要先下算法单，再通过模拟行情触发，最后由算法引擎送单到网关。

第四，背景流量会污染证据。

稳定性脚本持续下单，订单不可控，证据无法精确归因到具体 case。

Agent 初期偏差

第一个偏差是忽略环境前置。

Agent 一开始关注下单逻辑，没有第一时间确认二进制和 env。即使结果符合预期，也无法证明是 fake-clock 行为。

第二个偏差是工具选型不充分。

它倾向观察稳定性脚本的订单，但这些订单标识不可控，证据无法归因到具体 case。

第三个偏差是混淆工具前提。

它把不同入口的前置条件混在一起，测试准备复杂化，出错概率也随之上升。

第四个偏差是执行记录滞后。

不是所有 case 一开始都按模板补齐，报告阶段容易补写推断而非事实。

第五个偏差是错误理解算法单预期。

初期按“直接拒绝”理解，忽略算法单需要闭环终态。

这些偏差并不是简单的能力问题。缺少工程约束时，Agent 的行为路径本来就难以预测。

方法论如何介入

用例设计阶段，对需求通知、代码变更和用户澄清进行对齐，形成 18 个 case 和覆盖清单。

关键决策是区分理论输入与当前可执行输入。

例如，DayOrderExpireTime=0 表示不过期，理论上应该测。但当前环境下上游服务不会下发 0，无法构造，因此标记为“本轮不执行”，不能写成通过或失败。

再如，真实已过期订单需要等到真实过期时间点，当前窗口不可控，也应标记为“本轮不执行”。

测试实施设计阶段，先解决环境和工具，而不是直接下单。

普通未过期 ACK 和普通过期拒单，使用自动化框架独立 type，保证输入可归因、断言可执行。

算法单入口使用自动化框架加行情模拟，因为需要触发行情，让算法引擎送单。

背景稳定性流量明确不采用，因为订单不可控，证据不可精确归因。

执行证据层，每个 case 保存订单标识、内部标识、过期时间下发值、回包断言、状态迁移日志和南向无发送证据。

层间反馈也很关键。某个算法单 case 实际是“过期撤单闭环”，而不是“直接新单拒绝”。这个发现反馈到判断基线层，修正了 case 预期。

执行结果

通过：12 个 case。覆盖 drift=0、正漂移、非法 env、未设置 env、算法单入口、普通构建回归。

部分覆盖：1 个 case。负漂移只覆盖“不误拒正常未到期订单”。

需复测：1 个 case。已验证超过边界会过期，但未达严格边界精度。

本轮不执行：4 个 case。输入当前不可构造，或已由 UAT 人工完成。

案例结论

复杂功能测试中，Agent 的可靠性来自持续纠偏：每一层约束都在把它拉回可验证、可复核、可交付的轨道。

案例二：Runner 自身的 43 条用例测试

Runner 自身的功能测试，是方法论的一次自举验证：用方法论约束的流程，测试方法论的实现工具。

门禁的真实拦截记录

Runner 实际拦截过这些问题：

缺失标题。

标题无内容。

依赖未满足。

表格全占位符。

产物文件不存在。

每次拦截都迫使 Agent 回去补全内容，而不是带着空壳继续推进。

中断恢复验证

步骤被阻塞后，Agent 通过 next 命令获取当前步骤、产物路径和阻塞原因。

修正产物后重新提交，通过校验，流程再继续推进。

幂等性验证

第一次 complete 某个步骤时，Runner 正常标记完成。

重复 complete 同一个步骤时，Runner 返回 already completed，不修改完成时间，不推进指针，不影响后续步骤。

发现的 2 个缺陷

第一个缺陷是 run_id 同秒冲突。连续快速创建同名需求时，run_id 可能重复。修复方式是加入微秒级精度。

第二个缺陷是重复 step id 未拒绝。配置中有重复 step id 时，Runner 未报错。修复方式是增加唯一性校验。

两个缺陷在同一天内完成修复和复测验证。

完整 happy path 验证

full 目标模式下，8 步全部通过门禁校验，validate 返回 target achieved。

最终结果

设计用例 43 条。

首轮通过 41 条。

首轮失败 2 条。

修复后复测通过 2 条。

最终通过率 100%。

产生 run 实例 20 个。

门禁实际拦截多次。

两个案例的对比

虚拟时钟漂移测试的测试对象是业务功能，环境复杂度高，涉及远端环境和守护服务。它验证了分层约束对 Agent 初期偏差的纠偏效果。

Runner 自身测试的测试对象是工具软件，环境复杂度较低，主要运行在本地 Python 环境。它验证了门禁系统的技术保障能力，并发现了 2 个工具自身缺陷。

案例一验证了分层约束对 Agent 行为的纠偏效果；案例二验证了门禁系统的技术保障能力。

案例结论

Agent 的可靠性不来自单次回答的正确性，而来自分层约束对其行为的持续收敛。

任务路由让 Agent 先意识到环境前置。

用例设计澄清了理论输入与可执行输入。

实施设计补齐了二进制、env、守护服务、PID 和工具选型。

执行证据层保存了真实日志和标识。

判断基线使不可构造输入不被误写成失败或通过。

门禁系统在 Agent 跳步时实时阻止。

要点总结

真实案例中，Agent 的初期偏差是常态，需要被流程识别和纠正。

方法论的价值在于持续纠偏，而不是追求一次性正确。

“本轮不执行”是诚实的测试状态，不能被误写成通过或失败。

门禁拦截不是形式动作，它能阻止空壳产物进入后续流程。

Runner 自测说明：方法论不仅能约束业务测试，也能反向发现工具自身缺陷。
