# 从用例设计到执行报告：一种可落地的 Agent 测试工程方法论

## 摘要

Agent 已经能够辅助测试用例设计、脚本执行、日志检索和结果摘要，但真实功能测试交付并不止于生成用例。缺少工程化约束时，Agent 容易跳过环境前置、误用工具、遗漏证据或将推断写成结论。本文提出"分层约束的 Agent 测试工程闭环"，用任务路由、需求与用例、测试实施设计、执行证据、判断基线、交付与沉淀六层机制，将 Agent 的不确定性响应转化为可执行、可复核、可交接、可沉淀的测试交付过程。进一步地，本文设计并实现了 Test Agent Workflow Runner——一个配置化的流程门禁控制系统，将六层约束中的关键步骤固化为可校验的步骤序列，通过依赖校验、产物内容校验和状态持久化，在 Agent 跳过关键环节时实时阻止流程推进。通过 EXAMPLE-1001 sample-client fake-clock 案例和 Runner 自身的 43 条测试用例执行实践，本文展示该方法如何收敛 Agent 在二进制切换、env 注入、工具选型和执行记录中的偏差，并形成可复核测试结果。

## 关键词

Agent 测试；功能测试；测试实施设计；工具选型；证据链；测试报告；分层约束；流程门禁；配置化工作流；中断恢复

## 1. 引言

大模型 Agent 已经能够参与软件测试中的多类任务，例如阅读需求、生成测试用例、执行命令、检索日志和总结结果。在理想化场景中，Agent 看似能够快速完成从需求到测试结论的工作。但在真实功能测试中，测试交付不是单步生成行为，而是一组跨环境、跨工具、跨证据层和跨业务判断的工程活动。

这带来一个核心矛盾：

```
会写测试用例 ≠ 能交付测试结果
```

测试用例只回答"应该验证什么"。测试交付还要回答任务路径、环境前提、工具选择、证据归因、异常解释和报告口径。若这些问题没有被显式约束，Agent 的表现会高度依赖上下文记忆和临场判断：它可能在某一步给出合理答案，却在后续执行中跳过关键前置；也可能完成了命令执行，却没有留下可复核证据；还可能把当前无法证明的推断写成正式测试结论。

本文所说的"不确定性"，不是指模型输出随机性本身，而是指 Agent 在缺少显式工程约束时，其任务路径选择、信息获取范围、执行动作和结论形成过程的不可预测性。同一个测试请求，在不同上下文中可能被 Agent 解释为下单执行、日志调查、部署验证或报告整理，并产生质量差异很大的结果。

因此，本文关注的问题不是"Agent 是否能参与测试"，而是：

```
如何把 Agent 组织进一套可执行、可复核、可交接、可沉淀的测试工程闭环？
```

本文的主论点是：面向真实功能测试的 Agent 能力建设，关键不在于让 Agent 一次性给出正确答案，而在于通过分层约束的测试工程闭环，将 Agent 的不确定性响应转化为可执行、可复核、可交接、可沉淀的测试交付过程。

更进一步，本文认为仅靠文档规则约束（如规则文件、技能文档）不足以保证 Agent 遵守流程——Agent 可能因上下文压缩、任务切换或临场判断而跳过关键步骤。因此，本文设计并实现了一个配置化的流程门禁控制系统（Test Agent Workflow Runner），将分层约束模型中的关键步骤固化为可执行的校验机制，在校验未通过时实时阻止流程推进。

本文的贡献包括四点：

1. 提出分层约束模型，用任务路由、实施设计、执行证据、判断基线和交付沉淀约束 Agent 测试行为。
2. 定义从用例到报告的测试交付闭环，将 Agent 测试从 test case generation 扩展到实施设计、工具选型、执行记录、覆盖矩阵和测试报告。
3. 设计并实现 Test Agent Workflow Runner，将分层约束从文档规则升级为可执行的门禁校验机制，支持配置化步骤定义、产物内容校验、状态持久化和跨会话中断恢复。
4. 通过两个完整案例（EXAMPLE-1001 功能测试和 Runner 自身测试）验证方法论的落地效果。

## 2. 相关实践与本文定位

当前 Agent 辅助测试实践大致可以分为三类。

**第一类是 prompt-based test generation**，即根据需求、接口说明或代码生成测试用例。代表性实践包括 CodiumAI、TestPilot 以及各类 IDE 内置的测试生成能力。这类实践提升了用例草拟效率，但通常停留在"应该测什么"，对环境前置、工具选择、执行证据和报告交付关注不足。由此留下的开放问题是：生成出来的用例如何落地为可执行、可归因、可交接的测试交付。

**第二类是 agentic execution**，即 Agent 按 ReAct 或类似模式调用命令、浏览器、日志检索和自动化脚本完成操作。SWE-agent、OpenHands 等项目体现了这类方向：Agent 能围绕 issue 或任务执行多步操作。这类实践增强了执行能力，但若缺少任务路由和证据模板，Agent 仍可能在错误流程中执行正确命令。由此留下的开放问题是：执行能力如何被组织进正确的任务流程，而不是在错误流程中高效地产生不可复核结果。

**第三类是更完整的软件工程 Agent 或 CI/DevOps Agent**，例如 GitHub Copilot Workspace、Devin 以及围绕 CI 失败分析的自动化助手。这类实践更接近工程现场，但主要围绕已有 issue、流水线和失败信号，较少讨论从测试用例设计到测试执行报告的完整交付链路。由此留下的开放问题是：当任务不是修复一个已知失败，而是交付一次功能测试时，测试设计、测试实施、证据采集和测试报告如何被统一管理。

本文与上述实践的区别在于：本文不把 Agent 测试限定为"生成测试用例"或"自动执行脚本"，而是关注真实功能测试交付的工程组织方式。本文提出的分层约束闭环，将任务路由、测试实施设计、工具选型、执行记录、判断基线和报告沉淀纳入同一个方法论框架，并通过可执行的门禁系统将约束从文档层面升级为技术保障。

## 3. Agent 测试落地的工程断点

Agent 在测试任务中的不确定性，通常不是因为它完全不理解需求，而是因为真实测试中存在多个需要工程约束的断点。

| 工程断点 | 常见表现 | 直接后果 |
| --- | --- | --- |
| 任务入口不稳 | 用户要求测试，Agent 直接进入下单或查日志 | 后续动作可能服务于错误目标 |
| 需求基线不稳 | 未甄别通知、代码、分支、用户澄清之间的差异 | 用例预期错误或覆盖遗漏 |
| 环境前置缺失 | 未确认包、二进制、配置、env、启动参数和重启方式 | case 结果无法证明目标功能 |
| 工具选型缺失 | 用背景流量观察替代定向验证，或用普通单工具测试算法单入口 | 输入不可控，证据不可归因 |
| 断言缺失 | 只执行动作，不定义通过标准 | 无法判断通过、失败或需复测 |
| 证据链不闭合 | 只看单层日志或单个报告 | 结论缺少复核基础 |
| 异常识别不足 | 只核对预期断言，不检查额外拒单、状态不自洽、时间边界和未知现象 | 隐蔽问题被漏掉或误报 |
| 执行记录缺失 | 测试结果停留在聊天窗口 | 后续无法交接和复查 |
| 报告失真 | 把推断写成结论，隐藏部分覆盖或阻塞项 | 团队同步被误导 |

这些断点说明，仅仅增加提示词或补充一个 skill 并不足以解决问题。Agent 测试交付需要一套分层机制：先约束任务入口，再约束用例设计，然后约束实施设计、执行证据、结果判断和报告输出。

更关键的是，即使这些约束被写成文档规则，Agent 仍可能因为以下原因跳过它们：

- **上下文压缩**：长对话中早期规则被压缩或遗忘。
- **任务切换**：从一个任务切换到另一个任务时，前置约束被忽略。
- **临场判断**：Agent 认为某个步骤"不需要"而自行跳过。
- **会话中断**：跨会话时无法恢复到中断前的执行进度。

这些问题说明，文档约束需要被升级为可执行的技术保障——这正是本文设计 Test Agent Workflow Runner 的动机。

## 4. 分层约束的 Agent 测试工程闭环

### 4.1 六层模型概述

本文提出"分层约束的 Agent 测试工程闭环"。该闭环不是简单的线性步骤，而是六层互相配合的约束关系。

```
Workflow 任务路由
  → 测试用例设计
  → 测试实施设计
      → 实施规划
      → 工具选型
      → 环境准备
      → 逐 case runbook
  → 测试执行与证据采集
  → 执行记录
  → 覆盖矩阵
  → 测试报告
  → 反思沉淀
```

六层模型如下：

| 层次 | 控制的不确定性 | 主要资产 | 典型输出 |
| --- | --- | --- | --- |
| 任务路由层 | 用户请求进入错误流程 | workflows | workflow 命中结果、主流程、子流程 |
| 需求与用例层 | 需求基线错误、覆盖遗漏 | 用例设计 skill、用例模板 | 需求分析、覆盖清单、测试用例 |
| 测试实施设计层 | 环境误用、工具误用、执行不可落地 | 实施指南 skill、实施模板 | 环境前置、工具选型、逐 case runbook |
| 执行证据层 | 执行事实丢失、证据不可归因 | 执行记录模板、日志层规范 | case 状态、关键标识、证据路径 |
| 判断基线层 | 把未知写成结论、误报或漏报异常 | 业务字典、缺陷库、三分法 | 正常/异常/未知列表 |
| 交付与沉淀层 | 报告失真、经验散落 | 报告模板、覆盖矩阵、反思机制 | 测试报告、候选规则/skill/字典 |

这六层并非任意拆分。它们分别对应功能测试交付中的六类断裂点：入口、需求、实施、事实、判断和交付。若缺少任务路由层，Agent 可能在错误流程中执行正确命令；若缺少需求与用例层，执行会建立在错误预期上；若缺少测试实施设计层，环境和工具错误会使 case 失效；若缺少执行证据层，结果无法复核；若缺少判断基线层，正常、异常和未知会被混淆；若缺少交付与沉淀层，测试经验会重新散落回聊天上下文。

### 4.2 任务路由层

当 Agent 拥有多个 skill、脚本和文档入口时，第一个问题不是如何执行，而是当前应该先进入哪条流程。真实测试任务可能是功能测试实施、失败排查、部署验证、远端 SSH 调查、日切检查、auto_case 执行、稳定性测试生命周期管理等。不同任务需要读取不同 skill、脚本、证据层和输出模板。

如果没有任务路由，Agent 可能拥有多个 skill，却不知道当前应该先使用哪一个。项目级 workflow catalog 将用户请求映射到主 workflow，并声明子流程、必读文档和输出结构。未命中 workflow 时，该机制要求 Agent 显式说明未命中，而不是临时拼接流程。

这一层控制的是入口不确定性。

### 4.3 需求与用例层

测试用例的质量首先取决于需求基线的准确性。需求与用例层关注的是"应该测什么"：该层要求 Agent 不只依据单一通知或单段需求生成 case，而是先列出信息源，进行跨源甄别，再形成需求分析、覆盖清单、test point 和具体 case。

这一层强调三件事：

- 需求、代码、通知和用户澄清必须对齐。
- 理论覆盖和当前可执行范围必须区分。
- 每个 case 都要能回到覆盖清单。

这一层控制的是需求基线和覆盖不确定性。

### 4.4 测试实施设计层

Agent 在实施阶段最容易犯的错误之一，是把 case 当成可以立即执行的命令，而没有先确认环境、工具和证据条件。测试实施设计层的作用，是把 case 转化为可执行 runbook。它包含实施规划、工具选型、环境准备和逐 case 步骤。

测试实施设计至少要回答：

- 当前测试是否依赖特定包、二进制、配置、env、feature flag 或 mock 能力。
- 修改配置后如何证明运行态已经生效。
- 是否需要停止背景流量，避免证据污染。
- 每个 case 应使用现有工具、新增自动化 case、脚本、SQL、fixture、mock 还是人工复核。
- 工具是否具备断言能力和证据归因能力。
- 测试结束后如何恢复环境。

**工具选型**是测试实施设计的一部分，不是测试实施之外的独立阶段。之所以单独强调，是因为它经常被 Agent 隐含在"执行 case"里。工具选型维度包括：

| 维度 | 判断问题 | 影响 |
| --- | --- | --- |
| 输入控制 | 是否需要精确构造输入？ | 决定用定向工具还是批量工具 |
| 断言能力 | 工具是否支持自动断言？ | 决定是否需要补断言 |
| 证据归因 | 是否会混入背景流量？ | 决定结果是否可归因 |
| mock 能力 | 是否需要模拟外部事件？ | 决定是否需要 mock 服务 |
| 环境影响 | 是否会影响其它测试？ | 决定是否需要隔离 |
| 可重复性 | 是否能稳定复现？ | 决定是否适合回归 |
| 开发成本 | 是否值得新增工具？ | 决定是否临时人工复核 |

这一层控制的是环境和工具不确定性。

### 4.5 执行证据层

执行证据层解决的是"实际发生了什么"的问题。该层要求执行过程不只保留聊天摘要，还要记录 case ID、输入、运行态、关键标识、实际输出、断言结果和证据路径。

证据类型包括：

- 标识类：clOrdID、OrderId、trace ID、request ID。
- 日志类：应用日志、event.log、FIX、systemd journal。
- 报告类：自动化报告、CSV、HTML report。
- 运行态：进程命令、PID、配置、版本。
- 外部层：下游原始报文、mock 服务记录、监控指标。

这一层控制的是事实和归因不确定性。

### 4.6 判断基线层

测试产出并不自动等于测试结论。判断基线层关注的是，在面对日志、报告、状态差异和历史反例时，如何形成可复核的解释。通过业务字典、已知缺陷库、历史反例和跨层证据检查，测试产出被区分为正常、异常和未知。

三分法如下：

| 分类 | 判定口径 | Agent 输出要求 |
| --- | --- | --- |
| 正常情况 | 命中业务字典，证据链自洽 | 写入正常情况列表，说明证据 |
| 异常情况 | 命中异常字典、历史反例，或跨层证据不自洽 | 写入疑似/确认问题列表，继续补证据 |
| 未知情况 | 字典外现象、证据不足、业务口径未确认 | 标记待确认，不得写成正常或异常结论 |

这一层控制的是结论定性不确定性。

### 4.7 交付与沉淀层

测试结果只有写成可交接的记录和报告，才算完成工程交付。该层要求测试报告从执行记录和覆盖矩阵提炼，避免新增执行记录里没有的结论。部分覆盖、需复测、本轮不执行和阻塞项需要显式写出。

测试结束后，Agent 还应形成测试工程反思候选，包括规则缺口、workflow 缺口、skill/流程缺口、模板缺口、工具缺口和字典缺口。这些候选项经人工 review 后，才能进入长期知识库或技能体系。

这一层控制的是报告和经验沉淀不确定性。

### 4.8 人机协作边界

分层约束并不意味着所有环节都由 Agent 自主完成。更合理的协作方式是按风险分配责任：

| 环节 | Agent 可自主完成 | Agent 应提交人类确认 | 人类必须主导 |
| --- | --- | --- | --- |
| 任务路由 | 根据 workflow catalog 匹配主流程和子流程 | workflow 未命中或多 workflow 冲突 | 新增长期 workflow 口径 |
| 需求与用例 | 列信息源、做 coverage checklist、生成 case 草案 | 需求冲突、不可构造输入、验收口径不明 | 最终业务验收标准 |
| 测试实施设计 | 梳理环境前置、工具选型、runbook 和恢复步骤 | 高风险环境变更、缺少工具能力 | 生产级变更授权 |
| 执行证据 | 执行命令、采集日志、整理关键标识和证据路径 | 证据链缺层、结果互相矛盾 | 高风险结论定责 |
| 判断基线 | 按字典、缺陷库和三分法做初步分类 | 字典外现象、业务口径未确认 | 新业务规则确认 |
| 交付沉淀 | 生成执行记录、覆盖矩阵、报告草稿和反思候选 | 是否沉淀为 rule/skill/dictionary | 长期规则和团队流程变更 |

人机边界不是静态的，它随工程资产成熟度变化。workflow 命中率越高、业务字典覆盖越充分、模板和执行记录校验越完善，Agent 可自主完成的范围就越大。

## 5. 工程资产协同与维护

分层约束模型需要由真实工程资产承载。本节说明资产之间如何协同，以及如何避免规则、skill、模板和记录彼此漂移。

| 资产类型 | 职责 | 示例 |
| --- | --- | --- |
| rules | 放红线、强约束和强制入口 | 全局团队标准规则 |
| workflows | 放任务路由、主流程、子流程和输出结构 | AI 工作流目录 |
| skills | 放可复用流程和场景化操作方法 | 测试用例设计 checklist、测试实施文档 skill |
| dictionaries / defect libraries | 放业务判断基线和历史反例 | 日切行为字典、已知缺陷库 |
| templates | 放交付物结构 | 实施指南模板、执行记录模板、报告模板 |
| execution records | 放真实执行事实和证据 | 测试执行记录 |

六类资产的关系可以概括为：

```
rules 放红线，
workflows 放路由，
skills 放步骤，
dictionaries 放判断基线，
templates 放结构，
records 放事实。
```

资产之间存在明确依赖关系：

| Source | Target | 依赖关系 |
| --- | --- | --- |
| rules | workflows / skills | 规定红线和强制入口，限制哪些动作必须进入正式流程 |
| workflows | skills / docs / scripts | 根据任务类型选择主流程，并指向需要读取或执行的资产 |
| skills | templates | 描述具体可复用步骤，并引用模板形成交付物 |
| templates | execution records / reports | 约束执行记录和报告的结构 |
| dictionaries | 结论判断 | 为正常、异常、未知提供判定基线 |
| execution records | rules / workflows / skills / templates / dictionaries | 保存真实执行事实，并反向暴露资产缺口 |

维护策略：长期规则只承载红线和强制入口；workflow 负责路由和编排，不替代 skill；skill 负责可复用步骤，不记录单次执行事实；template 固化输出结构，不替代证据；execution record 只保存真实发生的过程。若某次执行暴露流程缺口，应先进入反思候选，再由人类 review 后决定沉淀到哪类资产。

## 6. Test Agent Workflow Runner：从文档约束到可执行门禁

### 6.1 设计动机

前文提出的六层约束模型，在早期实践中主要通过规则文件（AGENTS.md）、技能文档（skills）和模板（templates）承载。这些文档能告诉 Agent 应该怎么做，但仍然主要依赖 Agent 自觉遵守。实际执行中，Agent 仍可能跳过环境前置、工具选型、执行记录或测试工程反思等关键环节。

具体而言，文档约束面临四个技术问题：

**第一，流程跳步问题。** Agent 在执行测试实施任务时，可能直接从用例跳到下单执行，跳过环境前置确认和工具选型。现有的文档规则约束仅依赖 Agent 自觉遵守，缺少可执行的阻止机制。

**第二，上下文丢失问题。** Agent 的对话上下文存在长度限制和压缩机制，当测试实施任务跨越多个会话或被中断时，Agent 无法可靠地恢复到中断前的执行进度。

**第三，产物质量不可控问题。** Agent 生成的测试实施产物可能存在关键内容缺失，例如标题存在但下方无实质内容，或表格存在但全部为占位符数据。

**第四，流程灵活性不足问题。** 不同测试任务需要完成的步骤范围不同。只需要生成测试实施指南时不需要执行记录和报告步骤，但现有约束缺少按需裁剪的能力。

因此，需要一个轻量级的流程门禁系统，把测试实施 workflow 从"文档约束"升级为"可执行、可检查、可恢复"的本地流程保护。

### 6.2 系统架构

Test Agent Workflow Runner 采用三层架构：

```
交互接口层（CLI）
  ├── start    创建工作流运行实例
  ├── status   查看运行状态
  ├── next     查看下一步
  ├── complete 步骤完成与门禁校验
  ├── validate 全局校验
  └── render   合并输出

核心逻辑层
  ├── 工作流配置模块    加载和解析 YAML 配置
  ├── 状态管理模块      创建实例、维护状态、持久化
  ├── 目标产物模式模块  按需裁剪必经步骤
  ├── 门禁校验模块      依赖校验 + 存在性校验 + 内容校验
  └── 中断恢复模块      从持久化状态恢复进度

存储层
  ├── config/test_agent_workflows/*.yaml  配置文件
  ├── .runs/<workflow>/<run_id>/run.json  运行状态
  ├── .runs/<workflow>/<run_id>/checklist.json  步骤状态
  └── .runs/<workflow>/<run_id>/artifacts/*.md  步骤产物
```

### 6.3 工作流配置

工作流通过声明式 YAML 配置定义，包含步骤序列、依赖关系、门禁校验规则和目标产物映射。以测试实施工作流为例：

```yaml
id: test_execution
name: 测试实施 Workflow

targets:
  execution_guide: execution_guide    # 只到实施指南
  execution_record: execution_record  # 到执行记录
  report: report                      # 到最终报告
  full: reflection                    # 完整闭环

steps:
  - id: input_sources
    name: 输入资料确认
    output: artifacts/01_input_sources.md
    required_headings:
      - 输入资料
      - 已确认项
      - 待确认项

  - id: scope
    name: 测试范围与执行口径
    depends_on: [input_sources]
    output: artifacts/02_scope.md
    required_headings:
      - 本轮测试范围
      - 不测范围
      - 部分覆盖项
      - 待确认项

  - id: environment_precheck
    name: 环境前置判断
    depends_on: [scope]
    output: artifacts/03_environment_precheck.md
    required_headings:
      - 目标环境
      - 版本 / 包 / 分支
      - 服务 / 进程 / 配置
      - 启动参数 / 环境变量
      - mock / 外部依赖
      - 恢复基线

  - id: tool_selection
    name: 测试工具选型
    depends_on: [environment_precheck]
    output: artifacts/04_tool_selection.md
    required_table_columns:
      - Case / 场景
      - 现有工具是否覆盖
      - 选用工具
      - 是否需要新增 case / 脚本
      - 断言方式
      - 选择理由
      - 缺口 / 风险
  # ... 后续步骤省略
```

配置加载时自动执行合法性校验：步骤标识唯一性、依赖步骤存在性、目标终点步骤存在性。任一校验失败则拒绝创建运行实例。

### 6.4 门禁校验机制

门禁校验按三层依次执行，任一层失败即阻止推进：

**第一层：依赖校验。** 检查当前步骤的所有前置依赖步骤是否均已完成。例如，`execution_guide` 依赖 `tool_selection`，若工具选型未完成，则实施指南步骤无法通过依赖校验。

**第二层：产物存在性校验。** 检查当前步骤配置的产物输出路径对应的文件是否存在。

**第三层：产物内容校验。** 根据步骤配置的校验规则类型执行对应校验：

- **标题校验**：解析 Markdown 文件中的标题，检查必需标题是否存在，且每个标题下方到下一个标题之间存在至少一行非空白正文内容。
- **表格有效数据校验**：解析 Markdown 表格，检查表头是否包含所有必需列，并检查数据行中是否存在至少一行非占位符的有效数据。占位符判定规则包括：空值、尖括号包围的模板文本（如 `<待填写>`）、不区分大小写的 `TBD`、`待补充`。

校验结果通过退出码传达：0 表示通过，1 表示错误（参数无效、依赖未满足），2 表示校验失败（步骤被阻塞）。

### 6.5 目标产物模式

不同测试任务需要完成的步骤范围不同。Runner 通过目标产物模式支持按需裁剪：

| 目标模式 | 必经步骤 | 典型场景 |
| --- | --- | --- |
| execution_guide | 步骤 1~5 | 只整理测试实施指南 |
| execution_record | 步骤 1~6 | 生成执行记录 |
| report | 步骤 1~7 | 生成最终报告 |
| full | 全部 8 步 | 完整测试实施闭环 |

创建运行实例时，系统根据目标产物类型确定终点步骤，将首个步骤到终点步骤之间的步骤标记为必经，将终点步骤之后的步骤标记为"当前目标不要求"。当所有必经步骤完成后，系统判定目标已达成。

### 6.6 状态持久化与中断恢复

所有运行状态持久化至本地 JSON 文件，不依赖 Agent 的对话上下文。状态文件包括：

**run.json**（运行状态）：记录运行标识、工作流类型、任务名称、目标产物类型、当前步骤指针和运行状态。

**checklist.json**（步骤状态）：记录每个步骤的当前状态（pending / blocked / completed / not_required_yet）、产物输出路径、依赖步骤列表、完成时间和校验错误列表。

中断恢复流程：

1. Agent 通过 `status` 命令读取持久化状态，获取各步骤当前状态。
2. 通过 `next` 命令获取当前应执行步骤的产物路径和校验要求。
3. 若当前步骤的产物文件已存在但步骤未完成，在已有内容基础上补全。
4. 补全后仍须通过 `complete` 命令的门禁校验。

关键约束：禁止依赖 Agent 的对话上下文推测当前进度，必须以持久化状态文件为唯一事实来源。

### 6.7 幂等性设计

对已完成步骤重复执行 `complete` 命令时，系统直接返回"已完成"提示，不修改已记录的完成时间，不重复推进步骤指针。这确保重复操作不会破坏已有状态，提高系统鲁棒性。

### 6.8 与分层约束模型的对应关系

Runner 通过工作流配置数据，将分层约束模型中第三层至第六层的关键步骤固化为可校验的步骤序列：

| 分层模型层次 | Runner 步骤 | 门禁校验规则 |
| --- | --- | --- |
| 第一层+第二层：路由+需求 | 输入资料确认、测试范围确认 | 标题校验 |
| 第三层：测试实施设计 | 环境前置判断 | 标题校验（6 个必需标题） |
| 第三层：测试实施设计 | 测试工具选型 | 表格校验（7 列 + 有效数据） |
| 第三层：测试实施设计 | 测试实施指南 | 标题校验（5 个必需标题） |
| 第四层：执行证据 | 测试执行记录 | 标题校验（6 个必需标题） |
| 第五层+第六层：判断+交付 | 最终报告 | 标题校验（5 个必需标题） |
| 第六层：交付与沉淀 | 测试工程反思 | 标题校验（4 个必需标题） |

分层约束模型为 Runner 提供了"应该约束什么"的方法论依据，Runner 为分层约束模型提供了"如何强制执行"的技术保障。


## 7. 案例研究一：EXAMPLE-1001 sample-client fake-clock

### 7.1 案例背景

EXAMPLE-1001 的功能变更是：sample-client 新增用于联调和仿真测试的虚拟墙钟漂移能力，配合上游 mock 时钟场景验证 `dayOrderExpireTime` 逻辑。核心公式为：

```
虚拟当前时间 = 真实当前时间 + UPS_CLIENT_VIRTUAL_CLOCK_DRIFT_SEC
```

过期判断为：

```
DayOrderExpireTime != 0 && 虚拟当前时间 >= DayOrderExpireTime
```

正 drift 会让订单更早过期，负 drift 会延后过期，`DayOrderExpireTime=0` 表示不过期。该能力只应在 fake-clock 构建中生效，普通 `sample-client` 和 `sample_client_debug` 不应受影响。

### 7.2 测试难点

该需求的测试难点不在于下单动作本身，而在于测试前提和证据链：

1. **环境前置不是附属动作**：fake-clock 能力依赖特定二进制（`sample_client_fake_clock_debug`）和启动时 env（`UPS_CLIENT_VIRTUAL_CLOCK_DRIFT_SEC`），必须通过 guard `start_cmd` 注入，而不是只在 SSH shell 中 export。修改 guard 配置后必须重启 guard 并验证 PID 变化。

2. **DayOrderExpireTime 不能任意构造**：该字段由 upstream-service 根据交易日历和日切口径计算后下发，不能由测试脚本手工传入。部分理论 case（如 `DayOrderExpireTime=0`）在当前环境下不可执行。

3. **普通单和算法单入口不同**：普通订单可用 auto_case 定向下单；算法单需要先下算法单，再通过 `mockTransactionPrice` 触发行情，使 core-engine 送单到 sample-client。

4. **背景流量会污染证据**：稳定性脚本持续下单的订单不可控，证据不可精确归因。

### 7.3 Agent 初期偏差

| 偏差 | 表现 | 若未纠正的后果 |
| --- | --- | --- |
| 忽略环境前置 | 一开始关注下单逻辑，没有第一时间确认二进制、env、guard 配置 | 即使订单结果符合预期，也无法证明是 fake-clock 行为 |
| 工具选型不充分 | 倾向观察稳定性脚本，而不是新增定向 auto_case case | clOrdID 和输入不可控，证据无法归因 |
| 混淆工具前提 | 将普通下单和 app.py 前置混在一起 | 测试准备复杂化 |
| 执行记录滞后 | 不是所有 case 一开始都按模板补齐 | 报告阶段容易补写推断 |
| 错误理解算法单预期 | FC-014 初期按直接 reject 理解 | 忽略算法单需要闭环终态 |

### 7.4 方法论如何介入

**用例设计阶段**：对通知、代码和用户澄清进行对齐，形成 18 个 case 和覆盖清单。区分了理论输入与当前可执行输入——`DayOrderExpireTime=0` 和真实已过期订单被标记为"本轮不执行"，而不是强行写成已执行。

**测试实施设计阶段**：先解决环境和工具，而不是直接下单。工具选型被明确写成测试实施的一部分：

| 场景 | 工具选择 | 原因 |
| --- | --- | --- |
| 普通未过期 ACK | auto_case 独立 type `sample_fake_clock_expect_ack` | 输入可归因，有北向断言 |
| 普通过期拒单 | auto_case 独立 type `sample_fake_clock_expect_expired_reject` | 可断言 `39=8 / 150=8` |
| 算法单入口 | auto_case + app.py + `mockTransactionPrice` | 需要触发行情 |
| 背景稳定性流量 | 不采用 | 订单不可控，证据不可精确归因 |

**执行证据层**：保存了每个 case 对应的 clOrdID、OrderId、`DayOrderExpireTime`、北向 FIX、event.log 和南向无发送证据。

**层间反馈**：FC-014 实际是算法单触发后形成终态闭环（`ordStatus=4 / execType=4 / Day order expired`），不是直接新单拒绝。这个发现反馈到需求与判断基线层，修正了 case 预期。

### 7.5 执行结果

| 状态 | Case | 说明 |
| --- | --- | --- |
| 通过 | FC-001~003、009~014、016~017 | 覆盖 drift=0、正漂移、非法 env、未设置 env、用户订单入口、算法单入口、普通 debug 回归 |
| 当前口径部分覆盖 | FC-005 | 负漂移只覆盖"不误拒正常未到期订单" |
| 需复测 | FC-004 | 已验证超过边界会过期，但未达到严格边界精度 |
| 本轮不执行 | FC-006~008、015 | 输入当前不可构造或已由 UAT 人工完成 |
| 不单独执行/已覆盖 | FC-018 | 由 guard startCmd、运行态、PID 和订单行为覆盖 |

### 7.6 案例结论

EXAMPLE-1001 案例说明：复杂功能测试中，Agent 的可靠性不是来自单次回答的正确性，而是来自分层约束对其行为的持续收敛。任务路由让 Agent 先意识到环境前置；用例设计澄清了理论输入与可执行输入；测试实施设计补齐了二进制、env、guard、PID 和工具选型；执行证据层保存了真实日志和标识；判断基线使不可构造输入不被误写成失败或通过。

1. Runner 的测试实施过程本身就使用了 Runner 作为流程门禁（run_id: `20260520_160449_test-agent-runner-execution`）。

### 8.3 门禁校验的实际拦截效果

在 43 条测试用例的执行过程中，门禁系统展示了以下拦截行为：

**拦截一：缺失标题**

### 8.6 发现的缺陷与修复

本轮测试发现 2 个缺陷：

**缺陷一：run_id 同秒冲突（Runner-TC-002）**

- 现象：连续快速 `start` 同名需求时，run_id 只精确到秒，第二次 start 复用了相同 run_id。
- 根因：`run_id` 生成格式为 `YYYYMMDD_HHMMSS_name`，同一秒内多次创建会冲突。
- 修复：将 run_id 格式改为 `YYYYMMDD_HHMMSS_ffffff_name`，加入微秒级精度。
- 复测验证（run_id: `20260520_162001_054969_EXAMPLE-1001-RETEST` 和 `20260520_162001_330722_EXAMPLE-1001-RETEST`）：同秒连续创建，两个 run_id 不同，复测通过。

**缺陷二：重复 step id 未被拒绝（Runner-TC-039）**

- 现象：workflow 配置中存在重复 step id 时，Runner 仍创建 run，未拒绝加载。
- 根因：配置加载时缺少 step id 唯一性校验。
- 修复：在 `WorkflowConfig.load_from_yaml` 中增加 step id 唯一性检查，存在重复时打印错误并退出。
- 复测验证：重复 step id 配置触发错误 `workflow config error: duplicate step id(s): input_sources`，退出码为 1，复测通过。

## 9. 讨论

### 9.1 方法有效性

本文方法的有效性主要体现在四个方面。

**第一，它让 Agent 的测试行为可控。** 通过 workflow、skill、模板和 Runner 门禁，Agent 不再只依赖上下文记忆决定下一步，而是在任务入口、实施设计和报告输出上有明确约束。Runner 的门禁校验将"应该做"升级为"必须做"——校验未通过时流程无法推进。

**第二，它让测试结果可复核。** 执行记录要求保存真实输入、输出、关键标识和证据路径。Runner 的状态持久化进一步确保了可复核性：每个步骤的完成时间、校验结果和阻塞原因都有 JSON 记录，不依赖聊天上下文。

**第三，它让测试经验可沉淀。** 测试结束后的反思候选可以转化为规则、workflow、skill、模板、工具或业务字典。Runner 自身测试中发现的 run_id 冲突和配置校验缺失，就是通过反思沉淀机制被识别并修复的。

**第四，它让流程约束可演进。** Runner 的配置化设计意味着新增步骤、修改校验规则或调整依赖关系只需修改 YAML 配置，无需修改程序代码。当方法论演进时，门禁系统可以同步演进。

### 9.2 两个案例的对比

| 维度 | EXAMPLE-1001 | Runner 自身测试 |
| --- | --- | --- |
| 测试对象 | 业务功能（sample-client fake-clock） | 工具软件（Runner CLI） |
| 环境复杂度 | 高（远端服务器、guard 配置、二进制切换） | 低（本地 Python 环境） |
| 工具选型 | auto_case 独立 type + app.py | Runner CLI + 本地 harness |
| 门禁系统参与 | 方法论指导，无 Runner（Runner 尚未实现） | Runner 全程参与 |
| 发现的缺陷 | 0（功能验证通过） | 2（run_id 冲突、配置校验缺失） |
| 方法论价值体现 | 纠正 Agent 初期偏差，区分理论输入与可执行输入 | 验证门禁拦截效果，发现工具自身缺陷 |

两个案例从不同角度验证了方法论：EXAMPLE-1001 验证了分层约束对 Agent 行为的纠偏效果；Runner 自身测试验证了门禁系统的技术保障能力。

### 9.3 外部适用性

六层模型并不只服务上述两个案例。当前项目中，已有多类任务可以映射到同一组约束层：

| 任务类型 | 重点约束层 | 说明 |
| --- | --- | --- |
| 日切检查 | 任务路由层、判断基线层、执行证据层、交付沉淀层 | 需要先命中日切 workflow，再使用业务字典和报告模板 |
| 稳定性失败排查 | 任务路由层、执行证据层、判断基线层 | 需要区分 rejected/failed/non_terminal，通过跨层证据复核 |
| 部署验证 | 任务路由层、测试实施设计层、执行证据层 | 需要确认包、组件、guard 重启、PID 和运行态 |
| auto_case 功能回归 | 测试实施设计层、执行证据层、交付沉淀层 | 需要选择 case type、确认断言、记录报告 |
| 远端 SSH 调查 | 任务路由层、执行证据层 | 需要按"小命令、短输出、分步骤"原则执行 |

Runner 当前只覆盖"测试实施 workflow"，但其配置化设计允许后续扩展到其他 workflow 类型。

### 9.4 方法边界

本文方法也有明确边界：

**第一，它不能保证 Agent 永远正确。** 它提升的是可控性和可复核性，而不是消除所有错误。Agent 仍可能在门禁通过后的具体执行中犯错。

**第二，它依赖工程资产的质量。** 若 workflow 不完整、skill 过时、业务字典缺失或工具没有断言能力，Agent 仍可能执行出低质量结果。门禁只能校验产物结构，不能校验产物内容的业务正确性。

**第三，它仍需要人类确认关键业务口径。** 尤其是涉及交易日历、日切、维护窗口、异常定性和高风险结论时，Agent 应明确事实、推断和待确认点。

**第四，它有成本。** 完整分层约束需要维护 workflow、skill、模板、业务字典和执行记录。对于输入输出明确、环境稳定、无需跨层证据的简单冒烟测试，可以只轻量激活部分层次。

**第五，门禁校验的粒度有限。** 当前版本只做结构校验（标题存在性、非空内容、表格列完整性、占位符检测），不做语义校验。Agent 可以写出结构合格但内容质量低的产物通过门禁。后续可通过增强校验规则（如关键字段引用检查、证据路径存在性检查）逐步提升。

### 9.5 后续工作

后续建设可以从五个方向推进：

1. **建立测试工具能力矩阵**：帮助 Agent 更稳定地完成工具选型，减少工具误用。

2. **开发执行记录质量检查脚本**：自动发现漏 case、漏证据、漏恢复记录，将门禁从结构校验扩展到内容质量校验。

3. **抽象通用业务字典模板**：让正常/异常/未知三分法跨需求复用，降低判断基线层的维护成本。

4. **扩展 Runner 覆盖更多 workflow 类型**：将日切检查、稳定性分析、部署验证等任务纳入门禁管理。

5. **增强门禁校验规则**：支持 artifact 间引用检查（如执行记录引用实施指南中的 case ID）、blocked/待确认项检测、证据路径存在性校验。

## 10. 结论

本文提出了一种面向真实功能测试交付的 Agent 测试工程方法论。该方法论的核心不是追求 Agent 一次性正确，而是通过任务路由、测试实施设计、执行证据、判断基线和交付沉淀，把 Agent 工作中的不确定性显式化，并纳入可复核的工程过程。

在此基础上，本文设计并实现了 Test Agent Workflow Runner，将分层约束从文档规则升级为可执行的门禁校验机制。Runner 通过配置化的步骤定义、分层门禁校验（依赖校验 → 存在性校验 → 内容校验）、目标产物模式和状态持久化，解决了 Agent 测试实施中的流程跳步、上下文丢失、产物质量不可控和流程灵活性不足四个技术问题。

通过两个完整案例的验证：

- EXAMPLE-1001 案例证明了分层约束对 Agent 行为的纠偏效果——从环境前置到工具选型到执行记录，方法论在每个断裂点约束了 Agent 的不确定性行为。
- Runner 自身测试案例证明了门禁系统的技术保障能力——43 条用例中门禁多次实际拦截了标题缺失、内容为空、依赖跳步和占位符数据，并通过状态持久化支持了完整的可复核记录。

随着 Agent 能力持续提升，具体的 workflow、skill、模板和字典可能会自动生成、自动校验甚至自动演进，但"将不确定性显式化并工程化管理"这一原则不会过时。未来的 Agent 测试工程可能从人工维护资产走向资产自动维护，但人类对关键业务口径、风险边界和最终责任的确认仍然是闭环的锚点。
