# 阶段 2：方法论框架

论文题目：

```text
从用例设计到执行报告：一种可落地的 Agent 测试工程方法论
```

## 1. 框架目标

阶段 2 的目标是建立论文的核心方法论框架，回答：

```text
Agent 如何被组织进一套从测试用例设计到测试执行报告的工程闭环？
```

该框架不追求让 Agent 完全自主测试，而是通过流程分层、资产约束和证据记录，让 Agent 的测试工作具备以下特征：

- 可执行：从测试用例能落到具体步骤。
- 可复核：每个结论能回到证据。
- 可交接：下一个人或 Agent 能继续执行或复查。
- 可沉淀：经验能转化为 rules、workflows、skills、templates 或字典。

## 2. 任务路由到执行报告闭环模型

本文提出“任务路由到执行报告闭环模型”。模型覆盖功能测试从需求输入到最终报告的完整链路：

```text
需求 / 代码 / 通知 / 历史问题
        ↓
Workflow 任务路由
        ↓
测试用例设计
        ↓
测试实施设计
  - 实施规划
  - 工具选型
  - 环境准备
  - 逐 case runbook
        ↓
测试执行与证据采集
        ↓
测试产出可疑问题发现
        ↓
执行记录
        ↓
覆盖矩阵
        ↓
测试报告
        ↓
反思与沉淀
```

这个模型的关键不是把流程拉长，而是把 Agent 容易跳过的测试工程动作显式化。例如，测试工具选型属于测试实施的一部分，但不能隐含在“执行 case”里；异常发现不能隐含在“断言通过”里，环境恢复不能隐含在“测试结束”里。

今天的工程实践进一步证明，闭环前面还必须增加一层 `Workflow 任务路由`。它用于回答：

```text
当前用户请求到底属于哪类测试工程任务，应该进入哪条主流程，并联动哪些子流程？
```

没有这一层时，Agent 即使拥有 skill，也容易在任务入口处误判：该先做部署还是先做 case、该走失败排查还是日切检查、该用远端 SSH 调查还是直接读本地文档。`docs/ai_workflows.md` 将这一步显式化，要求 Agent 先匹配主 workflow，再读取对应 skill、证据要求、模板和脚本。

## 3. 阶段总览

| 阶段 | 输入 | Agent 关键动作 | 输出 | 主要风险 | 防错机制 |
| --- | --- | --- | --- | --- | --- |
| Workflow 任务路由 | 用户请求、AGENTS 入口、workflow catalog | 判断任务类型，选择主 workflow，识别子流程和必读资产 | workflow 命中结果 / 未命中说明 | 一开始走错流程，后续执行全部偏航 | `docs/ai_workflows.md`，未命中必须显式说明 |
| 测试用例设计 | 需求、代码、通知、历史资料 | 信息源甄别、需求分析、覆盖清单、case 拆解 | `test_case_design.md` | 需求基线错误、覆盖遗漏 | 信息源对齐、checklist back-check |
| 测试实施设计 | 测试用例、环境说明、部署说明、现有工具、mock 能力 | 判断环境前置、执行口径、工具选型、恢复方案，拆逐 case 步骤 | `test_execution_guide.md`、工具选型表 | 直接跳业务 case，忽略环境或误用工具 | 前置清单、工具能力矩阵、逐 case runbook |
| 执行与证据采集 | 实施指南、工具、测试数据 | 执行 case，记录输入、输出、日志、报告、关键标识 | case 证据 | 只执行不记录，断言缺失 | 逐 case 执行记录 |
| 可疑问题发现 | 执行产出、日志、报告、历史反例 | 识别正常、异常、未知情况，复核跨层一致性 | 疑点列表 / 正常列表 / 未知列表 | 只看预期断言，漏掉隐藏问题 | 业务字典、三分法、反例库 |
| 执行记录 | case 证据、环境切换、恢复动作 | 写真实执行过程、状态、证据、结论 | `test_execution_record_*.md` | 把计划当结果，状态不清 | 状态枚举、证据路径、恢复记录 |
| 覆盖矩阵 | 执行记录 | 汇总所有 case 状态和证据摘要 | 覆盖矩阵 | 遗漏失败、部分覆盖、阻塞项 | case 全覆盖、状态统一 |
| 测试报告 | 覆盖矩阵、执行摘要 | 提炼结论、问题、风险、恢复状态 | 测试报告 / 团队渠道报告 | 报告失真，新增未验证结论 | 只从执行记录提炼 |
| 反思与沉淀 | 测试过程、失误、复盘 | 提取规则缺口、workflow 缺口、skill 缺口、工具缺口 | 候选 rules / workflows / skills / checklist | 经验散落在聊天里 | 测试工程反思 |

## 4. 六类资产协作关系

该方法论依赖六类资产：`rules`、`workflows`、`skills`、`dictionaries / defect libraries`、`templates`、`execution records`。它们的职责不同，不能互相替代。

| 资产 | 职责 | 不应该承担的职责 | 当前项目示例 |
| --- | --- | --- | --- |
| `rules` | 红线、强约束、强制入口 | 不承载长流程细节 | `.cursor/rules/00-global-team-standards.mdc` |
| `workflows` | 根据任务类型做流程路由，声明主 skill、子流程、必读文档和输出结构 | 不替代具体操作步骤 | `docs/ai_workflows.md` |
| `skills` | 可复用流程和场景化操作方法 | 不写成项目流水账 | `test-case-design-checklist`、`feature_test_execution_docs`、`deploy_install` |
| `dictionaries / defect libraries` | 提供业务判断基线、已知正常 / 异常 / 灰区和历史反例 | 不替代本次证据采集 | `docs/daycut_behavior_dictionary.md`、`docs/known_defects/known_defects.yaml` |
| `templates` | 固化交付物结构 | 不替代实际执行证据 | 实施指南模板、执行记录模板、团队渠道报告模板 |
| `execution records` | 保存真实执行过程、证据和结论 | 不写成计划或模板 | `test_execution_record_<date>_<env>.md` |

协作关系：

```text
rules 决定什么时候必须进入某个流程；
workflows 决定当前任务应该走哪条主流程、联动哪些子流程；
skills 描述这个流程应该怎么执行；
dictionaries / defect libraries 提供判断正常、异常、未知的业务基线；
templates 规定流程产物应该长什么样；
execution records 记录这次真实执行发生了什么。
```

因此，长期维护原则是：

```text
rules 放红线，workflows 放路由，skills 放步骤，dictionaries 放判断基线，templates 放结构，records 放事实。
```

说明：本阶段框架文档将“从测试产出中发现可疑问题”作为独立阶段，是为了强调 Agent 不能只按预期断言判断通过。V2 论文将该能力进一步收敛为“判断基线层”的核心职责，因为可疑问题发现依赖业务字典、缺陷库、正常 / 异常 / 未知三分法和跨层证据。两种表述不冲突：早期框架保留阶段视角，正式论文以“判断基线层”为主口径。

## 5. 阶段一：测试用例设计

测试用例设计阶段的目标是把需求、代码、通知、历史问题等输入转化为可执行、可回归、可 review 的测试用例。

### 5.1 输入

- 需求说明
- 代码变更或配置变更
- 通知、issue、部署说明
- 历史缺陷或反例
- 现有测试用例
- 用户在当前对话中的澄清

### 5.2 关键动作

1. 列出信息源。
2. 做信息源甄别和冲突处理。
3. 写需求分析。
4. 建 coverage checklist。
5. 拆 test point。
6. 设计具体 case。
7. 做 checklist back-check。

### 5.3 输出

```text
test_case_design.md
```

该文档至少应包含：

- 信息源
- 需求分析
- 覆盖清单
- test point
- case 表
- checklist back-check

### 5.4 防错机制

| 风险 | 防错机制 |
| --- | --- |
| 需求基线错误 | 信息源甄别，冲突项标记待确认 |
| 只按技术模块写 case | 先按业务维度建 checklist |
| 用例不可执行 | 每个 case 写前置、输入、预期、证据 |
| 覆盖遗漏 | checklist item 到 case ID 的 back-check |

## 6. 阶段二：测试实施设计

测试实施设计阶段的目标是把测试用例转化为可执行 runbook。Agent 在这里必须先回答“环境怎么用、工具怎么选、证据怎么收”，再回答“case 怎么跑”。

测试工具选型是测试实施设计的一部分，而不是测试实施之外的独立阶段。之所以在方法论中单独展开，是因为它经常被 Agent 隐含在“执行 case”里，导致工具误用、断言缺失或证据不可归因。

### 6.1 输入

- `test_case_design.md`
- 目标环境说明
- 包、版本、分支或镜像说明
- 服务、配置、启动参数
- 现有工具和 mock 能力
- 测试数据和账号

### 6.2 关键动作

1. 确认测试范围与执行口径。
2. 判断环境前置：环境、版本、包、配置、进程、env、feature flag、重启方式。
3. 判断每个 case 的工具选型：现有工具、新增自动化 case、脚本、SQL、fixture、mock 或人工复核。
4. 判断工具是否具备断言能力和证据归因能力。
5. 判断是否需要停止背景流量。
6. 判断是否需要 mock 外部依赖。
7. 拆公共准备步骤。
8. 按 case 拆执行步骤。
9. 设计恢复步骤。
10. 明确执行记录要求。

### 6.3 输出

```text
test_execution_guide.md
```

### 6.4 防错机制

| 风险 | 防错机制 |
| --- | --- |
| 直接跳业务 case | 环境前置清单必须在 case 前完成 |
| 运行态不是目标版本 | 记录版本、包、进程、命令行或等价运行态 |
| 配置未生效 | 记录重启 / reload 前后状态 |
| 背景流量污染证据 | 测试流量隔离或明确风险 |
| 测完忘记恢复 | 恢复步骤独立成节 |

## 7. 测试实施中的工具选型

测试工具选型用于决定每个 case 应该用现有工具、补充自动化 case，还是新增脚本或 mock 能力。它是测试实施设计内部的强制环节，必须在逐 case 执行步骤之前完成。

### 7.1 输入

- 每个 case 的触发方式
- 需要构造的输入
- 需要观察的输出
- 现有自动化工具
- mock 服务和分析脚本
- 环境限制

### 7.2 关键动作

1. 判断现有工具是否覆盖 case。
2. 判断现有工具是否支持断言。
3. 判断是否需要新增 case、SQL、fixture、mock 配置或脚本。
4. 判断工具是否会产生背景流量污染。
5. 判断工具输出是否能支持证据链闭合。
6. 将选择理由写入实施指南和执行记录。

### 7.3 工具选型维度

| 维度 | 判断问题 | 影响 |
| --- | --- | --- |
| 输入控制 | 是否需要精确构造输入？ | 决定用定向工具还是批量工具 |
| 断言能力 | 工具是否支持自动断言？ | 决定是否需要补断言 |
| 证据归因 | 是否会混入背景流量？ | 决定结果是否可归因 |
| mock 能力 | 是否需要模拟外部事件？ | 决定是否需要 mock 服务 |
| 环境影响 | 是否会影响其它测试？ | 决定是否需要隔离 |
| 可重复性 | 是否能稳定复现？ | 决定是否适合回归 |
| 开发成本 | 是否值得新增工具？ | 决定是否临时人工复核 |

### 7.4 输出

```text
测试工具选型表
```

建议格式：

| Case / 场景 | 现有工具是否覆盖 | 选用工具 | 是否需要新增 case / 脚本 | 断言方式 | 选择理由 | 缺口 / 风险 |
| --- | --- | --- | --- | --- | --- | --- |

### 7.5 防错机制

| 风险 | 防错机制 |
| --- | --- |
| 用背景流量替代定向 case | 要求说明工具是否能精确归因 |
| 只执行不检查 | 要求说明断言方式 |
| 工具不支持输入构造 | 标记需要新增 case 或脚本 |
| 工具输出不足以定性 | 提前规划补充证据层 |

## 8. 阶段三：测试执行与证据采集

执行阶段的目标是按实施指南执行 case，并同步采集证据。Agent 在这一阶段要避免“跑完再回忆”，必须边执行边记录。

### 8.1 输入

- 测试实施指南
- 工具选型表
- 测试数据
- 环境前置记录

### 8.2 关键动作

1. 执行公共准备步骤。
2. 按 case 执行动作。
3. 记录实际输入。
4. 记录实际输出。
5. 记录断言结果。
6. 记录关键标识。
7. 收集证据路径。
8. 记录失败、阻塞或偏差。

### 8.3 证据类型

| 证据类型 | 示例 |
| --- | --- |
| 标识类 | request ID、order ID、trace ID、case ID |
| 日志类 | 应用日志、event log、FIX、gateway log、systemd journal |
| 报告类 | 自动化 report、CSV、HTML report |
| 数据类 | DB 查询结果、归档文件、统计文件 |
| 运行态 | 进程命令、PID、配置、版本、健康检查 |
| 外部层 | 下游原始报文、mock 服务记录、监控指标 |

### 8.4 防错机制

| 风险 | 防错机制 |
| --- | --- |
| 执行完无证据 | 每个 case 必须有证据字段 |
| 证据无法精确匹配 | 使用完整标识，不用尾号或时间邻近替代 |
| 只看单层日志 | 按问题类型补充必要证据层 |
| 失败原因混乱 | 区分工具失败、环境阻塞、业务失败、断言失败 |

## 9. 阶段四：从测试产出中发现可疑问题

测试执行不应只停留在“预期断言是否通过”。真实测试中，很多问题不是由单个预设断言直接暴露，而是出现在日志细节、状态差异、数量不一致、时间边界偏差或链路不自洽中。

因此，本阶段框架将“从测试产出中发现可疑问题”作为独立阶段。正式论文 V2 中，该能力归入“判断基线层”，这里保留独立章节用于展开其输入、机制和防错点。

### 9.1 输入

- case 执行结果
- 自动化报告
- 日志与归档
- 统计结果
- 历史缺陷库
- 业务字典
- 已知正常和异常模式

### 9.2 核心机制

| 机制 | 作用 | 输出 |
| --- | --- | --- |
| 业务字典 | 定义当前业务口径下的正常、异常、未知行为 | 场景 -> 预期分类 |
| 正常情况列表 | 防止把已知正常现象误报为 bug | 已核实正常项 |
| 异常情况列表 | 固化明确问题、强疑点、必须深挖信号 | 疑似 / 确认问题项 |
| 未知情况列表 | 对字典外现象不擅自定性 | 待确认项 |
| 历史反例库 | 遇到相同模式时优先按同类异常复核 | 样本和命中依据 |
| 跨层一致性检查 | 检查不同证据层是否自洽 | 证据链闭合情况 |

### 9.3 正常 / 异常 / 未知三分法

| 分类 | 判定口径 | Agent 输出要求 |
| --- | --- | --- |
| 正常情况 | 命中业务字典，且证据链自洽 | 写入正常情况列表，说明证据 |
| 异常情况 | 命中异常字典、历史反例，或跨层证据不自洽 | 写入疑似 / 确认问题列表，继续补证据 |
| 未知情况 | 字典外现象、证据不足、业务口径未确认 | 标记待确认，不得写成正常或异常结论 |

### 9.4 可疑信号类型

| 信号类型 | 示例 | 处理方式 |
| --- | --- | --- |
| 状态不自洽 | 北向成功但内部状态为拒绝 | 回到完整链路复核 |
| 数量不一致 | CSV 桶数量与 event 统计对不上 | 按状态域、责任层、reason 重新过滤 |
| 时间边界异常 | 边界 case 晚于或早于预期窗口 | 标记需复测或重新设计执行窗口 |
| 链路缺口 | 有请求无响应、有上游无下游 | 补查下一层原始日志 |
| 文案与事件不一致 | 北向 text 指向 A，但内部事件指向 B | 优先按服务内事件定位责任层 |
| 历史反例相似 | 与已知缺陷样本模式接近 | 按同类异常优先复核 |
| 字典外现象 | 业务字典没有覆盖该表现 | 标记未知，交由人工确认 |

### 9.5 防错机制

| 风险 | 防错机制 |
| --- | --- |
| 把预期断言通过当成整体正常 | 增加“意外情况检查” |
| 把未知现象直接判正常 | 使用未知情况列表 |
| 把疑点直接写成 bug | 区分事实、推断、待确认 |
| 被历史经验带偏 | 先查业务字典和证据链 |
| 漏掉隐蔽问题 | 引入历史反例和跨层一致性检查 |

## 10. 阶段五：执行记录、覆盖矩阵与测试报告

该阶段将执行过程和可疑问题分析转化为可交付文档。

### 10.1 执行记录

执行记录保存真实发生的测试过程，不是实施计划的复述。

必须包含：

- 执行摘要
- 当前执行口径
- 测试前置记录
- 工具选型结果
- 逐 case 执行明细
- 恢复记录
- 覆盖矩阵
- 补充执行明细
- 未覆盖 / 阻塞项
- 测试工程反思候选

### 10.2 状态枚举

| 状态 | 含义 |
| --- | --- |
| 通过 | case 已执行，结果符合预期，证据可复核 |
| 失败 | case 已执行，结果不符合预期 |
| 需复测 | case 已执行但精度、时机、环境或数据不满足最终判断要求 |
| 当前口径部分覆盖 | 只能验证需求的一部分，剩余前提当前不可构造 |
| 本轮不执行 | 本轮范围外或前置条件缺失 |
| 不单独执行但已覆盖 | 该检查点已由其它 case 的证据覆盖 |
| 阻塞 | 因环境、权限、工具或数据问题无法执行 |

### 10.3 覆盖矩阵

覆盖矩阵用于回答：

```text
每个设计 case 本轮到底处于什么状态，有什么证据？
```

建议格式：

| Case ID | 状态 | 本轮执行记录 / 证据摘要 |
| --- | --- | --- |

覆盖矩阵必须覆盖全部 case，不能省略失败、阻塞、部分覆盖或不执行项。

### 10.4 测试报告

测试报告从执行记录和覆盖矩阵提炼，不新增执行记录中没有的结论。

报告至少说明：

- 总体结论
- 通过项
- 失败 / 需复测项
- 部分覆盖 / 未执行项
- 可疑问题和未知情况
- 环境恢复状态
- 剩余风险

### 10.5 防错机制

| 风险 | 防错机制 |
| --- | --- |
| 报告遗漏失败项 | 覆盖矩阵全量 case 校验 |
| 报告新增未验证结论 | 报告只从执行记录提炼 |
| 部分覆盖被写成通过 | 使用统一状态枚举 |
| 环境恢复不明 | 恢复记录独立成节 |

## 11. 反思与沉淀

测试结束后，Agent 不应只输出结果，还要形成测试工程反思候选。

### 11.1 输入

- 执行过程中的失误
- 工具缺口
- 文档缺口
- 规则缺口
- 用户纠偏
- 复测项和阻塞项

### 11.2 输出

| 类型 | 内容 |
| --- | --- |
| 规则缺口 | 需要进入 rules 的红线或强制入口 |
| workflow 缺口 | 需要进入 workflow catalog 的新任务类型、主流程或子流程关系 |
| skill / 流程缺口 | 需要沉淀到 skill 的流程知识 |
| 模板缺口 | 需要补进模板的交付字段 |
| 工具缺口 | 需要新增或增强的自动化工具 |
| 字典缺口 | 需要补进业务字典的正常 / 异常 / 未知现象 |

### 11.3 防错机制

- 反思项先作为候选，不自动写入规则或 skill。
- 用户确认后再沉淀。
- 避免把单次偶发现象固化成长期规则。
