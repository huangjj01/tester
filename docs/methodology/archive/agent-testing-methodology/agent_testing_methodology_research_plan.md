# 阶段 1：研究计划

论文题目：

```text
从用例设计到执行报告：一种可落地的 Agent 测试工程方法论
```

## 1. 研究背景

Agent 已经能够参与测试用例设计、脚本执行、日志检索和结果摘要。但在真实功能测试中，“能写用例”并不等于“能完成测试交付”。从测试用例到最终执行报告之间存在一段测试工程落地链路，包含环境前置判断、测试工具选型、执行过程控制、证据采集、执行记录、覆盖矩阵和团队同步。

如果没有明确的方法约束，Agent 容易出现以下问题：

- 从测试用例直接跳到业务执行，忽略环境、版本、包、配置、启动参数和 mock 能力。
- 没有显式选择测试工具，误用背景流量或不适合的脚本进行定向验证。
- 只执行动作，不补断言，导致结果无法判断通过或失败。
- 只看单层日志就下结论，证据链不闭合。
- 面对测试产出缺少异常嗅觉，只按预期字段勾选通过，不能从结果差异、日志细节、边界现象、状态不自洽中主动发现可疑问题。
- 执行结果只停留在聊天窗口，缺少可交接、可复核的执行记录。
- 报告阶段把推断写成结论，或隐藏部分覆盖、阻塞和需复测项。
- 测试过程中的经验没有沉淀为规则、skill 或模板，后续需求继续重复踩坑。

因此，本文关注的问题不是 Agent 是否能够辅助测试，而是如何把 Agent 放入一套测试工程闭环，使其能够稳定地从用例设计推进到执行报告。

## 2. 问题定义

本文将“Agent 测试工程方法论”定义为：

```text
一套面向功能测试的工程化流程与资产组织方式，用于约束 Agent 完成从需求理解、测试用例设计、测试实施设计、执行记录到测试报告的闭环工作，并保证测试结论可执行、可复核、可交接、可沉淀。
```

本文要解决的核心问题是：

```text
如何让 Agent 从“会设计测试用例”，进一步走到“能交付可复核的测试执行报告”？
```

这里的“可复核”至少包含：

- 每个 case 有明确状态。
- 每个执行结果有证据路径或关键标识。
- 每个结论能回溯到执行记录。
- 部分覆盖、阻塞、需复测项被显式写出。
- 环境恢复状态被单独记录。
- 经验沉淀有明确入口。

## 3. 研究目标

本文目标包括：

1. 梳理 Agent 从用例设计走向测试执行时的主要工程断点。
2. 提出“任务路由到执行报告闭环模型”，描述 Agent 完成功能测试闭环所需的阶段、输入、输出和防错机制。
3. 明确 `rules`、`workflows`、`skills`、`dictionaries / defect libraries`、`templates`、`execution records` 在 Agent 测试工程中的职责分工。
4. 将“测试工具选型”定义为测试实施设计内部的强制环节，说明其对测试归因、断言可靠性和证据闭合的影响。
5. 通过真实功能测试案例说明方法论如何修正 Agent 初期失误，并产出可复核测试结果。
6. 总结方法论的适用边界和下一阶段建设方向。

## 4. 研究问题

| 编号 | 研究问题 | 说明 |
| --- | --- | --- |
| RQ1 | Agent 从测试用例设计走向测试执行时，主要工程断点是什么？ | 用于识别为什么 Agent 不能只靠提示词直接完成测试交付。 |
| RQ2 | 如何把测试用例转化为可执行的测试实施指南？ | 用于说明环境前置、执行口径、恢复步骤和逐 case runbook 的必要性。 |
| RQ3 | 测试工具选型在 Agent 测试实施中承担什么作用？ | 用于说明为何必须先判断现有工具是否覆盖，是否需要新增 case、断言、mock 或分析脚本。 |
| RQ4 | 如何通过执行记录和证据链约束 Agent 的测试结论？ | 用于说明状态枚举、证据路径、关键标识、事实/推断分离如何降低结论风险。 |
| RQ5 | Agent 如何从测试产出中发现可疑问题，并形成接近人类测试工程师的异常敏感度？ | 用于说明如何从日志、状态、时间、数量、链路和历史反例中识别“不像预期”的信号。 |
| RQ6 | `rules`、`workflows`、`skills`、`dictionaries`、`templates` 和 `records` 如何共同支撑 Agent 测试工程闭环？ | 用于说明红线、路由、流程、判断基线、交付物和事实记录之间的职责边界。 |
| RQ7 | 如何通过 workflow catalog 将自然语言测试任务稳定路由到正确的测试工程流程？ | 用于说明为什么 Agent 需要先判断主 workflow 和子流程，再进入具体 skill。 |

## 5. 研究假设

本文基于以下假设展开：

1. Agent 在测试任务中的主要风险不是单点理解能力不足，而是缺少稳定的工程流程约束。
2. 当测试流程被拆解为用例设计、测试实施设计、执行记录和报告输出后，Agent 的行为更容易被人类 review 和纠偏；其中测试实施设计必须显式包含实施规划、工具选型和环境准备。
3. 将任务入口沉淀为 workflow，将流程沉淀为 skill，将交付结构沉淀为模板，可以减少同类需求中的重复沟通和重复失误。
4. 执行记录和覆盖矩阵能够把 Agent 的执行过程从聊天上下文转化为项目资产。
5. 将异常嗅觉显式化为业务字典、正常/异常/未知三分法、历史反例、跨层一致性校验和“意外情况”复核，可以提升 Agent 从测试产出中发现可疑问题的能力。
6. 高风险测试结论仍需要人类确认业务口径和关键证据，方法论不能替代人工责任判断。

这些假设将在案例研究中通过真实测试过程进行验证和修正。

## 6. 研究边界

本文研究范围：

- 功能测试场景下的 Agent 测试工程闭环。
- 从测试用例设计到执行报告的流程组织。
- rules、workflows、skills、dictionaries、templates、execution records 的职责划分。
- 测试工具选型和执行证据采集。
- 测试产出中的可疑信号识别和异常嗅觉沉淀，包括业务字典、正常情况、异常情况、未知情况的分类机制。
- 真实功能测试案例中的方法应用和经验抽象。

本文不研究：

- 通用大模型能力评测。
- 自动化测试平台架构设计。
- Agent 自主修复业务代码的能力。
- 完全无人值守测试执行。
- 覆盖率、缺陷率、效率提升等大规模量化评估。
- 某一个具体业务系统的完整测试规范。

本文关注的是“如何组织 Agent 完成可复核测试工作”，不是“如何让 Agent 取代测试工程师”。

## 7. 方法论对象

本文将方法论对象分为六类资产。

| 资产 | 职责 | 当前项目中的体现 |
| --- | --- | --- |
| rules | 放红线、强约束和强制入口 | `.cursor/rules/00-global-team-standards.mdc` |
| workflows | 放任务路由、主流程、子流程和输出结构 | `docs/ai_workflows.md` |
| skills | 放可复用流程 | `test-case-design-checklist`、`feature_test_execution_docs`、`deploy_install` |
| dictionaries / defect libraries | 放业务判断基线和历史反例 | `docs/daycut_behavior_dictionary.md`、`docs/known_defects/known_defects.yaml` |
| templates | 放交付物结构 | 实施指南模板、执行记录模板、团队渠道报告模板 |
| execution records | 放真实执行证据 | `test_execution_record_<date>_<env>.md` |

六类资产的关系是：

```text
rules 约束什么不能做、什么时候必须进入某个流程；
workflows 判断当前任务应该进入哪条主流程，并联动哪些子流程；
skills 描述某类任务应该如何做；
dictionaries / defect libraries 约束哪些现象属于正常、异常、未知或已知问题；
templates 固化应该交付什么结构；
execution records 保存真实执行过程和证据。
```

## 8. 案例选择

本文选择 EXAMPLE-1001 sample-client fake-clock 功能测试作为案例。

选择理由：

1. 它不是单纯业务下单验证，必须先处理环境前置，包括特殊二进制、启动参数、环境变量和 guard 重启。
2. 它包含测试工具选型问题：普通单可以用定向自动化 case，算法单入口需要 mock 行情触发，稳定性背景流量不适合做精确归因。
3. 它暴露了 Agent 初期常见失误：忽略二进制切换、忽略 env 注入位置、误判工具前置、执行记录不完整、误把日志输出当作需求验收点。
4. 它最终产出了完整测试资产：测试用例、实施指南、执行记录、覆盖矩阵、团队渠道报告和通用 skill。
5. 它既有通过项，也有部分覆盖、需复测和本轮不执行项，适合讨论真实测试结论的边界。

案例使用的主要资产：

```text
docs/iterations/EXAMPLE-1001-sample-client-fake-clock/test_case_design.md
docs/iterations/EXAMPLE-1001-sample-client-fake-clock/test_execution_guide.md

.cursor/skills/test-case-design-checklist/SKILL.md

```
