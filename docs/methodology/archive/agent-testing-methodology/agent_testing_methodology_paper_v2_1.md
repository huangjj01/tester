# 从用例设计到执行报告：一种可落地的 Agent 测试工程方法论

## 摘要

Agent 已经能够辅助测试用例设计、脚本执行、日志检索和结果摘要，但真实功能测试交付并不止于生成用例。缺少工程化约束时，Agent 容易跳过环境前置、误用工具、遗漏证据或将推断写成结论。本文提出“分层约束的 Agent 测试工程闭环”，用任务路由、需求与用例、测试实施设计、执行证据、判断基线、交付与沉淀六层机制，将 Agent 的不确定性响应转化为可执行、可复核、可交接、可沉淀的测试交付过程。通过 EXAMPLE-1001 sample-client fake-clock 案例，本文展示该方法如何收敛 Agent 在二进制切换、env 注入、工具选型和执行记录中的偏差，并形成可复核测试结果。

## 关键词

Agent 测试；功能测试；测试实施设计；工具选型；证据链；测试报告；分层约束

## 1. 引言

大模型 Agent 已经能够参与软件测试中的多类任务，例如阅读需求、生成测试用例、执行命令、检索日志和总结结果。在理想化场景中，Agent 看似能够快速完成从需求到测试结论的工作。但在真实功能测试中，测试交付不是单步生成行为，而是一组跨环境、跨工具、跨证据层和跨业务判断的工程活动。

这带来一个核心矛盾：

```text
会写测试用例 != 能交付测试结果
```

测试用例只回答“应该验证什么”。测试交付还要回答任务路径、环境前提、工具选择、证据归因、异常解释和报告口径。若这些问题没有被显式约束，Agent 的表现会高度依赖上下文记忆和临场判断：它可能在某一步给出合理答案，却在后续执行中跳过关键前置；也可能完成了命令执行，却没有留下可复核证据；还可能把当前无法证明的推断写成正式测试结论。

本文所说的“不确定性”，不是指模型输出随机性本身，而是指 Agent 在缺少显式工程约束时，其任务路径选择、信息获取范围、执行动作和结论形成过程的不可预测性。同一个测试请求，在不同上下文中可能被 Agent 解释为下单执行、日志调查、部署验证或报告整理，并产生质量差异很大的结果。本文讨论的分层约束，正是为了把这种不可预测性纳入可复核的工程过程。

因此，本文关注的问题不是“Agent 是否能参与测试”，而是：

```text
如何把 Agent 组织进一套可执行、可复核、可交接、可沉淀的测试工程闭环？
```

本文的主论点是：面向真实功能测试的 Agent 能力建设，关键不在于让 Agent 一次性给出正确答案，而在于通过分层约束的测试工程闭环，将 Agent 的不确定性响应转化为可执行、可复核、可交接、可沉淀的测试交付过程。

本文将这一测试交付闭环组织为六层约束结构，并在后文依次展开。

本文的贡献包括三点：

1. 提出分层约束模型，用任务路由、实施设计、执行证据、判断基线和交付沉淀约束 Agent 测试行为。
2. 定义从用例到报告的测试交付闭环，将 Agent 测试从 test case generation 扩展到实施设计、工具选型、执行记录、覆盖矩阵和测试报告。
3. 通过 EXAMPLE-1001 sample-client fake-clock 案例，说明该模型的落地方式和纠偏效果，并形成可复核测试交付。

## 2. 相关实践与本文定位

当前 Agent 辅助测试实践大致可以分为三类。

第一类是 prompt-based test generation，即根据需求、接口说明或代码生成测试用例。代表性实践包括 CodiumAI、TestPilot 以及各类 IDE 内置的测试生成能力。这类实践提升了用例草拟效率，但通常停留在“应该测什么”，对环境前置、工具选择、执行证据和报告交付关注不足。由此留下的开放问题是：生成出来的用例如何落地为可执行、可归因、可交接的测试交付。

第二类是 agentic execution，即 Agent 按 ReAct 或类似模式调用命令、浏览器、日志检索和自动化脚本完成操作。SWE-agent、OpenHands 等项目体现了这类方向：Agent 能围绕 issue 或任务执行多步操作。这类实践增强了执行能力，但若缺少任务路由和证据模板，Agent 仍可能在错误流程中执行正确命令。由此留下的开放问题是：执行能力如何被组织进正确的任务流程，而不是在错误流程中高效地产生不可复核结果。

第三类是更完整的软件工程 Agent 或 CI / DevOps Agent，例如 GitHub Copilot Workspace、Devin 以及围绕 CI 失败分析的自动化助手。这类实践更接近工程现场，但主要围绕已有 issue、流水线和失败信号，较少讨论从测试用例设计到测试执行报告的完整交付链路。由此留下的开放问题是：当任务不是修复一个已知失败，而是交付一次功能测试时，测试设计、测试实施、证据采集和测试报告如何被统一管理。

本文与上述实践的区别在于：本文不把 Agent 测试限定为“生成测试用例”或“自动执行脚本”，而是关注真实功能测试交付的工程组织方式。本文提出的分层约束闭环，将任务路由、测试实施设计、工具选型、执行记录、判断基线和报告沉淀纳入同一个方法论框架。

## 3. Agent 测试落地的工程断点

Agent 在测试任务中的不确定性，通常不是因为它完全不理解需求，而是因为真实测试中存在多个需要工程约束的断点。

| 工程断点 | 常见表现 | 直接后果 |
| --- | --- | --- |
| 任务入口不稳 | 用户要求测试，Agent 直接进入下单或查日志 | 后续动作可能服务于错误目标 |
| 需求基线不稳 | 未甄别通知、代码、分支、用户澄清之间的差异 | 用例预期错误或覆盖遗漏 |
| 环境前置缺失 | 未确认包、二进制、配置、env、启动参数和重启方式 | case 结果无法证明目标功能 |
| 工具选型缺失 | 用背景流量观察替代定向验证，或用普通单工具测试算法单入口 | 输入不可控，证据不可归因 |
| 断言缺失 | 只执行动作，不定义通过标准 | 无法判断通过、失败或需复测 |
| 证据链不闭合 | 只看单层日志或单个报告 | 结论缺少复核基础 |
| 异常识别不足 | 只核对预期断言，不检查额外拒单、状态不自洽、时间边界和未知现象 | 隐蔽问题被漏掉或误报 |
| 执行记录缺失 | 测试结果停留在聊天窗口 | 后续无法交接和复查 |
| 报告失真 | 把推断写成结论，隐藏部分覆盖或阻塞项 | 团队同步被误导 |

这些断点说明，仅仅增加提示词或补充一个 skill 并不足以解决问题。Agent 测试交付需要一套分层机制：先约束任务入口，再约束用例设计，然后约束实施设计、执行证据、结果判断和报告输出。

## 4. 分层约束的 Agent 测试工程闭环

本文提出“分层约束的 Agent 测试工程闭环”。该闭环不是简单的线性步骤，而是六层互相配合的约束关系。

```text
Workflow 任务路由
-> 测试用例设计
-> 测试实施设计
   -> 实施规划
   -> 工具选型
   -> 环境准备
   -> 逐 case runbook
-> 测试执行与证据采集
-> 执行记录
-> 覆盖矩阵
-> 测试报告
-> 反思沉淀
```

六层模型如下：

| 层次 | 控制的不确定性 | 主要资产 | 典型输出 |
| --- | --- | --- | --- |
| 任务路由层 | 用户请求进入错误流程 | `workflows` | workflow 命中结果、主流程、子流程 |
| 需求与用例层 | 需求基线错误、覆盖遗漏 | 用例设计 skill、用例模板 | 需求分析、覆盖清单、测试用例 |
| 测试实施设计层 | 环境误用、工具误用、执行不可落地 | 实施指南 skill、实施模板 | 环境前置、工具选型、逐 case runbook |
| 执行证据层 | 执行事实丢失、证据不可归因 | 执行记录模板、日志层规范 | case 状态、关键标识、证据路径 |
| 判断基线层 | 把未知写成结论、误报或漏报异常 | 业务字典、缺陷库、三分法 | 正常 / 异常 / 未知列表 |
| 交付与沉淀层 | 报告失真、经验散落 | 报告模板、覆盖矩阵、反思机制 | 测试报告、候选规则 / skill / 字典 |

这六层并非任意拆分。它们分别对应功能测试交付中的六类断裂点：入口、需求、实施、事实、判断和交付。若缺少任务路由层，Agent 可能在错误流程中执行正确命令；若缺少需求与用例层，执行会建立在错误预期上；若缺少测试实施设计层，环境和工具错误会使 case 失效；若缺少执行证据层，结果无法复核；若缺少判断基线层，正常、异常和未知会被混淆；若缺少交付与沉淀层，测试经验会重新散落回聊天上下文。相反，若将这些层过度合并，例如把实施设计和执行证据合并，容易让工具选择、环境前置和实际证据混成一段执行叙述，最终削弱复核性。

### 4.1 任务路由层

当 Agent 拥有多个 skill、脚本和文档入口时，第一个问题不是如何执行，而是当前应该先进入哪条流程。真实测试任务可能是功能测试实施、失败排查、部署验证、远端 SSH 调查、日切检查、auto_case 执行、稳定性测试生命周期管理等。不同任务需要读取不同 skill、脚本、证据层和输出模板。

如果没有任务路由，Agent 可能拥有多个 skill，却不知道当前应该先使用哪一个。项目级 `docs/ai_workflows.md` 将用户请求映射到主 workflow，并声明子流程、必读文档和输出结构。未命中 workflow 时，该机制要求 Agent 显式说明未命中，而不是临时拼接流程。

这一层控制的是入口不确定性。

### 4.2 需求与用例层

测试用例的质量首先取决于需求基线的准确性。需求与用例层关注的是“应该测什么”：该层要求 Agent 不只依据单一通知或单段需求生成 case，而是先列出信息源，进行跨源甄别，再形成需求分析、覆盖清单、test point 和具体 case。

这一层强调三件事：

- 需求、代码、通知和用户澄清必须对齐。
- 理论覆盖和当前可执行范围必须区分。
- 每个 case 都要能回到覆盖清单。

这一层控制的是需求基线和覆盖不确定性。

### 4.3 测试实施设计层

Agent 在实施阶段最容易犯的错误之一，是把 case 当成可以立即执行的命令，而没有先确认环境、工具和证据条件。测试实施设计层的作用，是把 case 转化为可执行 runbook。它包含实施规划、工具选型、环境准备和逐 case 步骤。这里需要强调：工具选型是测试实施设计的一部分，不是测试实施之外的独立阶段。之所以单独展开，是因为它经常被 Agent 隐含在“执行 case”里。

测试实施设计至少要回答：

- 当前测试是否依赖特定包、二进制、配置、env、feature flag 或 mock 能力。
- 修改配置后如何证明运行态已经生效。
- 是否需要停止背景流量，避免证据污染。
- 每个 case 应使用现有工具、新增自动化 case、脚本、SQL、fixture、mock 还是人工复核。
- 工具是否具备断言能力和证据归因能力。
- 测试结束后如何恢复环境。

这一层控制的是环境和工具不确定性。

### 4.4 执行证据层

执行证据层解决的是“实际发生了什么”的问题。该层要求执行过程不只保留聊天摘要，还要记录 case ID、输入、运行态、关键标识、实际输出、断言结果和证据路径。

证据类型包括：

- 标识类：clOrdID、OrderId、trace ID、request ID。
- 日志类：应用日志、event.log、FIX、systemd journal。
- 报告类：自动化报告、CSV、HTML report。
- 运行态：进程命令、PID、配置、版本。
- 外部层：下游原始报文、mock 服务记录、监控指标。

这一层控制的是事实和归因不确定性。

### 4.5 判断基线层

测试产出并不自动等于测试结论。判断基线层关注的是，在面对日志、报告、状态差异和历史反例时，如何形成可复核的解释。该层要求 Agent 避免把所有非预期现象直接判为 bug，也避免把看起来常见的现象直接判为正常。通过业务字典、已知缺陷库、历史反例和跨层证据检查，测试产出被区分为正常、异常和未知。

三分法如下：

| 分类 | 判定口径 | Agent 输出要求 |
| --- | --- | --- |
| 正常情况 | 命中业务字典，证据链自洽 | 写入正常情况列表，说明证据 |
| 异常情况 | 命中异常字典、历史反例，或跨层证据不自洽 | 写入疑似 / 确认问题列表，继续补证据 |
| 未知情况 | 字典外现象、证据不足、业务口径未确认 | 标记待确认，不得写成正常或异常结论 |

这一层控制的是结论定性不确定性。

### 4.6 交付与沉淀层

测试结果只有写成可交接的记录和报告，才算完成工程交付。交付与沉淀层关注的是“如何让结果可交接、可复查、可复用”。该层要求测试报告从执行记录和覆盖矩阵提炼，避免新增执行记录里没有的结论。部分覆盖、需复测、本轮不执行和阻塞项需要显式写出。

其中，execution records 不只是结果归档，还承担反向反馈作用：当记录中出现未命中的 workflow、缺失的工具断言、无法归类的未知现象或模板字段不足时，这些事实会成为后续修订 rules、skills、templates 或 dictionaries 的依据。

测试结束后，Agent 还应形成测试工程反思候选，包括：

- 规则缺口。
- workflow 缺口。
- skill / 流程缺口。
- 模板缺口。
- 工具缺口。
- 字典缺口。

这些候选项经人工 review 后，才能进入长期知识库或技能体系。

这一层控制的是报告和经验沉淀不确定性。

### 4.7 人机协作边界

分层约束并不意味着所有环节都由 Agent 自主完成。更合理的协作方式是按风险分配责任。

| 环节 | Agent 可自主完成 | Agent 应提交人类确认 | 人类必须主导 |
| --- | --- | --- | --- |
| 任务路由 | 根据 workflow catalog 匹配主流程和子流程 | workflow 未命中或多 workflow 冲突 | 新增长期 workflow 口径 |
| 需求与用例 | 列信息源、做 coverage checklist、生成 case 草案 | 需求冲突、不可构造输入、验收口径不明 | 最终业务验收标准 |
| 测试实施设计 | 梳理环境前置、工具选型、runbook 和恢复步骤 | 高风险环境变更、缺少工具能力、需新增测试工具 | 生产级变更授权、关键环境使用策略 |
| 执行证据 | 执行命令、采集日志、整理关键标识和证据路径 | 证据链缺层、结果互相矛盾 | 高风险结论定责 |
| 判断基线 | 按字典、缺陷库和三分法做初步分类 | 字典外现象、业务口径未确认 | 新业务规则确认、缺陷最终定性 |
| 交付沉淀 | 生成执行记录、覆盖矩阵、报告草稿和反思候选 | 是否沉淀为 rule / skill / dictionary | 长期规则和团队流程变更 |

这种边界将 Agent 定位为测试工程协作者，而不是测试责任主体的替代者。

人机边界不是静态的，它随工程资产成熟度变化。workflow 命中率越高、业务字典覆盖越充分、模板和执行记录校验越完善，Agent 可自主完成的范围就越大；当资产薄弱、业务口径缺失或证据链不完整时，更多环节应回到人类确认。

## 5. 工程资产协同与维护

分层约束模型需要由真实工程资产承载，否则容易退化为抽象口号。本节不再重复六层模型，而是说明资产之间如何协同，以及如何避免规则、skill、模板和记录彼此漂移。

| 资产类型 | 职责 | 示例 |
| --- | --- | --- |
| `rules` | 放红线、强约束和强制入口 | `.cursor/rules/00-global-team-standards.mdc` |
| `workflows` | 放任务路由、主流程、子流程和输出结构 | `docs/ai_workflows.md` |
| `skills` | 放可复用流程和场景化操作方法 | `test-case-design-checklist`、`feature_test_execution_docs` |
| `dictionaries / defect libraries` | 放业务判断基线和历史反例 | `daycut_behavior_dictionary.md`、`known_defects.yaml` |
| `templates` | 放交付物结构 | 实施指南模板、执行记录模板、报告模板 |
| `execution records` | 放真实执行事实和证据 | `test_execution_record_<date>_<env>.md` |

六类资产的关系可以概括为：

```text
rules 放红线，
workflows 放路由，
skills 放步骤，
dictionaries 放判断基线，
templates 放结构，
records 放事实。
```

资产之间存在明确依赖关系：

| Source | Target | 依赖关系 |
| --- | --- | --- |
| `rules` | `workflows` / `skills` | 规定红线和强制入口，限制哪些动作必须进入正式流程 |
| `workflows` | `skills` / `docs` / `scripts` | 根据任务类型选择主流程，并指向需要读取或执行的资产 |
| `skills` | `templates` | 描述具体可复用步骤，并引用模板形成交付物 |
| `templates` | `execution records` / `reports` | 约束执行记录和报告的结构，避免聊天式散落输出 |
| `dictionaries / defect libraries` | 结论判断 | 为正常、异常、未知和历史反例提供判定基线 |
| `execution records` | `rules` / `workflows` / `skills` / `templates` / `dictionaries` | 保存本次真实执行事实，并反向暴露资产缺口 |

这种分工避免了两类常见问题。第一，避免把所有流程都塞进全局规则，导致规则臃肿且不可维护。第二，避免 skill 只写操作步骤，却没有 workflow 决定何时进入，也没有执行记录保存真实结果。

维护策略同样重要。长期规则只承载红线和强制入口，不承载长篇操作细节；workflow 负责路由和编排，不替代 skill；skill 负责可复用步骤，不记录单次执行事实；template 固化输出结构，不替代证据；execution record 只保存真实发生的过程，不写成计划或模板。若某次执行暴露流程缺口，应先进入反思候选，再由人类 review 后决定沉淀到哪类资产。

在论文方法论中，资产映射的意义不是罗列文件，而是说明每类资产如何控制一种 Agent 工作不确定性。

## 6. 案例研究：EXAMPLE-1001 sample-client fake-clock

### 6.1 案例背景

EXAMPLE-1001 的功能变更是：sample-client 新增用于联调和仿真测试的虚拟墙钟漂移能力，配合上游 mock 时钟场景验证 `dayOrderExpireTime` 逻辑。

核心公式为：

```text
虚拟当前时间 = 真实当前时间 + UPS_CLIENT_VIRTUAL_CLOCK_DRIFT_SEC
```

过期判断为：

```text
DayOrderExpireTime != 0 && 虚拟当前时间 >= DayOrderExpireTime
```

正 drift 会让订单更早过期，负 drift 会延后过期，`DayOrderExpireTime=0` 表示不过期。该能力只应在 fake-clock 构建中生效，普通 `sample-client` 和 `sample_client_debug` 不应受影响。

案例中涉及的主要系统名如下：

| 术语 | 含义 |
| --- | --- |
| `sample-client` | 示例业务系统 系统中连接下游交易模拟器 / 交易通道的客户端组件 |
| `guard` | 负责按配置拉起和管理业务进程的守护服务 |
| `auto_case` | 团队内部用于构造订单、执行断言和生成报告的自动化测试工具 |
| `event.log` | 服务端事件日志，用于观察订单请求、内部状态和连接器事件 |
| `nv-ext-msg` | 下游 某外部交易所 EXTP 原始消息层证据，用于确认是否继续南向发送 |
| `core-engine` | 算法单处理组件，部分算法单触发后会送单到 sample-client |

### 6.2 测试难点

该需求的测试难点不在于下单动作本身，而在于测试前提和证据链。

首先，fake-clock 能力依赖特定二进制和启动时 env。测试前必须确认运行的是 `sample_client_fake_clock_debug` 或对应 fake-clock 二进制，并且 `UPS_CLIENT_VIRTUAL_CLOCK_DRIFT_SEC` 是通过 guard `start_cmd` 注入，而不是只在 SSH shell 中设置。

其次，修改 guard 配置后必须重启 guard，使 guard 使用最新配置拉起 sample-client。每次切换二进制或 drift 后，都要记录 guard PID 与 sample-client PID 的前后变化。如果 PID 未变化，就不能继续执行依赖该配置的 case。

第三，`DayOrderExpireTime` 由 upstream-service 根据交易日历和日切口径计算后下发，不能由测试脚本任意传入。因此，执行时必须从 `event.log` 取真实字段，而不能只引用用例中的可读示例时间。

第四，普通单和算法单入口不同。普通 place-only case 可以用 auto_case 定向下单，不需要 `app.py`；算法单入口则需要先下算法单，再通过 `mockTransactionPrice` 触发行情，使 core-engine 送单到 sample-client。

这些难点使该需求成为检验 Agent 测试方法论的合适案例。

### 6.3 Agent 初期偏差

本案例中，Agent 初期出现过多类偏差。

| 偏差 | 表现 | 若未纠正的后果 |
| --- | --- | --- |
| 忽略环境前置 | 一开始关注下单逻辑，没有第一时间确认二进制、env、guard 配置和重启方式 | 即使订单结果符合预期，也无法证明是 fake-clock 行为 |
| 混淆工具前提 | 将普通下单和 app.py 前置混在一起 | 测试准备复杂化，且可能把工具健康问题误判为业务问题 |
| 工具选型不充分 | 倾向观察稳定性脚本，而不是新增定向 auto_case case | clOrdID 和输入不可控，证据无法归因到目标 case |
| 执行记录滞后 | 不是所有 case 一开始都按模板补齐 | 用户无法检查完整执行结果，报告阶段容易补写推断 |
| 错误理解算法单预期 | FC-014 初期按直接 reject 理解 | 算法单入口可能被错误判为失败，或漏掉终态闭环检查 |
| 过度要求日志 | 曾把合法 env 必须打印到 sample-client 日志当作检查点 | 非需求项会被误写成验收标准，导致不必要的失败结论 |

这些偏差说明，Agent 的问题不是完全不理解需求，而是缺少一套在执行前约束环境、工具、证据和结论的工程机制。

如果没有分层约束，本案例很可能出现一条“看似通过但实际无效”的路径：Agent 在普通 `sample_client_debug` 或 env 未生效的进程上执行下单，得到 ACK 后将 FC-002 写成通过；或者从稳定性背景流量中观察到类似过期拒单，却无法证明该订单使用了目标 drift。这样的结果并不能验证 fake-clock 行为，只是把一次普通订单现象误包装成测试结论。

### 6.4 方法论如何介入

首先，用例设计阶段对通知、代码和用户澄清进行了对齐，形成 18 个 case 和覆盖清单。这个阶段区分了理论输入与当前可执行输入。例如，`DayOrderExpireTime=0` 和真实已过期订单在当前环境下不能模拟，因此相关 case 被保留为需求语义，并反馈到测试实施设计层，转化为“本轮不执行 / 当前口径部分覆盖”的执行策略，而不是强行写成已执行。

其次，测试实施设计阶段先解决环境和工具，而不是直接下单。实施指南明确了目标环境、目标二进制、guard 配置、env 注入位置、重启方式、PID 记录、稳定性脚本停止、DayOrderExpireTime 取证方式和逐 case runbook。

工具选型也在这一阶段完成：

| 场景 | 工具选择 | 原因 |
| --- | --- | --- |
| 普通未过期 ACK | auto_case 独立 type `sample_fake_clock_expect_ack` | 输入可归因，有北向断言 |
| 普通过期拒单 | auto_case 独立 type `sample_fake_clock_expect_expired_reject` | 可断言 `39=8 / 150=8` |
| 算法单入口 | auto_case + app.py + `mockTransactionPrice` | 需要触发行情，让 core-engine 送单到 sample-client |
| 背景稳定性流量 | 不采用 | 订单不可控，证据不可精确归因 |

这里的“可归因”指测试工具能产生可追踪的订单标识，并能将输入、断言、北向回执和服务端事件对应到同一个 case。相比之下，稳定性脚本虽然持续产生订单，但订单目的、触发时间和断言目标不受本次 case 控制，因此不适合作为主验证工具。

工具选型也反向影响了执行证据层：既然选择 auto_case 独立 type，而不是稳定性背景流量，执行记录就必须保存每个 case 对应的 clOrdID、OrderId、`DayOrderExpireTime`、北向 FIX、event.log 和南向无发送证据，确保每条结论都能回到同一笔订单。

第三，执行过程中出现的偏差会反馈到前置层。例如 FC-014 初期被理解为“触发后直接新单拒绝”，但实际算法单路径需要先 ACK，再通过 mock 行情触发，最终形成 `ordStatus=4 / execType=4 / Day order expired` 的终态闭环。这个发现反馈到需求与判断基线层，修正了 case 预期，也反馈到工具选型层，确认算法单入口必须使用 `app.py` 和 `mockTransactionPrice`。

最后，执行记录保存了真实执行事实，包括环境、guard 配置、PID 变化、clOrdID、OrderId、`DayOrderExpireTime`、北向 FIX、event.log、南向无发送证据和覆盖矩阵。

层间反馈可以概括为：

| 反馈路径 | 触发事实 | 修正结果 |
| --- | --- | --- |
| 用例层 -> 实施设计层 | `DayOrderExpireTime=0` 和真实已过期订单当前不可构造 | 相关 case 从“应执行”调整为“本轮不执行 / 部分覆盖”，避免伪造输入 |
| 工具选型 -> 执行证据层 | 选择 auto_case 独立 type，而不是稳定性背景流量 | 执行记录必须按 clOrdID 保存输入、断言、FIX、event.log 和南向证据 |
| 执行证据层 -> 需求与判断基线层 | FC-014 实际是算法单触发后形成终态闭环，不是直接新单拒绝 | 修正预期为 `ordStatus=4 / execType=4 / Day order expired`，并检查订单闭环终态 |

### 6.5 执行结果

本轮共处理 18 个设计 case，最终状态如下：

| 状态 | Case | 说明 |
| --- | --- | --- |
| 通过 | FC-001、FC-002、FC-003、FC-009、FC-010、FC-011、FC-012、FC-013、FC-014、FC-016、FC-017 | 覆盖 drift=0、正漂移、非法 env、未设置 env、用户订单入口、算法单入口、普通 debug 回归和 fake-clock debug |
| 当前口径部分覆盖 | FC-005 | 负漂移只覆盖“不误拒正常未到期订单”，无法覆盖真实已过期输入 |
| 需复测 | FC-004 | 已验证超过边界会过期，但未达到严格“刚好等于边界”的精度 |
| 本轮不执行 | FC-006、FC-007、FC-008、FC-015 | FC-006/007/008 输入当前不可构造；FC-015 release 回归已由 UAT 人工完成，本轮不重复 |
| 不单独执行 / 已覆盖 | FC-018 | 合法 env 由 guard startCmd、运行态、PID 和订单行为覆盖；非法值由 fallback 日志覆盖 |

这个结果不是“全部通过”的成功叙事，而是一个真实测试交付结果。它保留了通过项、部分覆盖项、需复测项、本轮不执行项和已覆盖项。正是这些状态让测试报告具备可复核性。

### 6.6 反思沉淀

本案例结束后，测试过程中的纠偏并未停留在聊天记录里，而是形成了可继续维护的候选资产：

| 沉淀方向 | 具体内容 | 价值 |
| --- | --- | --- |
| 全局规则 | 测试执行前必须先判断环境、包、二进制、启动参数、env 和 mock 能力 | 防止后续 Agent 直接跳业务 case |
| workflow | 将功能测试实施、远端 SSH、部署、auto_case 等任务纳入 workflow catalog | 降低任务入口选择不确定性 |
| skill | 固化 sample-client 二进制切换和 `UPS_CLIENT_VIRTUAL_CLOCK_DRIFT_SEC` 配置流程 | 让 fake-clock 类需求具备可复用执行路径 |
| 模板 | 形成测试实施指南、执行记录、覆盖矩阵和测试报告模板 | 让执行事实从聊天上下文转为项目资产 |
| 工具 | 新增 auto_case 独立 type，区分预期 ACK、预期过期拒单和算法单终态 | 提升输入控制和断言能力 |
| 字典 / 口径 | 将不可构造输入、部分覆盖、需复测、本轮不执行等状态显式化 | 避免把测试限制误写成通过或失败 |

这部分沉淀说明，分层约束闭环的最后一步不是“写完报告”，而是将本次测试暴露的流程缺口转化为下一次 Agent 可复用的工程资产。

### 6.7 案例结论

EXAMPLE-1001 案例说明了本文方法论的核心观点：复杂功能测试中，Agent 的可靠性不是来自单次回答的正确性，而是来自分层约束对其行为的持续收敛。

在该案例中：

- 任务路由和规则让 Agent 先意识到环境前置。
- 用例设计澄清了理论输入与可执行输入。
- 测试实施设计补齐了二进制、env、guard、PID 和工具选型。
- 执行证据层保存了真实日志、标识和回执。
- 判断基线使不可构造输入和非需求日志要求不被误写成失败或通过。
- 覆盖矩阵、报告和反思沉淀保留了完整测试状态，并将经验转化为后续可复用资产。

## 7. 讨论

### 7.1 方法有效性

本文方法的有效性主要体现在三个方面。

第一，它让 Agent 的测试行为可控。通过 workflow、skill 和模板，Agent 不再只依赖上下文记忆决定下一步，而是在任务入口、实施设计和报告输出上有明确约束。

第二，它让测试结果可复核。执行记录要求保存真实输入、输出、关键标识和证据路径，使下一个工程师或 Agent 可以继续检查，而不是只能依赖聊天摘要。

第三，它让测试经验可沉淀。测试结束后的反思候选可以转化为规则、workflow、skill、模板、工具或业务字典，减少同类错误反复发生。

### 7.2 外部适用性

本文只完整展开了 EXAMPLE-1001 一个案例，但六层模型并不只服务 fake-clock 场景。当前项目中，已有多类任务可以映射到同一组约束层。

| 任务类型 | 重点约束层 | 说明 |
| --- | --- | --- |
| 日切检查 | 任务路由层、判断基线层、执行证据层、交付沉淀层 | 需要先命中日切 workflow，再使用业务字典、已知缺陷库和报告模板 |
| 稳定性失败排查 | 任务路由层、执行证据层、判断基线层 | 需要区分 rejected / failed / non_terminal，并通过跨层证据复核 |
| 部署验证 | 任务路由层、测试实施设计层、执行证据层 | 需要确认包、组件、guard 重启、PID 和运行态 |
| auto_case 功能回归 | 测试实施设计层、执行证据层、交付沉淀层 | 需要选择 case type、确认断言、记录报告和覆盖矩阵 |

这些任务没有在本文中作为完整案例展开，但它们说明该模型的层次划分具有跨场景复用潜力。后续仍需要更多完整案例验证其外部效度。

### 7.3 方法边界

本文方法也有边界。

首先，它不能保证 Agent 永远正确。它提升的是可控性和可复核性，而不是消除所有错误。

其次，它依赖工程资产的质量。若 workflow 不完整、skill 过时、业务字典缺失或工具没有断言能力，Agent 仍可能执行出低质量结果。

第三，它仍需要人类确认关键业务口径。尤其是涉及交易日历、日切、维护窗口、异常定性和高风险结论时，Agent 应明确事实、推断和待确认点，而不是替代人类责任判断。

第四，它有成本。完整分层约束需要维护 workflow、skill、模板、业务字典和执行记录，会增加测试前置工作量。对于输入输出明确、环境稳定、无需跨层证据、无需多人交接的简单冒烟测试，可以只轻量激活部分层次；当测试涉及环境前置、多层证据、业务判断、工具选型或跨人交接时，完整分层约束的收益通常大于成本。

第五，目前本文只完整展开了一个案例。该案例能说明方法的必要性和可落地性，但不足以证明方法在所有业务域中都同等有效。外部适用性仍需要更多功能需求验证。

### 7.4 后续工作

后续建设可以从四个方向推进：

- 建立测试工具能力矩阵，帮助 Agent 更稳定地完成工具选型。
- 开发执行记录质量检查脚本，自动发现漏 case、漏证据、漏恢复记录。
- 抽象通用业务字典模板，让正常 / 异常 / 未知三分法跨需求复用。
- 扩展 workflow catalog，覆盖更多功能测试任务类型。

## 8. 结论

本文提出了一种面向真实功能测试交付的 Agent 测试工程方法论。该方法论的核心不是追求 Agent 一次性正确，而是通过任务路由、测试实施设计、执行证据、判断基线和交付沉淀，把 Agent 工作中的不确定性显式化，并纳入可复核的工程过程。

随着 Agent 能力持续提升，具体的 workflow、skill、模板和字典可能会自动生成、自动校验甚至自动演进，但“将不确定性显式化并工程化管理”这一原则不会过时。未来的 Agent 测试工程可能从人工维护资产走向资产自动维护，但人类对关键业务口径、风险边界和最终责任的确认仍然是闭环的锚点。
