# 阶段 5 前置：论文论证骨架

论文题目：

```text
从用例设计到执行报告：一种可落地的 Agent 测试工程方法论
```

## 1. 本文主论点

本文的主论点是：

```text
面向真实功能测试的 Agent 能力建设，关键不在于让 Agent 一次性给出正确答案，而在于通过分层约束的测试工程闭环，将 Agent 的不确定性响应转化为可执行、可复核、可交接、可沉淀的测试交付过程。
```

这个论点包含三层含义：

1. Agent 在真实功能测试中的主要风险不是“不会生成用例”，而是缺少工程化流程约束。
2. 功能测试交付不是单点动作，而是跨越任务识别、用例设计、实施设计、执行取证、结果判断和报告同步的连续过程。
3. 方法论的目标不是消除 Agent 不确定性，而是让不确定性可见、可记录、可复核、可纠偏、可沉淀。

## 2. 核心概念

本文的核心概念定义为：

```text
分层约束的 Agent 测试工程闭环
```

它不是一个单一流程图，而是一组分层约束关系：

| 层次 | 控制的不确定性 | 主要资产 | 输出 |
| --- | --- | --- | --- |
| 任务路由层 | 用户请求进入错误流程 | `workflows` | workflow 命中结果、主流程、子流程 |
| 需求与用例层 | 需求基线错误、覆盖遗漏 | `skills`、用例模板 | 需求分析、覆盖清单、测试用例 |
| 测试实施设计层 | 环境误用、工具误用、执行不可落地 | `skills`、实施指南模板 | 环境前置、工具选型、逐 case runbook |
| 执行证据层 | 执行事实丢失、证据不可归因 | 执行记录模板、日志层规范 | case 状态、关键标识、证据路径 |
| 判断基线层 | 把未知写成结论、误报或漏报异常 | 业务字典、缺陷库、三分法 | 正常 / 异常 / 未知列表 |
| 交付与沉淀层 | 报告失真、经验散落 | 报告模板、反思机制 | 覆盖矩阵、测试报告、候选沉淀项 |

这六层共同构成论文的方法论主体。

## 3. 需要避免的偏移

本文不是：

- 通用大模型能力评测。
- 自动化测试平台设计。
- 单纯的测试用例生成方法。
- 完全无人值守测试执行方案。
- 某个 示例业务系统 功能的测试复盘报告。

本文是：

```text
一套面向真实功能测试交付的 Agent 测试工程组织方法。
```

因此，阶段 5 写初稿时不能把重点写散到“大模型很强”“测试自动化趋势”“Agent 未来会如何”等宽泛话题上。

## 4. 三个贡献点

阶段 5 初稿中，贡献点应压缩为三个，避免贡献列表过多导致主线发散。

| 贡献 | 说明 | 支撑材料 |
| --- | --- | --- |
| 提出分层约束模型 | 用任务路由、实施设计、执行证据、判断基线和交付沉淀约束 Agent 测试行为 | `agent_testing_methodology_framework.md` |
| 定义从用例到报告的测试交付闭环 | 将 Agent 测试从 case generation 扩展到实施设计、工具选型、执行记录、覆盖矩阵和报告 | `writing_plan.md`、`feature_test_execution_docs` 对应实践 |
| 用真实案例验证模型如何收敛偏差 | 用 EXAMPLE-1001 展示 Agent 初期偏差如何被流程和资产逐层纠正 | `case_study_example_1001.md` |

不建议把 `workflow`、`工具选型`、`异常嗅觉`、`执行记录` 分别列为独立贡献。它们应该作为分层约束模型中的组成机制，而不是把贡献点拆碎。

## 5. 论证链

阶段 5 初稿应围绕下面的链条展开：

```text
问题：Agent 在真实功能测试中存在高不确定性。
原因：真实测试不是单步生成，而是多阶段、多环境、多工具、多证据、多判断的工程活动。
方法：提出分层约束的 Agent 测试工程闭环。
机制：每一层约束一种不确定性。
验证：EXAMPLE-1001 案例中，Agent 初期偏差被逐层收敛。
结论：该方法不能消除不确定性，但能把它转化为可管理的测试交付过程。
```

这条链必须贯穿全文。每一章都应该服务其中一个环节。

## 6. 章节论证关系

### 6.1 摘要

摘要要回答四件事：

- 背景：Agent 能生成用例，但真实测试交付仍不稳定。
- 问题：缺少任务路由、实施设计、证据记录和判断基线。
- 方法：提出分层约束的 Agent 测试工程闭环。
- 结果：通过 EXAMPLE-1001 案例验证该方法能收敛 Agent 偏差并形成可复核交付。

摘要不应写成“本文介绍了某项目的一次测试过程”。

### 6.2 引言

引言的任务是制造问题张力：

```text
会写用例 != 能交付测试结果
```

应说明功能测试交付至少涉及：

- 任务类型判断。
- 需求与代码对齐。
- 环境和版本确认。
- 工具选型。
- 执行证据采集。
- 异常识别。
- 覆盖矩阵和报告。

引言最后引出本文主张：Agent 测试需要分层约束的工程闭环。

### 6.3 工程断点

本章回答 RQ1。

核心是先罗列 Agent 在真实测试中如何失败，以及这些失败会造成什么直接后果。不要在这一章提前展开六层模型的解法。

| 断点 | 直接后果 |
| --- | --- |
| 从用例直接跳执行 | 后续动作可能服务于错误目标 |
| 忽略环境前置 | case 结果无法证明目标功能 |
| 误用工具 | 输入不可控，证据不可归因 |
| 只看单层日志 | 结论缺少复核基础 |
| 缺少异常嗅觉 | 隐蔽问题被漏掉或误报 |
| 报告新增推断 | 团队同步口径被误导 |

本章为后文“分层约束”铺垫。

### 6.4 方法论框架

本章回答 RQ2、RQ3、RQ4、RQ5、RQ6、RQ7 的主体部分。

建议按六层写，而不是按资产清单写：

1. 任务路由层。
2. 需求与用例层。
3. 测试实施设计层。
4. 执行证据层。
5. 判断基线层。
6. 交付与沉淀层。

每一层固定写：

- 解决什么不确定性。
- 依赖什么资产。
- 产出什么交付物。
- 防止什么典型错误。

本章还需要补充“为什么是六层”的反事实论证：缺少任一层会造成哪类断裂，过度合并某些层又会造成哪些复核问题。

这样论文会更像方法论，而不是工具说明书。

### 6.5 资产映射

本章的作用是证明方法论不是抽象口号，而是已有项目资产支撑。

资产映射应服务六层模型：

| 六层模型 | 对应资产 |
| --- | --- |
| 任务路由层 | `docs/ai_workflows.md`、`AGENTS.md` |
| 需求与用例层 | `test-case-design-checklist` |
| 测试实施设计层 | `feature_test_execution_docs`、实施指南模板 |
| 执行证据层 | 执行记录模板、`log_layers` |
| 判断基线层 | `daycut_behavior_dictionary.md`、`known_defects.yaml` |
| 交付与沉淀层 | 报告模板、覆盖矩阵、反思候选 |

本章不应逐文件展开太长，避免变成项目文档目录。

### 6.6 案例研究

案例研究回答：

```text
这套方法在真实测试中如何发挥作用？
```

EXAMPLE-1001 的叙事结构应是：

1. 需求本身要求特殊二进制、env、guard 重启和真实 `DayOrderExpireTime` 证据。
2. Agent 初期偏差暴露工程断点。
3. 用例设计澄清理论输入与可执行输入。
4. 测试实施设计补齐环境和工具选型。
5. 执行记录让结果可复核。
6. 覆盖矩阵保留通过、部分覆盖、需复测、本轮不执行等真实状态。

案例不是为了证明“全部通过”，而是证明方法能让复杂测试变得可管理。

### 6.7 讨论与边界

本章要保持克制。

可以写：

- 该方法提升的是可控性和可复核性，不是保证 Agent 永远正确。
- 对业务字典和缺陷库依赖较强。
- 对工具能力和日志可观测性有要求。
- 当前只有一个完整案例，后续需要更多需求验证。
- 通过日切检查、稳定性失败排查、部署验证、auto_case 功能回归等任务类型说明外部适用性潜力。
- 用人机协作边界说明哪些环节 Agent 可自主完成、哪些应交由人类确认、哪些必须由人类主导。

不要写：

- 完全自动化。
- 替代测试工程师。
- 大幅提升效率但没有量化证据。

### 6.8 结论

结论回扣主论点：

```text
Agent 测试工程的关键不是让 Agent 一次性正确，而是通过分层约束，把不确定性纳入可复核的测试交付过程。
```

## 8. 阶段 5 初稿写作规则

阶段 5 写 `agent_testing_methodology_paper.md` 时遵守以下规则：

1. 不机械拼接阶段 1 到阶段 4。
2. 每章开头先说明该章服务哪一段论证链。
3. 案例材料只选能支撑论点的证据，不复刻执行记录。
4. 贡献点保持三个，不拆成过多小贡献。
5. “Agent 不确定性治理”作为贯穿逻辑，不单独膨胀成大章。
6. 不夸大自动化效果，不写无量化依据的效率提升。
7. 所有正式结论都回到资产或案例证据。
