# 《从用例设计到执行报告：一种可落地的 Agent 测试工程方法论》写作规划

## 1. 论文定位

本文定位为一篇工程方法论论文，目标不是证明 Agent 能否参与测试，而是说明如何把 Agent 纳入可执行、可复核、可交接、可沉淀的功能测试流程。

论文要回答的问题是：

```text
Agent 如何从“会设计测试用例”，进一步走到“能完成测试实施、证据记录和执行报告”？
```

论文主线覆盖：

```text
Workflow 任务路由
-> 测试用例设计
-> 测试实施设计
   -> 实施规划
   -> 工具选型
   -> 环境准备
   -> 逐 case runbook
-> 测试执行与证据采集
-> 执行记录
-> 覆盖矩阵
-> 测试报告
-> 反思沉淀
```

## 2. 核心论点

Agent 要真正参与功能测试，不能停留在用例生成或命令执行层面，而必须被纳入一套工程化闭环。该闭环通过 `rules` 约束红线、`workflows` 完成任务路由、`skills` 承载流程、`dictionaries / defect libraries` 提供业务判断基线、`templates` 固化交付物、`execution records` 保存证据，使 Agent 的测试工作具备可执行、可复核、可交接和可沉淀的特征。

本文强调的是“约束 Agent 完成测试工程闭环”，而不是强调 Agent 的单点智能。

## 3. 论文贡献点

| 贡献点 | 说明 |
| --- | --- |
| 提出“任务路由到执行报告”的 Agent 测试工程闭环 | 明确 Agent 测试不只是 test case generation，而是覆盖流程路由、规划、执行、记录、报告的完整链路。 |
| 引入 Workflow 任务路由层 | 明确 Agent 在进入 skill 前必须先识别任务类型、选择主 workflow，并联动子流程、证据层和输出模板。 |

## 7. 章节写作规划

### 7.1 引言：从“会写用例”到“能交付测试结果”

本章说明论文背景和必要性。Agent 已能辅助生成测试用例，但“写出用例”不等于“完成测试”。功能测试真正难的是落地执行：环境是否正确、工具是否合适、输入是否可构造、断言是否可靠、证据是否闭合、结果是否可复核。

本章应输出：

- 问题背景
- 论文目标
- 论文贡献
- 章节安排

### 7.2 相关实践与本文定位

本章简要定位本文与现有 Agent 测试实践的关系。重点不是做完整学术综述，而是区分：

- prompt-based test generation：偏用例生成。
- agentic execution：偏命令和工具调用。
- CI / DevOps Agent：偏已有流水线和失败信号处理。

本文区别在于关注从用例设计到执行报告的完整测试交付闭环。

### 7.3 Agent 测试落地的工程断点

本章定义 Agent 在功能测试中容易失败的地方。

| 工程断点 | 表现 | 风险 |
| --- | --- | --- |
| 需求基线不稳 | 未甄别需求、代码、通知之间的差异 | 用例设计错误 |
| 环境前置缺失 | 未确认版本、包、配置、进程、env | case 结果无效 |
| 工具选型缺失 | 用不适合的脚本或背景流量观察 | 证据不可归因 |
| 断言缺失 | 只下单或只观察日志 | 无法判断通过失败 |
| 证据链不闭合 | 只看单层日志 | 结论风险高 |
| 异常嗅觉不足 | 只核对预期断言，不主动识别日志、状态、数量、时间、链路中的可疑信号 | 漏掉隐藏缺陷 |
| 执行记录缺失 | 结果只在聊天里 | 无法交接和复查 |
| 报告失真 | 把推断写成结论 | 误导团队判断 |
| 经验未沉淀 | 每次重新踩坑 | 方法不可复用 |

本章要说明：问题不是简单的提示词不够长，而是缺少工程结构。本章只写失败现象和直接后果，不提前展开六层模型的解法。

### 7.4 方法论总览：从任务路由到执行报告的闭环

本章提出论文核心模型：从任务路由到执行报告的闭环模型。

```text
需求 / 代码 / 通知 / 历史问题
        ↓
Workflow 任务路由
        ↓
测试用例设计
        ↓
测试实施设计
  - 实施规划
  - 工具选型
  - 环境准备
  - 逐 case runbook
        ↓
测试执行与证据采集
        ↓
执行记录
        ↓
覆盖矩阵
        ↓
测试报告
        ↓
反思与沉淀
```

核心表：

| 阶段 | 输入 | 关键动作 | 输出 | 防错机制 |
| --- | --- | --- | --- | --- |
| Workflow 路由 | 用户请求 / AGENTS 入口 | 匹配主流程、识别子流程和必读资产 | workflow 命中结果 | 未命中显式说明 |
| 用例设计 | 需求/代码/通知 | 信息源甄别、覆盖设计 | `test_case_design` | checklist back-check |
| 测试实施设计 | 测试用例、环境、工具、mock 能力 | 环境前置、执行口径、工具选型、逐 case runbook | `test_execution_guide`、工具选型表 | 前置清单、工具能力矩阵 |
| 执行记录 | 实际执行 | 记录输入、输出、证据 | `execution_record` | 状态枚举 |
| 报告输出 | 覆盖矩阵 | 提炼结论 | `test_report` | 不新增未验证结论 |

本章还需要说明为什么是六层：入口、需求、实施、事实、判断、交付分别对应不同断裂点，缺少任一层都会导致测试交付不可复核或不可沉淀。

### 7.5 Workflow 任务路由：让 Agent 先选对流程

本章对应资产：

```text
docs/ai_workflows.md
AGENTS.md 中的 AI 工作流入口
```

重点写：

- workflow catalog 解决的是“任务入口判断”问题，不是具体执行步骤。
- Agent 先匹配主 workflow，再读取主 skill、子流程、必读文档和输出模板。
- 同一请求可能命中多个 workflow，需要选一个主 workflow，再按子流程联动。
- 未命中 workflow 时必须显式说明，回到规则和 skill 入口判断，不能临时编造流程。
- Workflow 层让测试体系从“有很多 skill”升级为“知道什么时候用哪个 skill”。

### 7.7 阶段二：测试实施设计：规划、工具选型与环境准备

本章对应资产：

```text
.cursor/skills/feature_test_execution_docs/SKILL.md
.cursor/skills/feature_test_execution_docs/references/test_execution_guide_template.md
```

重点写：

- Agent 不能从 case 直接跳到执行
- 必须先完成环境前置判断
- 必须在实施设计内完成工具选型，工具选型不是测试实施之外的独立阶段
- 工具选型必须先于逐 case 执行步骤，明确现有工具、新增 case、脚本、mock、断言和证据归因方式
- 必须形成逐 case 可执行 runbook
- 恢复步骤必须成为实施指南的一部分
- 执行记录要求必须在执行前说明

### 7.8 测试实施关键环节：工具选型

本章说明工具选型是 Agent 测试实施设计中的必选环节。它不独立于测试实施之外，但必须被显式写出。

工具选型维度：

| 维度 | 判断问题 |
| --- | --- |
| 输入控制 | 是否需要精确构造输入 |
| 断言能力 | 工具是否支持自动断言 |
| 证据归因 | 是否会混入背景流量 |
| mock 能力 | 是否需要模拟外部事件 |
| 环境影响 | 是否会影响其它测试 |
| 可重复性 | 是否能稳定复现 |
| 开发成本 | 是否值得新增工具 |

本章要提出“测试工具能力矩阵”作为后续工作。

### 7.9 阶段三：测试执行、证据采集与执行记录

本章对应资产：

```text
.cursor/skills/feature_test_execution_docs/references/test_execution_record_template.md
```

重点写：

- 执行记录不能把计划当结果
- 每个 case 要有状态、输入、实际结果、断言、证据和结论
- 每个结论必须能回到证据
- 查不到也要写
- 事实、推断、待确认点分开

状态枚举：

```text
通过
失败
需复测
当前口径部分覆盖
本轮不执行
不单独执行但已覆盖
阻塞
```

### 7.10 阶段四：从测试产出中发现可疑问题

本章说明 Agent 不能只按预设断言判定通过，还需要从测试产出中识别可疑信号，形成接近人类测试工程师的异常敏感度。

重点写：

- 预期断言通过不等于没有问题。
- Agent 需要主动检查“意外情况”：额外拒单、异常日志、状态机不自洽、数量差异、时间边界偏差、链路缺口、历史反例相似模式。
- 可疑信号必须先写成事实或疑点，不能直接升级为 bug 结论。
- 异常嗅觉需要从“感觉”落到可操作机制：业务字典、正常情况列表、异常情况列表、未知情况列表、已知缺陷库、历史反例、跨层证据清单、桶级样本复核和执行勾稽。

实践框架：

| 机制 | 作用 | 输出 |
| --- | --- | --- |
| 业务字典 | 先定义哪些行为在当前环境和业务口径下属于正常、异常或待确认 | 场景 -> 预期分类 |
| 正常情况列表 | 防止 Agent 把已知正常现象误报为 bug | 已核实正常项 |
| 异常情况列表 | 固化明确问题、强疑点、必须深挖信号 | 疑似/确认问题项 |
| 未知情况列表 | 对字典外现象不擅自定性，先标记待确认 | 待业务/开发复核项 |
| 历史反例库 | 遇到相同模式时优先按同类异常复核 | 样本和命中依据 |
| 跨层一致性检查 | 检查不同证据层是否自洽 | 证据链闭合情况 |

三分法：

| 分类 | 判定口径 | Agent 输出要求 |
| --- | --- | --- |
| 正常情况 | 命中业务字典，且证据链自洽 | 写入正常情况列表，说明证据 |
| 异常情况 | 命中异常字典、历史反例，或跨层证据不自洽 | 写入疑似/确认问题列表，继续补证据 |
| 未知情况 | 字典外现象、证据不足、业务口径未确认 | 标记待确认，不得写成正常或异常结论 |

可疑信号示例：

| 信号类型 | 示例 | 处理方式 |
| --- | --- | --- |
| 状态不自洽 | 北向成功但内部状态为拒绝 | 回到完整链路复核 |
| 数量不一致 | CSV 桶数量与 event 统计对不上 | 按状态域、责任层、reason 重新过滤 |
| 时间边界异常 | 边界 case 晚于或早于预期窗口 | 标记需复测或重新设计执行窗口 |
| 链路缺口 | 有 TO_VENDOR 无 FROM_VENDOR | 补查下游原始日志 |
| 历史反例相似 | 与已知缺陷样本模式接近 | 按同类异常优先复核 |

### 7.13 方法论效果、边界与后续工作

效果：

- 减少跳过环境前置的风险
- 让工具选择显式化
- 让执行过程可复核
- 让报告可以回溯到证据
- 把测试经验沉淀为 skill 和模板

边界：

- 仍需要人类确认业务口径
- 高风险结论仍需人工 review
- 工具能力矩阵尚未完善
- 执行记录质量检查还未自动化
- 方法论需要更多不同需求验证

后续工作：

- 建立测试工具能力矩阵
- 扩展 workflow catalog 覆盖更多功能测试任务
- 开发执行记录质量检查脚本
- 自动生成团队渠道报告草稿
- 让测试用例 skill 和实施 skill 显式交接
- 抽象通用业务字典模板和字典外现象回补流程
- 用更多需求验证模板通用性

## 8. 写作质量要求

本文应避免：

- 空泛表达，例如“赋能测试体系”“打造智能闭环”。
- 把 EXAMPLE-1001 写成流水账。
- 夸大为“完全自动化测试”。
- 把工具清单当方法论。
- 把执行记录原文直接贴进论文。

本文应强调：

- Agent 为什么会犯错。
- 方法论如何约束 Agent。
- 文档和记录如何让测试结果可复核。
- 哪些仍然需要人类判断。
- 哪些经验已经沉淀为 skill。
