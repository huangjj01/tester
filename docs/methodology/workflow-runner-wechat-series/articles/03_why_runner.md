## 三、正文结构

### 1. 开头 hook

前两篇我们确认了一个问题：文档约束不等于执行约束。治理体系做得再完整，只要 Agent 执行过程中缺少一道"拦住它"的门禁，规则就可能被绕过。

但接下来的解法选择，很容易走偏。

有人的第一反应是：再改 Prompt，把规则写得更强势、更命令式。
有人想做一个大而全的 Agent 管理平台，加界面、加审计、加权限。
有人想上 Agent 编排框架，用 DAG、状态机、事件总线把所有流程编排一遍。

我们最终选了一条不太一样的路。

### 2. 为什么不是这些解法

先说为什么排除了常见选项。

**改 Prompt 更强势？** 在我们的实践中，约束力度和指令遵循之间不是线性关系。规则从"你应该先做 A 再做 B"改成"你必须先做 A 才能做 B，否则禁止继续"——效果有改善，但仍不稳定。原因在前两篇已经拆过：上下文丢失后，规则没有持久化状态支撑，Agent 恢复时可能跳过。

**做一个管理平台？** 对于一个本地仓库驱动、几个人用的 Agent 工作流来说，维护一套 Web 服务的成本远大于收益。我们的需求不是"多租户""可视化面板""审计日志"，而是"在 CLI 层面拦住 Agent 不让跳步骤"。

**上 Agent 编排框架？** 编排框架解决的是 Agent 之间的协调问题。我们要解决的是单个 Agent 内部流程推进问题。用 DAG 编排来管"Agent 有没有先做环境前置"，是高射炮打蚊子。

所以我们回到了最朴素的问题：**怎么用最低成本，给 Agent 的执行流程加一道真正拦得住的门？**

### 3. Workflow Runner 是什么

Workflow Runner 是一个 CLI 工具。它做的事情很简单：

1. 为一次测试实施任务创建一个本地 run 目录
2. 在这个 run 中定义好步骤序列和依赖关系
3. Agent 每完成一步，通过 Runner 做门禁校验
4. 校验通过才推进到下一步
5. 校验失败则阻断，Agent 必须补齐后重试

Runner 就是一层壳。它不自动执行测试，不自动 SSH 到远端，不替代 skill 里的具体方法论，也不替代人类的判断。它只负责两件事：

- **流程推进**：告诉 Agent 下一步是什么
- **门禁校验**：检查这一步的产物是否满足最低结构要求

```text
用户请求
  → Agent 命中测试实施任务
  → Agent 启动 Runner（CLI）
  → Runner 创建 run 目录 + checklist
  → Agent 按 next step 产出 artifact
  → Runner 校验 artifact（标题、非空、表格、有效数据）
  → 通过 → 推进到下一步
  → 不通过 → blocked，Agent 必须补齐
  → 目标产物达成
```

### 4. Runner 的职责边界

为了避免 Runner 变成又一个过度设计的产物，我们在设计时明确划了边界。

Runner 负责的事情：定义步骤和顺序；记录每步状态（pending / blocked / completed / not_required_yet）；校验 artifact 的结构（标题是否存在、内容是否为空、表格是否有效数据）；阻止跳步和跳依赖；支持中断后恢复（通过 `status` / `next` 读取持久化状态）。

Runner 不负责的事情：不自动执行真实测试，不自动连接远端环境，不替代现有 skill 里的方法论，不替代人工判断，不自动修改规则或 skill，不自动发消息通知，不做多 Agent 并发控制。

这条边界很重要。Runner 的价值不在于它能做多少事，而在于它**只做一件事**——拦住 Agent 跳步骤——并且把这件事做可靠。

### 5. Target 模式：不强求跑完全程

测试实施不是每次都需要跑完整闭环。有时候用户只需要整理实施指南，有时候只需要生成执行记录，有时候要从头到尾跑到最终报告。

Runner 通过 target 模式支持这一点：

| target | 说明 | 必经终点 |
| --- | --- | --- |
| `execution_guide` | 只整理测试实施指南 | 第 5 步 |
| `execution_record` | 生成或维护执行记录 | 第 6 步 |
| `report` | 生成最终报告 | 第 7 步 |
| `full` | 完整测试实施闭环 | 第 8 步（反思） |

当目标是 `execution_guide` 时，后面的执行记录、报告、反思步骤不会被要求必须完成。它们的状态标记为 `not_required_yet`——不阻塞，但也不假装做了。

如果用户后续要继续往下走，可以基于同一个 run 继续推进，不需要重新来一遍。

### 6. 为什么"轻量本地"是当下更合适的方案

Runner 本质上是一个 Python CLI + 本地 YAML 配置 + 本地 JSON 状态文件。没有服务端，没有数据库，没有 UI。

这个选择是有意为之的。不需要额外部署和维护，因为它就是一个 CLI。状态落在仓库 `.runs/` 目录下，和代码在一起。Agent 可以直接调用，不需要额外 adapter。`run.json` 和 `checklist.json` 是普通 JSON 文件，人类随时可以打开检视。`.runs/` 已加入 `.gitignore`，不污染主仓库，用完可以直接丢。

对于一个本地开发环境下的 Agent 测试工作流来说，这已经够了。未来如果需要跨团队协作或审计追溯，再考虑服务化——但那是下一步的事，不是第一步。

### 7. 收束：Runner 的价值判断

Runner 的价值不在于它多厉害，而在于它补上了一个很具体的缺口。

在 Runner 之前，我们的治理体系能告诉 Agent"你应该先确认环境，再做工具选型，再写实施指南"。但如果 Agent 直接写了实施指南，没人拦。

在 Runner 之后，如果 Agent 没有通过环境前置的门禁校验，它就做不了工具选型。如果工具选型表里只有占位符数据，它就进不了实施指南步骤。

这不是把 Agent 管死，而是让流程有了最低的执行保障。
