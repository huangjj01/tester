# 为什么写了那么多 Agent 规范，结果还是一地鸡毛？

## 一、文章定位

- 篇次：第 1 篇
- 目标读者：正在落地 AI 测试 Agent 的测试工程师；想用 Agent 但担心不可控的研发负责人
- 这篇唯一核心观点：文档约束不等于执行约束，Agent 规范写得再多，如果没有流程门禁机制，它仍然可以跳步骤、漏证据、绕规则
- 这篇希望读者看完记住的一句话：规则写在 Markdown 里，不等于 Agent 被 Markdown 管住了

## 三、正文结构

### 1. 开头 hook

你大概也经历过这种事——

团队花了不短的时间，把 Agent 的规则文档写得很漂亮：什么该做、什么不能做、遇到什么先走哪个 skill、看到什么任务类型先读哪份 workflow。写完之后，大家觉得终于可以放心了。

然后 Agent 转头就跳过了环境前置检查，直接产出一份"已完成"的测试实施指南。

没有人收到任何阻断。它甚至不觉得自己做错了——因为文档只是告诉它"应该做什么"，没有人在流程里真正拦住它。

这是我们在项目里真正把 Agent 治理体系搭起来之后，得到的第一个教训：规则写在 Markdown 里，不等于 Agent 被 Markdown 管住了。

### 2. 幻觉：有文档就等于有约束

这种假象很容易建立。

你打开仓库，`AGENTS.md` 写了强制 skill 入口，写了红线禁止项，写了十几种场景下的必读文档。`docs/ai_workflows.md` 列了十多个 workflow，每个都有触发条件、主 skill、子流程、必须输出项。`.cursor/skills/` 目录下有二十几个 skill，涵盖部署、排查、日切、稳定性、混沌测试、报告输出。`toolset/` 目录下有正式脚本入口。

看起来方方面面都管到了。

但如果你仔细想一个问题：**谁来检查 Agent 有没有真按这些文档走？**

答案是——没有人。或者更准确地说，只有人类事后逐条去对，才能发现它漏了什么。

### 3. Agent 真的会跳步骤，而且不自知

这不是假设，是我们实际碰到过的事：

- Agent 被要求生成测试实施指南时，直接跳过工具选型，产出一份没有断言依据的 runbook。
- Agent 被要求做测试执行记录时，没有确认过环境版本和进程状态，直接开始填写用例结果。
- Agent 被要求整理测试报告时，跳过测试工程反思段落，或者用空泛表述蒙混过关。

这不是模型能力问题。Agent 确实读到了规则。问题在于：它跳过规则的时候，没有任何机制将其阻止。

### 4. 根因：文档是"可读提示"，不是"执行门禁"

为什么会这样？

原因其实很朴素：现有的所有治理资产——`AGENTS.md`、workflow catalog、skill、操作规范——它们的存在形式是 **文档**。文档对 Agent 的作用机制是"提示"：我把规则加载到你的上下文里，你读到了就按规则做。

但"提示"和"门禁"是两个完全不同的东西。

提示的意思是：我告诉你应该做，但你不做也不会被拦。
门禁的意思是：你如果不做，流程走不下去。

一个简单的类比：把公司考勤规则写在员工手册里，是提示。把闸机装在公司门口，是门禁。有人不打卡也不是因为没看过手册，而是因为没打卡也能进门。

Agent 也是一样。它不是没读规则，它是读了规则之后，发现不遵守也不会有任何后果。

### 5. 再想深一步：为什么提示会失效

把约束写在文档里，对 Agent 来说有几个结构性弱点：

**第一，状态不落盘。** Agent 读了规则之后，它的执行进度只存在于当前聊天上下文里。一旦对话被 compact、被中断、或者隔了一天再继续，之前走到哪步、哪些产物已经落盘、哪些门禁已经通过——全部丢失。

**第二，中断不可恢复。** Agent 被打断后，恢复靠的是重新读文档、重新猜进度。而文档里没有任何关于"当前状态"的记录，只有"应该怎么做"的描述。

**第三，缺少阻止机制。** 文档可以说"必须先完成 A 才能做 B"，但如果 Agent 直接做了 B，没有任何机制把它挡回去。

这三个弱点不是写更多文档能解决的。写更多文档只是增加了更多"提示"，并没有在流程里加上一道真正的门。

### 6. 收束：如果要让 Agent 真按流程走

写到这里，方向其实已经很清楚了：

如果想让约束真正生效，需要的不是"更多规则"，而是一个能让规则变成可检查状态的机制——一个 Agent 绕不过去的流程壳。

这个壳不需要多复杂。它不需要变成一个平台，不需要引入数据库，不需要部署 Web 服务。它只需要做到几件事：

- 把流程步骤定义清楚
- 把执行状态落到本地文件
- 在关键节点做门禁校验
- 校验不过就不让进入下一步

听起来很简单。但"把规则变成门禁"这件事，比"把规则写成文档"难得多。

下一篇，我们会具体拆解：为什么现有体系已经把"怎么说"解决得很好了，但"怎么执行"的断点到底卡在哪里。

## 四、边界与待补项

- 已验证事实：现有治理体系的文档结构和体量（AGENTS.md、ai_workflows.md、skills 目录均为仓库实际资产）；Agent 跳步骤的行为是项目实际经历过的问题
- 工程判断："文档是提示不是门禁"的判断属于作者对问题根因的工程归纳
- 仍待补证据：Agent 跳步骤的具体截图或日志（后续可补）
- 当前不能写死的结论：不能说"所有 Agent 都会这样"，只能表述为"在纯文档约束体系下，这类问题普遍存在"
