### 3. 失败点 1：同秒冲突

**Runner-TC-002：连续快速 `start` 同名需求时，run_id 冲突。**

这个失败很直接。Runner 的 run_id 格式是 `YYYYMMDD_HHMMSS_<name>`。当用户在同一秒内连续两次 `start` 同一个需求名时，两次产生了完全相同的 run_id。

第二次 `start` 没有报错——它直接复用了第一次的 run 目录。这意味着如果一个 Agent 因为某种原因快速重试了 start 命令，它可能不知道自己在操作的是哪个 run。

**为什么这个问题值得讲？**

因为它暴露了一个典型的"设计时没想到、测试时才暴露"的工程盲点。设计文档说"run_id 必须包含时间戳"，但没有说"时间戳精度必须防止同秒冲突"。这不是逻辑错误，而是对现实使用模式的覆盖不足。

### 4. 失败点 2：重复 step id 未被拒绝

**Runner-TC-039：workflow 配置中存在重复的 step id 时，Runner 仍然创建了 run。**

这个问题更微妙。我们用一份故意包含重复 step id 的 YAML 配置去 start Runner。预期行为是 start 失败并报错。实际行为是 Runner 正常创建了 run——它在加载配置时没有做 step id 唯一性校验。

**为什么这个问题值得讲？**

因为 workflow 配置是 Runner 门禁的"元规则"。如果配置本身有缺陷（比如同一个 step 定义了两次），Runner 的门禁行为就不可预测。配置校验是门禁的门禁——缺了这层，整套机制的根基就不牢。

### 5. 修复与复测：从红到绿

两个失败点修复后，我们做了针对性复测。

TC-002 的复测：连续快速 start 同名需求，两次产生了不同的 run_id：
- 第一次：`20260520_162001_054969_feature-retest`
- 第二次：`20260520_162001_330722_feature-retest`

修复方案是在时间戳中加入微秒精度。简单、直接、无副作用。

TC-039 的复测分成了两个检查点：
- 非法 YAML：start 退出码 1，错误信息指向 YAML 解析失败 ✓
- 重复 step id：start 退出码 1，错误信息为 `workflow config error: duplicate step id(s): input_sources` ✓

两个失败点均已复测通过。

### 6. 这 2 个失败告诉我们什么

两个失败看起来都不大，但它们的共同特征很有代表性：

**它们都不是"核心逻辑错误"，而是"边界条件覆盖不足"。**

核心逻辑——步骤推进、门禁校验、依赖阻断、target 模式——全部通过。出问题的是"连续快速操作"和"配置自身缺陷检测"这种边角场景。

这恰好说明了一件事：**Runner 的核心设计是成立的，但第一版实现的边界加固还需要持续补齐。**

这也是为什么我们把这两个 case 标记为后续回归的固定冒烟项——每次改动 run_id 生成或 workflow 配置加载逻辑时，优先执行这两条。

### 7. 补充观察：不是失败但值得记录的

除了 2 个明确失败，执行记录中还有几条值得留意的观察：

- **Runner-TC-032**：target 未完成时执行 `render`，当前实现会输出已完成 artifact（不报错）。不是 bug，但需要在文档中明确这个行为。
- **Runner-TC-040**：`checklist.json` 损坏时命令失败且不覆盖原文件（这是好的），但错误提示是 Python traceback 而非友好消息。可改进，但不阻塞功能。

这些观察项没有被标记为失败，但被完整记录在了执行记录里。这也是 Runner 方法论自身的一个体现：**你不只记录通过和失败，还要记录"通过但有条件"的情况。**

### 8. 收束：可信度来自闭环

回到标题的问题：Runner 值不值得做？

从验证结果看：

- 核心逻辑（步骤推进、门禁校验、依赖阻断、target 模式、中断恢复）**全部验证通过**。
- 边界条件暴露 2 个缺陷，**修复后复测通过**。
- 验证范围覆盖 6 个维度、43 条用例。

这不能说明 Runner 完美无缺——它是第一版，肯定还有更多边角场景没覆盖到。但它至少说明了一件事：

**这不是一个只有设计文档的方案。它有实现、有测试、有失败、有修复、有复测。这个闭环本身就是可信度的来源。**
