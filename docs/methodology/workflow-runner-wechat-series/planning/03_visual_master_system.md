# Workflow Runner 专题系列视觉母版

## 1. 母版目标

这份母版不是给设计师“自由发挥”的，而是先把系列视觉秩序定住，保证后续无论谁补正文、谁补图片，最后出来的东西都像一个完整专题，而不是 6 篇各说各话。

这个专题的视觉目标只有三条：

1. 一眼看上去像“工程方法论”，不是泛 AI 宣传图。
2. 有传播感，适合公众号头图、转发卡片、封面裁切。
3. 能和真实工程证据融合，不会因为太花哨把信息压没。

## 2. 系列视觉关键词

建议统一围绕下面 6 个关键词展开：

- 门禁
- 轨道
- 收束
- 校验
- 可追溯
- 有边界的控制感

如果后续再扩写视觉提示词、封面 brief、设计说明，都不要跑出这个语义场。

## 3. 总体风格定义

### 视觉气质

- 不是“未来感炫技”
- 不是“企业宣传海报”
- 不是“程序员截图拼贴”
- 是“高级媒体封面 + 工程结构图”的混合风格

### 关键词翻译成画面

| 抽象词 | 画面化表达 |
| --- | --- |
| 门禁 | 发光闸门、拦截线、校验框、状态关卡 |
| 轨道 | 直线流程、分叉收束、受控路径 |
| 收束 | 杂乱输入进入统一框架 |
| 校验 | 对勾、红点、状态提示、字段检查 |
| 可追溯 | 时间线、run 目录、artifact 卡片、审计链 |
| 边界 | 虚实分层、明确保留的人类判断节点 |

## 4. 色彩系统

### 主色板

| 角色 | 颜色 | 用途 |
| --- | --- | --- |
| 背景主色 | `#0D1B2A` | 大面积底色、封面背景 |
| 深层辅助 | `#111827` | 深色块、局部压暗区域 |
| 次级中性色 | `#98A2B3` | 注释、次级信息、网格线 |
| 高亮色 | `#46C2CB` | 门禁、关键路径、标题点睛 |
| 辅助白 | `#E5E7EB` | 主要文字、线条、卡片描边 |
| 风险红 | `#EF4444` | 失败点、blocked、异常 |
| 修复绿 | `#22C55E` | 通过、复测成功、闭环 |

### 配色原则

- 一个画面里高亮色不要超过 2 种。
- 青色只给“主路径/主结论”，不要到处点。
- 红色只在“失败、阻塞、断裂”场景使用，避免平时滥用。
- 如果是第 5 篇数据型封面，允许红绿同场，但背景一定保持克制。

## 5. 字体与文案落版原则

### 标题气质

标题要像媒体专题，不像 PPT 汇报页。建议偏“短、硬、准”。

### 落版规则

- 封面大标题最多 2 行。
- 每行尽量控制在 6~11 个汉字的视觉长度。
- 英文词如 `Workflow Runner` 可以单独成一行，增强识别度。
- 不要把完整正文标题原封不动塞进封面。

### 封面字数建议

| 类型 | 建议长度 |
| --- | --- |
| 中文封面标题 | 8~16 字 |
| 英文副标题 | 1~3 个词 |
| 封面副标 | 10~18 字 |

## 6. 版式系统

## A 版：冲突型封面

适用于第 1、2 篇。

特征：

- 左右或上下形成失控对比
- 标题压得更大
- 画面冲突更明显
- 信息元素不宜过多

适合表达：

- 规则失效
- 文档和执行脱节
- Agent 偏航

## B 版：方案型封面

适用于第 3、4 篇。

特征：

- 结构更稳定
- 中心主体清晰
- 门禁、流程、框架感更强
- 可以带一张主结构示意

适合表达：

- 方案登场
- Runner 机制
- 流程治理

## C 版：验证型封面

适用于第 5 篇。

特征：

- 数字主导
- 结果导向
- 局部红绿对照
- 适合做成传播卡片

适合表达：

- 用例数量
- 失败数
- 复测闭环

## D 版：边界型封面

适用于第 6 篇。

特征：

- 留白更大
- 画面更克制
- 不追求冲击，追求成熟度

适合表达：

- 边界
- 演进
- 人机协作

## 7. 封面固定元素

建议整个系列统一保留一组弱品牌元素：

- 左上角小标签：`Agent Testing`
- 右上角期数标签：`01 / 06` 这种格式
- 底部或角落弱标识：`Workflow Runner Series`

作用：

- 建立连载识别度
- 即使单篇转发出去，也能看出是一个系列

## 8. 正文插图规范

正文图不要和封面图抢戏，职责要分清：

| 图类型 | 目标 | 形式 |
| --- | --- | --- |
| 主逻辑图 | 讲清结构 | 流程图、架构图、状态图 |
| 证据图 | 建立可信度 | 表格摘要、测试结果、前后对比 |
| 说明图 | 降低理解门槛 | 目录结构图、步骤拆解图 |

### 正文图原则

- 每张图只传达 1 个核心意思。
- 图里文字别太小，公众号手机端必须能看清。
- 如果一张图字太多，拆成两张，不要硬塞。
- 证据图比抽象图更重要，尤其是第 5 篇。

## 9. 截图处理规范

如果后续文章里要放终端、目录、状态文件截图，建议统一处理，不要直接裸贴。

### 处理方式

- 保留真实命令和输出
- 增加深色外框和轻标题条
- 局部高亮关键字段，比如 `run_id`、`blocked`、`target achieved`
- 如果一张截图太长，只截核心区域

### 不建议的做法

- 整页终端原样长截屏
- 五颜六色标注一堆箭头
- 截图过小让手机端看不清

## 10. 现有资产复用策略

### 直接可复用

- `03_gate_check` 适合作为“门禁”类结构图基础
- `03_runner_architecture` 适合作为“Runner 总流程”基础
- `01_delivery_gap` 适合作为“为什么文档不等于执行”的基础图

### 建议二次改造

- 封面图建议保留结构，重做标题和局部氛围
- 正文图建议保留逻辑，压缩文字，增强手机端可读性

### 暂不建议复用

- 任何已经强绑定旧系列标题文案的成图
- 任何画面过满、字过多的旧封面

## 11. 给后续写作 agent 的协作接口

后续负责文章正文的 agent，不需要设计图片，但需要按下面格式给设计留位：

```text
[插图位]
图类型：封面 / 主逻辑图 / 证据图
图目的：这一张图要解决什么理解问题
图依据：引用哪份真实材料
图重点：希望读者一眼看到什么
```

只要文章里按这个格式留位，我后面补图会非常顺。

## 12. 最终交付建议

如果后面真的开始出图，建议每篇最终至少交 3 个文件：

1. 公众号头图
2. 正文主逻辑图
3. 一张适合转发传播的摘要卡片

这样一篇文章就同时具备：

- 公众号正式发布
- 朋友圈/群转发
- 文章内解释复杂结构

三种传播能力。
