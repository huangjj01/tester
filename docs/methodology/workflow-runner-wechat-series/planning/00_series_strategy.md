# Agent 测试 Workflow Runner 公众号连载总策划

## 1. 专题定位

本专题聚焦一个非常具体、也很容易引发共鸣的问题：

**团队明明已经写了很多 Agent 约束文档、skill、操作规范，但 Agent 依然可能跳步骤、漏证据、绕门禁，最后交不出可信的测试结果。**

公众号连载不直接讲“大而全的 Agent 方法论”，而是抓住一个足够尖锐、足够工程化、也足够容易传播的切口：

**怎么把“写在文档里的要求”，变成 Agent 真绕不过去的可执行门禁。**

这套选题适合面向三类读者：

- 正在落地 AI 测试 Agent 的测试工程师
- 想把 Agent 用起来、但担心不可控的研发负责人
- 关注 Agent 工程治理、流程治理、质量治理的 AI 工程化实践者

## 2. 连载目标

这个系列不以“讲清全部实现细节”为目标，而以三个传播目标为核心：

1. 让读者先被问题击中：为什么文档约束不等于执行约束。
2. 让读者记住一个方法：Workflow Runner 是把规则变成门禁的一种工程解法。
3. 让读者相信这不是概念包装：仓库里已经有设计、测试用例、执行记录、失败复测记录等真实材料可支撑。

## 3. 写作红线

- 不凭空编造“线上落地效果”“团队规模收益”“效率提升百分比”。
- 不虚构未发生过的事故、对话、冲突、业务背景。
- 不把设计稿当成“已经全面落地”的事实。
- 不把单次本地验证写成“已在所有复杂 workflow 中稳定运行”。
- 涉及结论时，优先引用现有材料中的真实证据：设计文档、测试用例、执行记录、复测记录、现有配图资产。

## 4. 推荐连载结构

建议做 **6 篇主线连载**。原因是 6 篇比 3 篇更能形成栏目感，比 8 篇更容易完结；同时可以把“问题定义”“核心方案”“真实验证”“边界反思”拆开，利于传播和追更。

| 篇次 | 文章主标题候选 | 核心任务 | 传播抓手 | 证据基础 |
| --- | --- | --- | --- | --- |
| 第 1 篇 | 为什么写了那么多 Agent 规范，结果还是一地鸡毛？ | 打痛点，建立问题张力 | 共鸣、吐槽、反常识 | `AGENTS.md`、`docs/ai_workflows.md`、设计文档背景段 |
| 第 2 篇 | 文档会说话，Agent 不一定会照做：问题到底卡在哪 | 拆解“文档约束失效”的根因 | 认知升级、结构化拆解 | 设计文档第 1~4 节 |
| 第 3 篇 | 从文档约束到可执行门禁：我们为什么做 Workflow Runner | 正式抛出 Runner 方案 | 概念命名、工程方案感 | 设计文档第 5~8 节 |
| 第 4 篇 | 不是再造平台，而是加一道门：Workflow Runner 怎么工作 | 讲清步骤、状态、target、门禁 | 架构图、流程图、低成本落地 | 设计文档、配置与目录结构 |
| 第 5 篇 | 43 条用例、2 个失败、1 次复测：Runner 值不值得做 | 用测试结果建立可信度 | 真实验证、翻车与修复 | 执行记录、复测记录 |
| 第 6 篇 | 真正有价值的，不是把 Agent 管死，而是让交付可追溯 | 总结边界与演进方向 | 价值升华、边界感、格局感 | 设计文档非目标、执行记录反思段 |

## 5. 每篇文章的逻辑结构模板

每篇都建议使用同一套结构，这样更适合公众号读者的阅读习惯，也方便后续批量成稿。

### 标准结构

1. **开头冲突句**
   直接抛矛盾，不铺垫，不做行业大背景。
2. **一个具体场景**
   用 1 个真实、可复述的工程场景开题，比如“已经有 AGENTS、workflow catalog、skills、toolset，但 Agent 还是能跳过环境前置”。
3. **问题拆解**
   解释为什么会这样，不急着给方案。
4. **核心观点**
   每篇只保一个主观点，不能一篇里塞三个中心论点。
5. **工程证据**
   插入设计截图、流程图、测试记录表、失败复测摘要。
6. **结论回收**
   收回到“这件事为什么重要”，同时压一句下篇预告。

### 推荐篇幅

- 主文：2200~3200 字
- 图：2~4 张
- 金句框：2 处以内
- 小标题：4~6 个

## 6. 每篇的详细提纲

## 第 1 篇：为什么写了那么多 Agent 规范，结果还是一地鸡毛？

### 文章目标

先把读者拉进来，不急着讲 Runner。重点是让做过 Agent 落地的人产生“这就是我们”的感觉。

### 标题池

- 为什么写了那么多 Agent 规范，结果还是一地鸡毛？
- AGENTS.md 写得越认真，Agent 越可能当没看见
- 你以为你在管理 Agent，其实你只是在安慰自己
- 文档写了，流程也写了，为什么 Agent 还是会乱跑

推荐主标题：

**为什么写了那么多 Agent 规范，结果还是一地鸡毛？**

### 逻辑结构

1. 先写常见幻觉：以为有文档就等于有约束。
2. 再写真实现象：Agent 会漏环境前置、跳过工具选型、直接给结论。
3. 再写原因：文档是“可读提示”，不是“执行门禁”。
4. 最后埋钩子：如果要让 Agent 真按流程走，需要把规则变成可检查状态机。

### 必须落的证据

- `AGENTS.md` 中关于 workflow、skill、Runner 的入口约束
- `docs/ai_workflows.md` 在体系中的定位
- `test_agent_workflow_runner_design.md` 背景与目标

### 传播点

- 强共鸣标题
- 开头适合截成朋友圈转发文案
- 可以带一点工程吐槽，但不能失控成情绪文

## 第 2 篇：文档会说话，Agent 不一定会照做：问题到底卡在哪

### 文章目标

把问题从“Agent 不听话”升级为“治理机制不闭环”。

### 标题池

- 文档会说话，Agent 不一定会照做：问题到底卡在哪
- 真正失效的不是提示词，而是执行闭环
- Agent 失控，很多时候不是模型问题，是工程问题
- 规则写在 Markdown 里，门禁却没写进流程里

推荐主标题：

**文档会说话，Agent 不一定会照做：问题到底卡在哪**

### 逻辑结构

1. 把现有治理资产列出来：规则、workflow、skills、toolset。
2. 指出它们已经解决了“怎么说”的问题，但没彻底解决“怎么执行”的问题。
3. 拆出几个关键断点：
   - 规则只存在文本层
   - 状态不落盘
   - 中断不可恢复
   - 缺少阻止跳步的门禁
4. 引出下一篇：Runner 的价值不是更复杂，而是把断点补上。

### 必须落的证据

- 设计文档中的总体背景、目标、非目标、适用范围
- 现有材料目录图或资产映射

### 传播点

- 这篇很适合被转给管理者和工程负责人
- 标题里要有“不是模型问题，是工程问题”这种判断力

## 第 3 篇：从文档约束到可执行门禁：我们为什么做 Workflow Runner

### 文章目标

正式定义专题主角。把 Runner 讲成一个清晰的工程选择，而不是一个“新造轮子”。

### 标题池

- 从文档约束到可执行门禁：我们为什么做 Workflow Runner
- Agent 治理最缺的，不是更多规则，而是一道真门禁
- 让 Agent 真按流程干活，我们补了一个很小但很关键的东西
- 不是让 Agent 更聪明，而是让流程更难被绕过

推荐主标题：

**从文档约束到可执行门禁：我们为什么做 Workflow Runner**

### 逻辑结构

1. 说明为什么不是改 Prompt、不是补更多文档、不是上大平台。
2. 解释 Runner 的职责边界：
   - 不替代 skill
   - 不替代人工判断
   - 不自动执行真实测试
   - 只负责流程推进和门禁校验
3. 解释为什么“轻量本地流程”是当下更合适的方案。
4. 引出“target 模式”和“逐步推进”的设计思想。

### 必须落的证据

- 设计文档中的目标、非目标、总体设计、目标产物模式

### 传播点

- 这一篇是整个系列的“方法论封面”
- 最适合做精致主视觉图

## 第 4 篇：不是再造平台，而是加一道门：Workflow Runner 怎么工作

### 文章目标

把 Reader 真正带进机制内部，看清楚它到底怎么卡住流程、怎么恢复、怎么推进。

### 标题池

- 不是再造平台，而是加一道门：Workflow Runner 怎么工作
- 8 个步骤、4 种 target、1 套门禁：Runner 的核心结构
- 我们没有做一个平台，只做了一个 Agent 绕不过去的流程壳
- Agent Workflow Runner 的关键，不在界面，在状态推进

推荐主标题：

**不是再造平台，而是加一道门：Workflow Runner 怎么工作**

### 逻辑结构

1. 先给总流程图。
2. 解释 8 个步骤各自解决什么问题。
3. 解释 target 模式为什么重要。
4. 解释门禁规则为什么不能只检查“标题存在”。
5. 解释 `status / next / complete / validate / render` 的价值。

### 必须落的证据

- 设计文档中的 8 步 workflow、门禁规则、文件结构
- workflow config 与 run 目录结构

### 传播点

- 适合工程读者收藏
- 适合做“架构长图 + 一张表总结”

## 第 5 篇：43 条用例、2 个失败、1 次复测：Runner 值不值得做

### 文章目标

这是可信度最强的一篇。不要写成测试报告，而要写成“我们拿真实验证去拷问这个方案是否成立”。

### 标题池

- 43 条用例、2 个失败、1 次复测：Runner 值不值得做
- 设计说得再漂亮，也得拿失败用例说话
- 我们拿 43 条测试用例，专门找 Workflow Runner 的麻烦
- 真正让人放心的，不是方案图，而是失败后怎么补上

推荐主标题：

**43 条用例、2 个失败、1 次复测：Runner 值不值得做**

### 逻辑结构

1. 先摆结果：首轮 41/43 通过。
2. 专门展开两个失败点：
   - 同秒同名 `run_id` 冲突
   - 重复 `step id` 未被拒绝
3. 再讲为什么这两个问题很有代表性。
4. 最后写复测通过，证明这不是 PPT 方案，而是闭环工程。

### 必须落的证据

- `test_agent_workflow_runner_execution_record_20260520_local.md`
- `test_agent_workflow_runner_retest_record_20260520_local.md`

### 传播点

- 数字特别抓人
- “失败后修复”比“全都成功”更有说服力

## 第 6 篇：真正有价值的，不是把 Agent 管死，而是让交付可追溯

### 文章目标

最后一篇负责拔高，但不能空。要把“边界感”写出来，让读者觉得这个团队不是在鼓吹万能方案。

### 标题池

- 真正有价值的，不是把 Agent 管死，而是让交付可追溯
- Agent 治理的终点，不是更严，而是更可验证
- 我们为什么不想把 Workflow Runner 做成一个大而全平台
- 把 Agent 管得太死，不一定是好事

推荐主标题：

**真正有价值的，不是把 Agent 管死，而是让交付可追溯**

### 逻辑结构

1. 先写边界：Runner 不替代判断，不覆盖全部 workflow。
2. 再写价值：可追溯、可恢复、可阻断、可沉淀。
3. 再写下一步演进方向：
   - 更多 workflow
   - 更强 schema 校验
   - 更好的失败提示
   - 与知识沉淀闭环联动
4. 最后收束到一句核心判断：
   真正的问题不是“Agent 会不会写”，而是“团队能不能验证它交付了什么”。

### 必须落的证据

- 设计文档非目标
- 执行记录中的未覆盖项、反思候选、工具缺口

### 传播点

- 很适合做系列收官
- 也适合单篇外发，吸引管理层和工程治理视角读者

## 7. 发布顺序建议

推荐按“问题 -> 根因 -> 方案 -> 机制 -> 验证 -> 边界”顺序发布，不建议一上来就发实现细节。

原因：

- 先发实现细节，传播会偏窄，只会吸引少量强技术读者。
- 先发痛点和根因，更容易破圈到测试负责人、研发经理、AI 落地团队。
- 把“43 条用例、2 个失败、1 次复测”放在第 5 篇，更容易形成“前面不是空讲，后面真有证据”的观感。

## 8. 每篇都必须补齐的真实材料

正式写作前，每篇都建议按下面清单做一次过稿检查。

| 检查项 | 要求 |
| --- | --- |
| 事实依据 | 每个核心观点都能指向现有文档、代码、记录或截图 |
| 结果口径 | 若只在本地验证过，就明确写“本地验证” |
| 图表来源 | 说明是复用现有图、从现有资产改图，还是后续新制图 |
| 数据真实性 | 不写未经记录支持的百分比、工时收益、缺陷率变化 |
| 边界说明 | 明确哪些是已落地，哪些是待扩展 |

## 9. 推荐配图策略

公众号要有“高大上”的观感，但不能俗套。建议统一成一套视觉语言：

- 主色：深海军蓝、冷银灰、青色高亮
- 关键词：门禁、流程、状态机、工程秩序、可追溯
- 风格：科技感 + 编辑感，不要泛 AI 紫色炫光风
- 图类型：
  - 封面图：大标题 + 强视觉隐喻
  - 逻辑图：流程、状态、层次关系
  - 证据图：测试结果表、失败点摘要、复测闭环

已有可复用素材见：

- `docs/methodology/agent-testing-methodology/publish-series/diagrams/premium/`
- `docs/methodology/agent-testing-methodology/publish-series/diagrams/covers/`
- `docs/methodology/agent-testing-methodology/publish-series/diagrams/output_premium/`

## 10. 推荐写作节奏

如果你们准备按真实落地推进再写，建议按下面节奏执行：

1. 先确定 6 篇标题和顺序，不急着写正文。
2. 先给每篇绑定“可用证据材料”和“待补证据”。
3. 先出封面和 1 张主逻辑图，统一视觉调性。
4. 先写第 1、3、5 篇，因为这三篇最容易形成传播闭环。
5. 第 2、4、6 篇作为体系化补充，围绕前面三篇的反馈再微调。

## 11. 最小可执行落地方案

如果想先低成本试水，不必一次做完 6 篇，可以先发 3 篇种子内容：

1. `为什么写了那么多 Agent 规范，结果还是一地鸡毛？`
2. `从文档约束到可执行门禁：我们为什么做 Workflow Runner`
3. `43 条用例、2 个失败、1 次复测：Runner 值不值得做`

这 3 篇已经能构成一个完整传播闭环：

- 有痛点
- 有方案
- 有验证

后续如果反馈好，再补机制拆解和边界升华篇。
