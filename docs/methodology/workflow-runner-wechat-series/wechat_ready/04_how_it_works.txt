不是再造平台，而是加一道门：Workflow Runner 怎么工作


Runner 的设计哲学是"最少够用"。它不追求覆盖所有场景，只追求在测试实施这一个 workflow 里，把两件事做可靠：防跳步，防中断后乱套。

这一篇把它的内部结构打开来看。

【图片：主逻辑图——8 步线性序列，每步之间有依赖箭头】


一、8 步，强制顺序

第一版测试实施 workflow 固定为 8 步：

第 1 步，输入资料确认——测的是什么？依据是什么？
第 2 步，测试范围与执行口径——测什么、不测什么？
第 3 步，环境前置判断——环境就绪了吗？版本对不对？
第 4 步，测试工具选型——现有工具能覆盖吗？需要新增吗？
第 5 步，测试实施指南——可执行的 runbook。
第 6 步，测试执行记录——真实跑的时候发生了什么？
第 7 步，最终报告——结论是什么？
第 8 步，测试工程反思——哪些规则、工具、流程需要沉淀？

顺序强制。每一步有前置依赖——不满足前置，后面进不去。

为什么要强制？因为 Agent 最容易犯的错就是"跳到后面"。直接写实施指南却没做工具选型，直接写报告却没有执行记录。强制顺序是最朴素的防跳步手段。


二、门禁：不是查标题在不在，是查内容有没有

如果只检查"文件有没有"或"标题存在不存在"，Agent 写一个空标题就能过关。

第一版门禁做了三层：

标题必须存在。每个步骤的产出文件必须包含配置中定义的必需标题。比如"环境前置判断"必须有：目标环境、版本/包/分支、服务/进程/配置、启动参数/环境变量、mock/外部依赖、恢复基线。

标题下必须有非空正文。标题存在不够，标题到下一个标题之间必须有内容。空章节不算通过。

表格类校验更严。对"测试工具选型"这种以表格为主的步骤：表格必须存在、表头必须包含必需列、必须至少有 1 行有效数据、有效数据不能只包含模板占位符。

校验失败时，Runner 把步骤标记为"已阻断"，写入具体校验失败原因。Agent 必须修复后重新提交。不修就进不了下一步。


三、状态落盘：进度不再只活在聊天里

Runner 的所有状态落在两个 JSON 文件里。

一个记录整体状态：当前在哪步、目标产物是什么、整体状态是运行中还是被阻断。

另一个记录每个步骤的状态：哪些已完成、哪些待执行、哪些被阻断、阻断原因是什么。

这解决了一个核心问题：Agent 的执行进度不再只活在聊天上下文里。对话中断、compact、隔天再来——Agent 都可以读取这两个文件恢复进度。不靠记忆，靠文件。


四、中断恢复：最实际的能力

测试实施任务跨越多天、多轮对话是常态。Runner 把中断恢复作为第一版核心能力，不是 nice-to-have。

恢复只需要两步：查看当前各步骤状态，获取当前应执行步骤。

恢复后的规则：不得凭聊天上下文猜进度——必须以状态文件为准。如果当前被阻断，先处理校验失败原因。如果当前产出文件已写了一部分，在原文件基础上补全，不覆盖有效内容。恢复后仍然要通过校验，不能直接标记完成。

无论中断多少次，流程推进的状态是确定的、可追溯的、不依赖记忆的。

五、6 个命令，覆盖完整周期

start——创建新的 workflow run。
status——查看当前各步骤状态。
next——获取当前应执行步骤和具体要求。
complete——提交步骤完成并触发校验。
validate——全局校验是否已达成目标。
render——合并产出文件生成目标文档。

一个典型流程：start 创建 run → next 看该做什么 → Agent 写产出文件 → complete 提交校验 → 通过则 next 进入下一步 → 逐步推进 → validate 全局校验 → 目标达成。


六、一切透明

每次 run 产生一个独立目录：整体状态文件、步骤状态文件、workflow 配置副本、每步的产出文件、执行日志。

.runs/ 目录加入 .gitignore，不污染主仓库。但在本地，所有状态和产出都是普通文件——人类随时可以打开检视、核对、甚至手动修正。

七、简单但有效

没有界面，没有数据库，没有服务端。

但它解决了一个之前解决不了的问题：让 Agent 的执行流程从"可建议"变成"可检查、不通过时会卡住"。
