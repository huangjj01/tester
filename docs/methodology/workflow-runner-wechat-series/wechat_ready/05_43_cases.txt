43 条用例、2 个失败、1 次复测：Runner 值不值得做


43 条用例。2 个失败。1 次复测。

这三个数字，就是我们拿来拷问 Workflow Runner 的全部弹药。

前面几篇讲了设计、讲了定位、讲了结构。但方案图画得再好看，最终要回答一个问题：它真的拦得住吗？

这一篇不讲设计。只讲验证。

【图片：封面——"43 / 2 / 1"三个数字最大化呈现】


一、43 条用例，专门找麻烦

我们没有写几个 happy path 就宣布收工。43 条用例覆盖了 6 个维度，从基本功能到边界异常，刻意往 Runner 的薄弱处去戳：

命令基本行为——6 个 CLI 命令全覆盖。
门禁校验——标题缺失、内容为空、表格全是占位符，一一试过。
Target 模式——四种目标产物各自的步骤状态和 validate 行为。
中断恢复与幂等——blocked 后恢复、半成品 artifact、重复 complete。
配置异常——非法 YAML、重复 step id、配置文件缺失。
非目标边界——确认 Runner 不会偷偷改规则、不会连远端、不会发通知。

结果：41 条通过，2 条失败。

核心逻辑全部站住了。翻车的是边角。

【图片：证据图——覆盖矩阵可视化，大面积绿 + 两个红点】


二、第 1 个失败：同秒冲突

连续快速 start 同一个需求名，两次产生了完全相同的 run_id。

原因很朴素：run_id 的时间戳只精确到秒。同一秒内启动两次，id 就撞了。第二次 start 没报错，直接复用了第一次的 run 目录。

这意味着：如果 Agent 因为某种原因快速重试了 start 命令，它可能不知道自己在操作哪个 run。

设计文档写了"run_id 必须包含时间戳"，但没写"时间戳精度必须防止同秒冲突"。这不是逻辑缺陷，而是对真实使用模式的估计不足——一个典型的"设计时没想到、测试时才暴露"的盲点。


三、第 2 个失败：配置缺陷没拦住

用一份故意包含重复 step id 的 YAML 配置去 start Runner。预期是 start 失败报错。实际是 Runner 正常创建了 run——它在加载配置时根本没做 step id 唯一性校验。

这个问题比第一个更值得重视。

workflow 配置是 Runner 门禁的"元规则"。如果配置本身有缺陷——比如同一个 step 定义了两次——Runner 的门禁行为就不可预测。配置校验是门禁的门禁，缺了这层，整套机制的根基就不牢。


四、从红到绿：修复与复测

修复方案都不复杂。

同秒冲突：在时间戳中加入微秒精度。简单、直接、无副作用。复测结果——连续快速 start 同名需求，两次产生了不同的 run_id。

重复 step id：加载配置时做唯一性校验。复测结果——start 退出码 1，错误信息明确指出哪个 step id 重复。

两个失败点均已复测通过。

【图片：对比图——两个失败点"修复前（红）→ 修复后（绿）"】


五、2 个失败说明了什么

它们有一个共同特征：都不是核心逻辑错误，而是边界条件覆盖不足。

步骤推进、门禁校验、依赖阻断、target 模式——这些核心链路全部通过。出问题的是"连续快速操作"和"配置自身缺陷检测"这种边角场景。

这恰好说明了一件事：Runner 的核心设计是成立的。但第一版实现的边界加固还需要持续补齐。

我们把这两个 case 标记为后续回归的固定冒烟项——每次改动 run_id 生成或配置加载逻辑时，优先跑这两条。


六、不是失败，但值得记下来

除了 2 个明确失败，还有几条观察：

target 未完成时执行 render，当前实现会输出已完成的部分（不报错）。不是 bug，但行为需要在文档里写清楚。

状态文件损坏时命令失败且不覆盖原文件（这是好的），但错误提示是 Python traceback 而非友好消息。能改进，不阻塞。

这些没被标记为失败，但被完整记录下来了。你不只记录通过和失败，还要记录"通过但有条件"的情况——这本身也是 Runner 方法论在自我示范。


七、可信度不来自全部通过，来自闭环

回到标题的问题。

Runner 值不值得做？如果 43 条全部通过，反而会让人怀疑测试是不是走过场。

真正有说服力的是这个闭环：有实现 → 有测试 → 有失败 → 有修复 → 有复测 → 闭环。

这不是一个只有设计文档的方案。它被 43 条用例拷问过，翻过车，补上了，再验证了一遍。

这个闭环本身就是可信度的来源。
