为什么写了那么多 Agent 规范，结果还是一地鸡毛？


规则写在 Markdown 里，不等于 Agent 被 Markdown 管住了。

这是我们把 Agent 治理体系搭到相当完整之后，得到的最大教训。不是规则不够多。规则已经多到打开仓库目录会晕的程度。问题在于：没有任何东西在检查 Agent 是不是真按规则走了。

最危险的不是 Agent 会出错，而是它没做完的时候，看起来像已经做完了。

【图片：封面——"规则很多 vs 结果仍然失控"的视觉冲突】


一、规则多不是重点，拦不住才是

我们的仓库里有什么？

规则入口文件写了强制 skill 入口、红线禁止项、十几种场景下的必读文档。Workflow catalog 列了十来个 workflow，每个都有触发条件、主 skill、子流程、必须输出项。Skills 目录下有二十多个 skill，涵盖部署、排查、稳定性、报告输出。Toolset 目录下有正式脚本入口。

文档化治理做到这个程度，"Agent 应该怎么做"这件事已经被回答得很清楚了。

但回答清楚了不等于拦住了。Agent 跳过某个步骤时，不会有任何弹窗、任何报错、任何阻断冒出来告诉你"它没做完"。你只有等它交出结果、人工逐条核对时，才有可能发现它漏了什么。

而很多时候你甚至不会去核对——因为它产出的东西看起来很完整。


二、Agent 跳步骤，而且不自知

这不是偶发，是结构性问题。我们反复碰到的情况：

Agent 被要求生成测试实施指南时，直接跳过工具选型，产出一份没有断言依据的 runbook。

Agent 被要求做测试执行记录时，没有确认过环境版本和进程状态，直接开始填写用例结果。

Agent 被要求整理测试报告时，跳过测试工程反思段落，或者用空泛表述蒙混过关。

这不是模型笨。Agent 确实读到了规则。问题是它跳过规则之后，没有任何东西拦它——它自己不会意识到自己跳了，你也不会立刻发现。

产出看起来是完整的。结构看起来是对的。但中间缺了关键步骤，你得用经验去一条条对着看才能发现。

【图片：主逻辑图——左侧"一摞治理文档"，右侧"Agent 实际执行路径"，中间缺失的那道"门"】


三、根因：文档是提示，不是门禁

所有治理资产——规则入口、workflow catalog、skill、操作规范——存在形式都是文档。文档对 Agent 的作用机制是"提示"：加载到上下文里，读到了就按规则做。

但提示和门禁是两回事。

提示：我告诉你应该做，你不做也不会被拦。
门禁：你如果不做，流程走不下去。

把考勤规则写在员工手册里是提示，把闸机装在门口是门禁。有人不打卡不是因为没看过手册，而是因为没打卡也能进门。

Agent 也一样。它不是没读规则，它是发现不遵守也没有后果。


四、写更多文档解决不了

把约束写在文档里，对 Agent 有三个结构性弱点：

状态不落盘——执行进度只活在当前聊天上下文里。对话中断后，走到哪步、哪些门禁通过了——全部丢失。

中断不可恢复——被打断后恢复靠重新读文档、重新猜进度。文档里没有"当前状态"，只有"应该怎么做"。

缺少阻止机制——文档可以说"必须先完成 A 才能做 B"。但如果 Agent 直接做了 B，没有任何机制挡它。

这三个弱点不是写更多文档能解决的。更多文档只是更多"提示"。流程里仍然没有一道门。

【图片：说明图——三个断点并列】


五、方向

如果想让约束真正生效，需要的不是更多规则，而是一个 Agent 绕不过去的流程壳——步骤定义清楚，状态落到本地文件，关键节点做校验，校验不过就进不了下一步。

听起来简单。但"把规则变成门禁"比"把规则写成文档"难得多。
