# Feature Test Execution Docs

## Runner 启动与门禁

当用户要求以下任一产物时，Agent 必须先启动 Runner：

- 测试实施指南 / 测试工具选型 / 测试执行记录 / 覆盖矩阵 / 最终测试报告 / 团队报告草稿 / 根据已有需求落地执行方案

启动命令：

```bash
python toolset/test_agent_runner.py start test_execution --name <需求编号或功能名> --target <target>
```

target 选择：

| 用户要求 | target |
|---------|--------|
| 只整理测试实施指南 | `execution_guide` |
| 生成或维护执行记录 | `execution_record` |
| 生成最终报告或团队报告草稿 | `report` |
| 完整测试实施闭环 | `full` |

Runner 校验未通过时，不得跳过步骤，不得生成目标产物，不得宣称测试实施流程完成。

每完成一个步骤的 artifact 后，必须执行 `complete` 命令通过门禁校验：

```bash
python toolset/test_agent_runner.py complete <run_id> <step_id>
```

中断恢复时，必须先通过 `status` / `next` 恢复进度，不得凭聊天上下文猜测当前进度：

```bash
python toolset/test_agent_runner.py status <run_id>
python toolset/test_agent_runner.py next <run_id>
```

测试实施 workflow 的事实来源：本 skill 与 `references/`。

## 何时使用

当用户已经有需求说明、代码变更说明或测试用例，并要求继续落地以下任一产物时使用：

- 测试实施指南
- 测试工具选型
- 测试执行记录
- 覆盖矩阵
- 最终测试报告 / 团队报告草稿
- 将一次功能测试流程沉淀成通用模板

本 skill 不负责重新设计完整测试用例。若用户要求“设计测试用例”，先使用 `test-case-design-checklist`。

当用户说“我需要进入测试实施阶段了，告诉我怎么进行”、询问如何与 Agent 协作完成测试实施，或需要解释测试实施阶段的人机分工时，优先打开并展示 / 解释同级文件 `test_execution_collaboration_flow.md`。

## 必须遵守的原则

1. 先确认输入资料：需求、测试用例、代码/配置变化、部署说明、环境说明、历史缺陷、已有工具。
2. 不把计划写成结果。实施指南写“应该怎么做”，执行记录写“实际做了什么”。
3. 执行测试前必须先列出可使用测试环境，并由 Agent 按 case 需求判断环境归属；能在默认环境覆盖的优先放默认环境，默认环境不满足时再匹配其它环境，只有必须依赖特定外部条件时才使用对应专用环境。环境列表不需要人类确认状态，环境本身不作为阻塞项。
4. 测试工具选型是必选步骤。工具选型表围绕本项目实际可用的测试工具类别展开（见下方“测试工具选型”）。Agent 必须根据业务用例判断各类工具的当前能力、是否需要改造、改造方向和验收标准；这些判断结果必须等待人类工程师确认。逐 case 只引用依赖的测试环境和测试工具，不在工具选型阶段展开长 case 明细表。
5. 每个 case 必须能让下一个人或 agent 按步骤执行，不能只写“验证功能正常”。
6. 每个执行结论必须有证据：请求 ID、关键业务标识、日志路径、报告文件、截图、数据库记录、接口返回、监控指标等，按业务实际选择。若 case 由自动化用例工具执行，且其断言已经覆盖测试意图，则该工具的执行报告、日志、用例定义和关键业务标识就是该 case 的证据；不额外要求补其它证据层。只有自动化断言不能证明测试意图、执行失败或需要调查定性时，才补跨层证据。
7. 无法执行或只能部分覆盖时，写清楚限制来自需求前提不可构造、环境能力不足、工具缺口、本轮范围外，还是待人工确认。
8. 恢复记录是条件产物。只有不同 case 需要切换包、配置、启动参数、服务状态、测试流量或其它环境配置时，才需要单独写恢复步骤并记录恢复前后状态；涉及重启时记录 PID 或等价运行态变化。不涉及环境变化时写明“不适用”或省略恢复步骤。
9. 生成团队报告时只从执行记录提炼，不新增执行记录里没有的结论；发送到团队渠道前必须先给用户预览并获得明确确认。
10. 若本次需求引入新的业务能力（例如新的类型、语义、配置能力、接口能力），最终报告完成并通过验收后，必须执行“已知业务能力沉淀检查”：列出新增能力名称、支持范围、限制条件、证据来源，并提示回填对应业务能力基线文档。
11. 生成实施指南后必须做 Markdown 格式自检：所有表格的表头列数、分隔行列数和数据行列数必须一致；长路径、长说明、长验收标准优先使用列表或表格后的说明段，不塞进表格单元格；若发现表格渲染为普通文本，必须先修复再交付。
12. 测试过程默认不得使用 `sudo` 破坏执行环境。除 `systemctl` 停启明确 unit 等真实特权边界外，实施指南、执行记录、恢复步骤和临时命令不得默认写入 `sudo mkdir`、`sudo touch`、`sudo tee`、`sudo chown`、`sudo find ... -exec rm -rf`、`sudo kill`、`rsync --delete` 等会制造 mixed ownership、全量清理共享内存或删除执行环境内容的动作。若普通运行用户无权写入，必须标记为 ownership 阻塞；一次性修复需人类明确授权并限定目标路径。

## 推荐产物路径

对单个需求，建议放在：

```text
docs/iterations/<需求编号或功能名>/
```

新迭代测试中必须落地、后续需要 review / 提交的正式产物必须放在 `docs/iterations/<需求编号或功能名>/` 下：

```text
requirements_analysis.md
test_cases.md
test_execution_guide.md
test_execution_record_<YYYYMMDD>_<env>.md
test_report_<YYYYMMDD>_<env>.md
```

Agent 中间工作文件不要放进正式 docs 目录，也不要提交 git。按用途分流：

- 一次性临时执行载体或临时输出（只为单次验证生成的脚本、临时数据、diff 明细、临时分类表、辅助脚本输出），默认放本机 `/tmp/<需求编号或功能名>/`；需要上传远端执行时也放远端 `/tmp/<描述性文件名>`。
- 需要跨 agent 交接、可复核但不应提交的工作稿，才放当前项目的 `.agent_tmp/<需求编号或功能名>/`。

正式文档只记录必要结论、路径摘要和门禁状态。若执行记录引用了临时载体，必须同时写明正式 case 来源文件；不得把一次性临时执行载体沉淀为 `docs/iterations/...` 下的迭代 artifact。

## 文档生成流程

### 1. 输入资料确认

列出本次使用的资料来源，并标注是否已确认：

- 需求/通知/issue
- 测试用例文档
- 代码变更或配置变更
- 部署包/版本/分支
- 可使用环境
- 已有自动化、脚本、mock 服务、分析工具
- 历史缺陷或风险清单
- 用户在当前对话中的澄清

有冲突或缺失时，先标注待确认；会影响执行安全或结论口径的，先问用户。

### 2. 测试范围与执行口径

明确本轮：

- 测什么
- 不测什么
- 所有已进入测试用例文档的 case 都应进入实施指南；当前不能执行的 case 不删除，标记为 `阻塞`、`本轮不执行` 或 `当前口径部分覆盖`
- 哪些 case 需要特殊环境或特殊工具
- 哪些 case 只能部分覆盖
- 哪些 case 本轮不执行及原因
- 哪些回归由别人或其它环境完成，只在本轮记录说明

### 3. 可使用环境列表

执行测试前必须先列出本轮可使用环境（示例分层，按项目实际填写）：

- `test`：默认优先环境；能在此覆盖的 case 优先归到默认环境。
- `test01`：当默认环境不满足场景口径时使用（如特定周期/长稳类 case）。
- `uat`：只有默认环境无法覆盖，或必须依赖 UAT 外部条件时使用。

环境列表不需要人类确认状态，不作为阻塞项。具体 case 选择哪个环境，在逐 case 实施步骤中标注。

case 是否阻塞必须按 case 级前置条件逐项判断；测试环境本身不构成阻塞，但工具能力、mock 能力、业务口径、需求设计、测试数据、外部依赖、失败注入方式、UAT 条件、人工处理流程等任一项未确认或不具备时，该 case 必须保持 `阻塞`，不得进入真实执行。

### 4. 测试工具选型

测试工具选型按项目实际可用的工具类别展开，并由 Agent 根据业务用例判断当前能力、是否需要改造、改造方向和验收标准。常见通用类别：

- **自动化用例工具**：精确单 case、可断言、固定回归。
- **长稳 / 持续测试工具**：长跑、跨周期、持续流量、状态保留、结果归档。
- **依赖模拟器 / mock 服务**：构造外部或下游依赖的特定行为。

`当前能力判断` 和 `是否需要改造` 由 Agent 先判断，但结果必须保留 `人类确认状态`。未经人类工程师确认，不能把依赖该工具能力的 case 写成可直接执行。

工具选型表必须保持可读：表格单元格只写短摘要，避免把长段落塞进单元格；详细改造方向、影响 case 和验收标准放在表格后的分工具小节中。生成 Markdown 表格时，表头列数、分隔行列数和数据列数必须一致。

工具能力分析必须回答：

- **自动化用例工具**是否能真实构造目标输入、字段、动作链和断言；是否需要新增用例、字段支持、报告字段或分析脚本。

  若需要新增或改造自动化用例，必须遵守以下通用规则：

  - 先根据测试用例生成用例草稿交人类审核，审核通过后再落地为可执行形式，并做回归对账（把落地形式反解析回用例结构，确认与草稿一致）。
  - 用例的名称必须拼接测试用例文档中的 Case ID，确保可反查来源用例。
  - 用例草稿经人工确认后是正式产物，必须放在独立文件（如 `docs/iterations/<需求名>/auto_cases/proposed_cases.<ext>`）；测试意图和断言说明只写入用例的描述字段。
  - 只为单次执行子集或验证修正效果生成的临时用例是临时执行载体，必须放 `/tmp`，不得放入迭代目录。
  - 断言计划、字段确认草稿等可交接工作稿放 `.agent_tmp/<需求名>/auto_cases/`，不提交 git；反解析临时输出和 diff 明细默认放 `/tmp/<需求名>/auto_cases/`。
  - 不得把用例正文塞进测试实施指南；实施指南只记录用例路径、落地命令摘要和对账状态。
  - 用例未审核、未落地或对账未通过前，依赖该自动化用例的实施 case 必须保持 `阻塞：自动化门禁未通过`，不得执行。

- **长稳 / 持续测试工具**是否能支持长跑、跨周期、持续流量、状态保留、结果归档和证据采集；是否需要新增样本、参数、断言或分析能力。
- **依赖模拟器 / mock 服务**是否能提供目标外部行为（如正常应答/拒绝、部分完成、完全完成、撤销/改动拒绝、超时、边界事件等）；是否需要新增配置、控制脚本或原始回报记录能力。

逐 case 实施步骤必须引用依赖的测试环境和测试工具，例如：`测试环境：test`，`测试工具：自动化用例工具`。环境不作为阻塞项；若依赖工具的能力判断为“不支持 / 部分支持但无法证明目标输入真实发出 / 分析脚本无法区分该能力 / 人类未确认”，该 case 的实施状态必须标记为 `阻塞：待工具改造确认`。阻塞原因不限于测试工具，也可能是业务口径、需求设计、测试数据、外部依赖、mock 能力、失败注入方式、UAT 条件或人工处理流程尚未确认。Agent 必须写清楚阻塞原因、需要谁确认、解决后如何验收；未经人类工程师确认解决，不得进入执行阶段。

只要实施指南中仍存在任一阻塞项，必须在指南中明确提示：阻塞项解决并经人类工程师确认后，方可执行对应 case。存在阻塞项的 case 可以进入测试报告工作稿作为 `阻塞` 占位记录，但不得真实执行，不得填写真实执行结果或宣称该 case 可以开始执行；未阻塞 case 可在确认范围内继续落地。

工具选型结论必须写入实施指南；实际使用情况必须写入执行记录。

### 5. 实施测试指南

按 case 拆步骤。每个 case 至少包含：

- Case ID / 名称
- 目标
- 前置条件
- 测试环境
- 测试工具（自动化用例工具 / 长稳工具；如需临时手工工具，必须写明原因和确认状态）
- 自动化状态（如适用）：已有用例、草稿路径、人类审核状态、落地状态、对账状态
- mock / 模拟器能力依赖（若适用）
- 输入数据
- 执行动作或命令
- 观察点
- 断言方式
- 证据采集
- 通过标准
- 失败 / 阻塞处理

逐 case 必须显式标注依赖的测试环境和测试工具。所有测试用例 case 都应进入实施指南；若当前不能执行，只能写阻塞状态、阻塞原因、补齐动作和验收标准，不得从实施指南中删除或写成可直接执行。只要存在任一阻塞项，必须提示“阻塞项解决并经人类工程师确认后，方可进入执行阶段”。只有涉及包、配置、参数、服务状态或测试流量切换的 case，才需要单独写恢复步骤；不涉及时标注“不适用”或省略。

若逐 case 由自动化用例工具执行，并且其断言已经覆盖该 case 的测试意图，指南中的证据采集只写该工具的执行报告 / 日志 / 用例定义 / 关键业务标识；不要再要求额外证据层。若自动化断言只是部分覆盖，必须在“自动化不能证明部分 / 补充证据”中写清。

使用模板：`references/test_execution_guide_template.md`。

生成后自检：

- 检查所有 Markdown 表格列数一致，尤其是表头、`---` 分隔行和每一行数据。
- 检查表格单元格是否过长；长路径、长改造方向、长验收标准应移到列表或表格后的说明段。
- 检查所有测试用例 case 是否都进入指南；不能执行的 case 是否保留为阻塞 / 本轮不执行 / 当前口径部分覆盖，并写清阻塞原因、解决动作和验收标准。
- 检查是否错误地把测试环境作为阻塞项；环境只用于标注 case 执行位置。
- 检查是否包含 `自动化状态` 章节；不涉及新增 / 改造时必须写“不适用”，涉及时必须记录用例草稿、落地文件、反解析结果、对账结果和门禁状态。

### 6. 执行测试与测试报告工作稿

当用户第一次要求“执行测试”时，不是直接逐条跑 case，也不是等全部跑完后才写报告；必须按以下顺序执行：

1. 先确认是否已有可执行的测试实施指南。
   - 若没有实施指南，先回到 `execution_guide` 流程生成。
   - 逐 case 检查是否仍有阻塞项；未解决的 case 保留 `阻塞` 状态，只进入报告工作稿占位，不进入真实执行。
2. 启动或推进 Runner 到测试执行产物。
   - 若这是本轮第一次进入执行阶段，使用 `target=execution_record`。
   - 该产物在执行阶段作为“测试报告工作稿 / 执行记录”使用，不是最后才生成的静态报告。
3. 根据测试实施指南和模板，先生成测试报告工作稿骨架。
   - 所有实施指南中的 case 都要进入报告工作稿。
   - 初始状态可以是 `待执行`、`阻塞`、`本轮不执行` 或 `当前口径部分覆盖`。
   - 对执行周期长、需要跨周期或多轮观察的 case，必须在首次触发或准备执行时先写入可续跑信息：测试环境、测试工具、输入请求 / 配置 / 数据、关键标识、启动时间、预期观察节点、每个节点需要检查的断言和证据位置。后续 agent 必须基于这些信息继续观察和补证据，而不是重新猜测输入或重跑 case。
4. 按实施指南逐 case 执行。
   - 执行每个 case 前，必须再次检查该 case 是否还有未解决阻塞项；只有状态为可执行且所依赖工具 / mock / 业务口径 / 数据 / 外部条件均已确认时，才允许真实执行。
   - 若仍有阻塞项，只更新报告工作稿中的阻塞原因、需确认人、解决动作和验收标准，不得运行该 case。
   - 每执行完一个 case，立即更新报告工作稿中对应 case 的执行明细。
   - 对长周期 case，每完成一个观察节点就立即更新该节点的观察时间、实际状态、断言结果、证据路径和下一步动作；未到观察时间的节点保持 `待观察`，不得提前写通过或失败。
   - 不得等全部 case 执行完后再回填，也不得先写最终结论再补证据。
5. 全部可执行 case 处理完后，再从报告工作稿提炼最终摘要或团队报告草稿。

测试报告工作稿必须按真实发生顺序和 Case ID 记录。不要事后只写汇总。
长周期 case 的报告工作稿必须具备交接能力：即使更换 agent，也能从已记录的输入、关键标识、观察节点、待补证据和下一步动作继续检查。

必须包含：

- 执行摘要
- 当前执行口径说明
- 测试工具选型结果
- 逐 case 执行明细
- 恢复记录（仅当本轮涉及包、配置、参数、服务状态或测试流量切换时必填；否则写不适用）
- 覆盖矩阵
- 补充执行明细
- 未覆盖 / 阻塞项
- 测试工程反思候选

状态枚举建议统一为：

```text
待执行 / 通过 / 失败 / 需复测 / 当前口径部分覆盖 / 本轮不执行 / 不单独执行但已覆盖 / 阻塞
```

使用模板：`references/test_execution_record_template.md`。

### 7. 最终摘要 / 团队报告

最终摘要或团队报告只从已逐 case 更新过的测试报告工作稿提炼。报告中必须区分：

- 已验证通过
- 发现的问题或需复测项
- 部分覆盖和未执行项
- 环境恢复状态（如适用）
- 剩余风险
- 新增业务能力沉淀项：若本次需求新增了业务能力，报告必须列出能力名称、支持范围、限制条件、验收证据和建议回填位置；若没有新增能力，写明“不涉及新增业务能力沉淀”

若用于团队渠道，先给用户预览；用户确认后再发送。不能跳过逐 case 执行明细直接生成摘要。

使用模板：`references/team_report_template.md`。

### 8. 测试工程反思

每次完整测试结束后，输出候选沉淀项，但不要自动写入全局规则或其它 skill，除非用户确认。

至少覆盖：

- 已知业务能力沉淀检查：本次是否新增业务能力；若新增，是否需要回填业务能力基线文档
- 本次暴露的规则缺口
- 本次暴露的 skill / 执行流程缺口
- 本次暴露的工具缺口
- 建议沉淀项：规则 / 字典 / skill / checklist / 自动化工具

## 输出要求

- 和用户沟通使用中文。
- 文档内容要可执行、可复核、可交接。
- 保持通用，不在模板中写死某个项目、服务、字段或需求编号。
- 项目特有内容只写进具体需求文档，不写进本 skill 的通用模板。
