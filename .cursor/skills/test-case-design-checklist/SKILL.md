# 测试用例设计检查清单

## 硬规则：用例名称必须直接表达测试意图

用例名称必须让评审人只看标题就知道：
- 这个 case 要证明什么业务事实，或
- 这个 case 要防止什么业务风险

禁止把用例名称写成“测试对象 + 检查/校验/验证”这类检查项标题。

反例：
- 撤单校验
- GTC 订单检查
- 部分成交后改单验证

正例：
- 终态订单再次撤单必须被拒绝且不能复活旧订单
- GTC 订单跨日后必须保持有效而不能被误清理
- 部分成交后改单数量不能小于已成交数量

## 默认交付模式：用例设计分两个文档

除非用户明确要求只保留单文档，否则“测试用例设计”默认拆成两个文档交付：

1. **测试用例设计方案**
   - 保留：信息来源、跨资料甄别、需求分析、范围过滤、覆盖清单、维度分组、场景总览、判定表、优先级、缺口与待确认项。
   - 不保留：完整的逐条 case 表。

2. **具体用例设计**
   - 保留：按分组组织的正式 case。
   - 每个分组前保留简短说明（例如“发布过程”或“这组在测什么”）。
   - 不保留：信息来源、术语表、方法论、覆盖回查、优先级、缺口分析等方案层内容。

执行要求：
- 两个文档中的 case 集合必须一致，发布前必须做一次 **Case ID 对账**。
- “测试用例设计方案”文档里应明确指向“具体用例设计”文档。
- “具体用例设计”文档里不得重新堆入方案层内容，只保留分组说明和正式用例。

## 默认设计方法：场景法为主线，其他方法为辅

通用测试用例设计默认采用以下方法组合：

1. **场景法作为主线**
   - 先按完整业务流程、真实发布过程或真实使用路径组织主线 case。
   - 先回答“这次完整流程怎么发生”，再讨论局部动作或单点规则。
   - 文档主阅读路径优先按场景展开，而不是先按技术模块或动作拆分。

2. **其他方法作为补充**
   - **边界值法**：补充时间点、数量、文件缺失 / 损坏、顺序边界等高风险边界。
   - **等价类划分**：压缩重复输入空间，识别“同类场景”的代表值。
   - **判定表法**：用于规则组合多、条件交叉多的主题。
   - **状态迁移法**：用于有明显状态流转、异常恢复、Retry、重启、会话中断的主题。
   - **错误推测法 / 风险驱动法**：补充历史高风险点、经验性缺陷和优先级排序。

执行要求：
- 不得一开始就把文档主线拆成“模块列表 / 接口列表 / 字段列表 / 技术动作列表”这类零件章节。
- 这些维度可以存在，但应作为支撑校验点、边界补充或映射层，而不应取代场景主线。
- 如果用户明确要求按模块法、接口法或其他方式组织，则从用户指令。

## 必须遵循的流程

设计测试用例或测试计划时，始终按以下顺序执行：

1. 列出正在使用的**信息来源**。
2. 执行**跨资料甄别**（阅读、比对、标记冲突与歧义；在锁定基线前上升给人类工程师确认）。
3. 基于甄别后的资料编写**需求分析**，并在交付物中包含**资料甄别记录**。
4. 在构建覆盖清单前先应用**范围过滤**。
5. 在写任何 case 之前先构建**覆盖清单**。
6. 将覆盖清单分组为清晰的测试维度。
7. 对每个维度先列出简短、具体的测试点。
8. 将测试点拆解为具体 case，并应用**三质量标准**。
9. 按默认交付模式整理为**测试用例设计方案**和**具体用例设计**两个文档；若用户明确要求单文档，则在此步说明例外。
10. 完成 case 草稿后，执行一次**基于覆盖清单的回查**。
11. 如果某个清单项未覆盖，要么明确补充 gap 说明，要么补 case。
12. 如果设计过程中有任何规则更新，要对所有章节做一次**一致性扫描**。
13. 发布前对“方案文档”和“具体用例文档”执行一次 **Case ID 对账**，确认具体用例文档没有漏 case。

绝不能跳过第 1 步、第 2 步、第 3 步、第 10 步、第 12 步或第 13 步。

### 何时需要深入阅读资料

一旦识别出资料来源（第 1 步），就必须开始深入阅读和思考，并持续到跨资料甄别（第 2 步）结束。需求分析（第 3 步）在第 2 步完成前，或在相关问题仍标记为待人类确认前，**不得**把存在冲突的资料当作既定事实。

**优先级规则：** 在写任何规范性需求或测试用例之前，**必须先做资料交叉比对**，而不是等 case 写完后再回头检查。

## 第 1 步：列出信息来源

每次开始设计测试时，先列出你所依赖的资料基础。

常见资料类型包括：
- 业务需求或产品文档
- 架构文档或交互设计文档
- 协议或交易所规范
- API 文档
- 既有 case 或回归集
- 代码行为或日志
- 当前对话中用户补充澄清的内容

如果信息缺失或冲突：
- 说明缺的是什么
- 区分已确认事实与假设
- 在把假设写进 case 前先向用户确认

### 资料版本过滤（强制）

当多份文档描述同一主题（标题或路径相同或相近）时，必须在做资料甄别前先执行版本过滤：

1. 优先使用显式标注为 `CURRENT`、`LATEST`、`正式版`、`生效版`，或审批修订日期最新的资料。
2. 对标注为 `HISTORICAL`、`历史`、`归档`、`deprecated`、`superseded`、`obsolete` 的资料，视为非基线参考。
3. 如果同一主题同时存在 current 和 historical 版本：
   - 只有 current 版本可作为需求和测试用例的规范性基线。
   - historical 版本只能在简短的“背景/差异”说明中引用，**不得**用来定义 expected result。
4. 在“信息来源”章节中，每份资料都必须打上以下标签之一：
   - `BASELINE-CURRENT`
   - `REFERENCE-HISTORICAL`
   - `PENDING-CONFIRMATION`
5. 如果两个候选“当前版本”资料互相冲突，且没有既定优先级规则，必须上升给人类确认，并在写规范性 case 前标记为 `PENDING HUMAN`。

## 第 2 步：跨资料甄别（强制）

这一步是**高优先级**动作。它必须在列出资料后立即执行，并且必须在需求分析被视为权威结论之前完成。

**目标：** 围绕会影响测试的维度（时间线、术语、行为归属、阶段名称、API、版本日期等）比对所有资料，识别：

- **直接冲突**：资料 A 和资料 B 明确给出不同事实。
- **表述歧义**：措辞含糊、术语未定义、范围不清。
- **静默不一致**：同一个词在不同资料里的含义不同（例如时区不同、对“maintenance window”边界定义不同）。

**执行方法：**

1. 对每个高风险主题（如时间表、状态机、错误语义、版本偏差），提取**每份资料**的单行结论。
2. 构建甄别表或甄别列表：

   | 主题 | 资料 A | 资料 B | 问题类型（冲突 / 歧义 / 术语漂移） | 建议动作 |
   | ---- | ------ | ------ | ---------------------------------- | -------- |
   | ...  | ...    | ...    | ...                                | 问人 / 采用主资料 X / 标记 ASSUMPTION |

3. 对所有会影响 case 或验收标准的冲突与歧义，**必须上升给人类工程师确认**。除非用户已经在当前对话中明确给出优先级规则，否则不得私自选定其一。
4. 对上升后仍未关闭的问题，必须清楚标记为：`PENDING HUMAN`、`ASSUMPTION (until confirmed)` 或 `OUT OF SCOPE`。
5. 如果冲突来自 current 与 historical 文档，默认以 current 为准，并记录：`Historical ignored for baseline`。

**交付要求：** 甄别结果必须**复制进最终文档**，作为 **Source reconciliation**（或等价章节）存在，并在 **Requirements analysis** 中再次总结为**采用基线**（即本文档后续依赖的结论）。

## 第 3 步：需求分析

完成跨资料甄别后，用几条平铺的 bullet 总结需求。

总结应覆盖：
- 在测什么
- 系统职责边界
- 关键状态变化或业务结果
- 重要排除项或非目标
- **采用基线**：在存在冲突时最终采用了哪些资料，以及人类确认了什么
- 仍待确认的假设（必须与甄别表保持一致）

不要从原始资料直接跳到测试用例。

**文档规则：** 需求分析里必须让评审人看见**跨资料甄别结论**，不能只停留在聊天记录里。测试设计文档中的 case 前置条件和 expected result，也必须与**文档中显式写出的基线**一致，不能依赖未写明的隐式选择。

## 第 4 步：范围过滤 —— 不该写进本次用例的内容

在构建覆盖清单前，先过滤以下内容。这些**不属于**本次新增需求 case：

- **既有固有行为**：在本次变更前已经存在、且不受本次需求影响的行为。它们应进入回归集，而不是写进本次新增需求 case。
- **外部系统边界**：如果某个边界（例如会话状态切换时间）由外部系统（交易所、上游）拥有并强制执行，不要写 case 去验证外部系统切换正确与否；应写 case 验证你的系统在各状态内的行为。
- **回归管理**：回归集或冒烟集是独立工件，由自动化体系管理，不要直接嵌进新增需求 case。

只有以下情况才应纳入：
- 该行为是本次需求**新引入的**，或
- 既有组件的行为会因为本次需求而**发生变化**

## 第 5 步：构建覆盖清单

应用范围过滤后，构建一份平铺的覆盖维度清单。

常见维度包括：
- 功能动作
- 角色或客户类型
- 状态转换
- 时间窗口或时段
- 上下游消息链路
- 成功路径
- 失败来源分类
- 恢复或重启行为
- 配置变体
- 外部依赖行为
- 审计、日志或可观测证据

如果设计中存在多跳或分层校验（例如 gateway -> router -> downstream），
必须增加一个“多层失败模式”子清单，明确覆盖：
- 主层正确拦截
- 主层漏拦，次层兜底拦截
- 主层与次层判断不一致（fail-safe 行为）
- 双层同时漏拦（高风险路径：告警 + 可观测性 + 事件闭环）

项目需要时，应补充领域特定维度。

## 第 6 步：维度分组

把覆盖清单整理成几个易读分组，例如：
- 核心主流程
- 异常与失败
- 时间或状态边界
- 集成与透传
- 运维与恢复

**默认组织原则：**
- 分组时优先形成“场景主线”章节，例如“完整主流程 / 典型组合场景 / 通用异常分支”。
- 技术模块、校验点、字段清单、日志层等内容，优先作为场景章节下的支撑说明，而不是先天一级目录。

## 第 7 步：列出简明测试点

在写 case 前，先为每个维度列出简短测试点。

好的测试点示例：
- 请求南向透传且内容不变
- 回应北向透传且内容不变
- 交易所主动撤单前不存在客户端撤单请求
- 失败被归类为交易所拒绝，而不是连接中断

不要还没写测试点就直接跳到长表格 case。

如果已经明确存在一条完整业务主线，应先写出该主线的场景测试点，再补异常、边界、组合和恢复分支。

## 第 8 步：拆解为具体测试用例

把测试点转换成可执行 case。

case 的 `name` 必须表达测试意图 —— 评审人只看名称，就应知道该 case 在验证什么业务事实，而不只是看见执行动作顺序。

每个 case 至少应包含：
- Case ID
- 简短用例名称
- 场景或触发条件
- 前置条件
- 预期结果
- 如有需要，补充证据来源

在有帮助时，可按以下维度拆分：
- 客户类型
- 时间边界
- 连接状态
- 请求类型
- 环境变体

### 每个 case 的三质量标准

在定稿前，对每个 case 执行以下三项质量检查：

**可执行（Executable）** —— 测试人员无需额外解释即可独立执行：
- 用例名称必须带出具体触发点、阶段或时间点（例如“收盘时段 / 16:00:05 / 盘前时段”），而不只是泛泛写“验证 maintenance window 行为”
- 前置条件必须是可检查的系统状态（例如“客户端和上游服务已断开”），而不是模糊描述（例如“处于异常状态”）
- expected result 必须是可观测结果，并注明证据类型（例如“client 收到失败响应”或“可在 link log 中看到”），不能只写“行为正确”

**可回归（Regression-ready）** —— case 可以自动化或稳定复现，而不依赖人工理解：
- expected result 中每一条都应能独立断言（可映射为单条 assert）
- case 之间的状态依赖必须显式写在前置条件中，不能依赖隐含执行顺序

**可评审（Reviewable）** —— 需求方和开发读 case 就能确认覆盖范围：
- case 必须围绕业务维度组织（例如按 maintenance window 时间阶段），而不是按技术模块组织
- 需求分析中的每一条规则，都必须能追溯到至少一个 case

### 多层逻辑脆弱性检查（适用时强制）

当某条规则由多个组件共同拦截或执行时，必须补充兼容性 case，
覆盖低概率链路缺陷，包括时钟/状态漂移和消息延迟穿越边界。

至少要包含以下四类 case：
- Layer A 检出，Layer B 一致
- Layer A 漏检，Layer B 兜底检出
- Layer A 与 Layer B 结论不一致
- 双层同时漏检（必须断言高优先级告警和取证日志）

不要把这些当作可选“边界 case”。只要存在分层校验，这些就是强制安全 case。

## 第 9 步：双文档整理

按默认模式产出两个文档：

### A. 测试用例设计方案

适合保留：
- 信息来源
- 跨资料甄别
- 需求分析
- 范围过滤
- 覆盖清单
- 维度分组
- 场景总览 / 判定表
- 优先级
- 缺口与待确认项

不应保留：
- 大段逐条 case 表

### B. 具体用例设计

适合保留：
- 分组标题
- 每个分组前的简短说明
- 正式 case 表

不应保留：
- 信息来源
- 术语表
- 方法论
- 覆盖回查
- 优先级
- 缺口分析

如果用户明确要求只保留单文档，必须在文中说明这是例外模式。

## 第 10 步：强制回查

完成 case 草稿后，创建一个简短回查章节：
- 清单项 -> 被哪些 case ID 覆盖

## 第 11 步：覆盖缺口

如果某个清单项尚未覆盖：
- 明确写 `Uncovered:`
- 列出缺口项
- 然后要么补 case，要么说明为什么它有意不在本轮范围内

## 第 12 步：规则变更一致性扫描

当设计过程中任一规则发生更新时（不只是最终阶段），在发布前扫描以下位置是否残留旧口径：

1. **Source reconciliation** —— 冲突/歧义是否仍与最终人工决策一致？
2. **Information sources summary** —— 资料章节里列出的规则是否已更新？
3. **Requirements analysis** —— 业务规则基线是否已同步？
4. **Coverage checklist** —— 清单项措辞是否仍用旧规则？
5. **Case names** —— 用例名称是否已经反映当前规则？
6. **Expected results** —— 预期结果是否与当前规则一致？
7. **Two-document split** —— “方案文档”和“具体用例文档”是否仍各自保持边界，没有互相串味？

如果任何位置仍保留旧规则，必须修正并显式标记变更：
> Rule updated: [old rule] → [new rule]

这样评审人就能确认该变更是有意的，而不是误改。

## 第 13 步：Case ID 对账

在双文档模式下，发布前必须做一次 Case ID 对账：

- 方案文档中提到的 case 范围，必须在“具体用例设计”中完整落地。
- 具体用例文档中的 Case ID，不能多出未经方案文档承接的额外 case。
- 若方案文档已经删除具体 case 表，则必须至少保留：
  - 具体用例文档链接
  - case 范围说明或分组范围说明

对账结论必须明确写成一句话，例如：

> 已对账：具体用例文档未丢失任何 Case ID。

## 复杂业务专项提醒（多层链路 / 状态窗口）

当被测系统是**多层链路**（如 `网关 -> 路由 -> 下游依赖`）或存在**时间/状态窗口**（如维护窗口、切换窗口、周期边界）时，跨资料甄别通常至少要比对：
- 外部规范 / 公开文档 与 内部实现文档（字段口径、时区、阶段名称、修订日期是否一致）
- 面向外部的接口契约 与 内部各组件行为（各层是否对同一事件给出一致语义）

若当前任务属于这类复杂业务，在写 case 前先构建一张显式**规则矩阵**：
把每个格子都填上，再确认每个“拒绝”格至少映射到一个失败 case，
每个“放行但透传”格至少映射到一个能区分**本地拒绝**与**下游拒绝**的 case。

示例矩阵（`<窗口>` × `<请求类型>`，格值填期望行为）：

| 窗口 / 状态 | 请求类型 A | 请求类型 B |
|--------|-------------|------------|
| 正常期 | ? | ? |
| 边界期（切换前） | ? | ? |
| 边界期（切换后） | ? | ? |
| 维护期 | ? | ? |

还要检查以下通用维度是否需要覆盖：
- 不同请求路径之间的行为差异
- 透传语义（下游请求已发送 + 结果原样回传）
- 由外部/下游驱动的终态事件（不要求事先存在客户端主动请求）
- 不同客户/租户类型差异及其边界期行为区别
- 连接失败、下游拒绝、本地拒绝 —— 三者必须可区分
- 周期切换或运维重启路径，以及目录/日期正确性
- 各层之间业务日 / 处理日的一致性
- 上下游组件之间的时钟或日历漂移
- 延迟消息跨越会话边界（接入时间与下游发送时间不一致）
